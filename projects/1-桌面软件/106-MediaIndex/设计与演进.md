# P106｜MediaIndex 设计与演进

> 记录影响长期维护的设计决策。硬约束以 `开发约束.md` 为准。

## D-01｜问题定义不是传统重复文件清理

MediaIndex 的核心问题是：

> 新收到的媒体是否已经以原版、压缩版、转码版、裁剪版或其他同源形式存在于大规模库存中，并返回其位置。

因此产品优先级是“查询与定位”，不是“扫描后删除重复”。

## D-02｜库存保持原位，建立旁路索引

原媒体目录保持不动。系统维护独立索引：

```text
可恢复路径标识
卷或存储标识
媒体元数据
精确 hash
感知指纹
局部特征或其摘要
视频时间序列指纹
```

离线磁盘仍可保留路径与索引状态。

## D-03｜快速召回与最终判定分离

图片当前架构：

```text
Exact hash
→ selected perceptual regions
→ compact visual-word candidate retrieval
→ Top-k candidates
→ local geometry
→ content consistency
→ final class
```

原因：单一全局 hash 对强裁剪脆弱，而局部特征不适合对几十万库存逐一暴力比较。

## D-04｜分级结果而不是二值重复

图片预期输出至少分为：

- Confirmed
- Probable
- Similar
- Not found

视频在此基础上进一步区分：

- Exact file
- Same video
- Derived video
- Partial clip
- Composite / edited sequence
- Similar
- Not found

“Similar”不等于“Same source”。

## D-05｜AI embedding 后置

在传统视觉召回 + 局部几何无法满足召回前，不默认引入 AI embedding。

AI embedding 更适合语义相似和候选补漏，但可能把同场景不同照片推得很近，因此不能默认承担最终同源判定。

## D-06｜图片视觉底座先收敛，但视频算法验证不等待图片 UI

早期设想是图片完全冻结并做完 MVP 后再进入视频。

R001 至 R016 之后，视觉底座已经足够清晰：

- pHash Lane A。
- visual-word Lane B。
- selected-frame verifier。
- verifier thumbnail / low-texture fallback。

因此调整顺序：

1. 图片视觉算法与索引继续完成 A4 前冻结。
2. 同时在 `p106-exp` 开始视频 V 系列算法验证。
3. 视频直接复用图片视觉引擎，只增加 sampled frame、timestamp 和 temporal alignment。
4. 在视频基本需求暴露后再冻结统一数据库和索引格式。
5. 最后再进入正式 UI 与产品化。

这样可以避免先做完图片产品，再因为视频时间索引要求重构核心数据结构。

## D-07｜视频时间层采用模型层级，不使用单一全局直线

V003 已证明：

- 普通 clip 适合 constant offset。
- 轻微 speed change 适合 affine model。
- 中间删除会产生多个 offset mode，单一 affine 会误拟合。

因此视频时间模型固定采用层级思路：

```text
constant offset
→ affine speed
→ piecewise monotonic alignment
```

正式 piecewise 算法尚未冻结，但不得退化为只支持全局 offset / slope。

## D-08｜共享视觉引擎，不建立图片和视频两套重复算法

视频 sampled frame 必须尽量复用图片：

- pHash。
- multi-region layout。
- visual-word quantization。
- verifier thumbnail。
- SIFT / NCC。
- low-texture fallback。

视频新增的是：

- video_id。
- timestamp。
- frame sequence。
- temporal correspondence。
- clip interval。

避免两套视觉代码长期漂移。

## D-09｜视频倒排索引必须保留 timestamp

V007 否定了把一个视频压成无序 visual-word bag 的方案。相关视频会复用相似局部内容，whole-video voting 会丢失最重要的顺序和时间位置。

因此视频 postings 至少必须保留：

```text
visual token
→ video_id
→ timestamp / frame_id
```

视频 candidate score 必须联合视觉证据和时间一致性。图片 Lane B 可以继续使用 image_id postings，但视频不能丢弃 frame timestamp。

## D-10｜视频基础采样暂定约 1 fps，scene keyframe 只做增强

V005 中：

- 0.5 s sampling：9/9 related 正确。
- 1 s：9/9。
- 2 s：5/9。
- 4 s：5/9。

2 s 及更粗采样对短 clip 出现 sampling phase alias，因此当前设计方向是：

```text
uniform baseline ≈ 1 fps
+
scene / motion adaptive extra samples
```

scene keyframe 不能完全替代 uniform baseline。正式采样率仍需长视频和真实视频域验证。


## D-11｜视频必须支持歧义而不是强行唯一

V012 中，多个视频使用完全相同的片头和片尾。

仅查询共享片头时，所有视频得到相同证据。

因此结果层必须允许：

- 多个 source video 同时成立。
- 同一个 source video 存在多个 source intervals。
- 共享模板片段降权。

不能为了 UI 简单而强迫所有 Query 只返回一个唯一 source。

## D-12｜视频 local-feature rescue 发生在候选和时间层之后

V013 证明强竖屏裁剪可以被 SIFT + RANSAC 明显救回。

为了控制成本，正式顺序应是：

```text
cheap temporal candidate retrieval
→ rough time neighborhood
→ local geometry verification
```

而不是全库逐帧 SIFT。

但候选层必须足够宽，或者 local-feature inverted index 必须能独立召回正确 source，避免 pHash 过早丢掉强裁剪视频。

## D-13｜视频索引按时间层级存储

V014 否定“每个 sampled video frame 保存完整图片签名”的实现。

固定设计方向：

```text
V0
continuous lightweight temporal anchors

V1
sparse local-feature keyframes

V2
very sparse verifier cache

A
audio fingerprint sequence
```

图片与视频共享算法实现，不共享相同记录密度。

## D-14｜音频是 supporting evidence，不是 same-video 充分条件

V010 中，相同音轨可以被放到完全不同的视频上，并得到完全一致的 audio fingerprint。

因此：

```text
audio match
不能单独推出
same video
```

Audio Lane C 用于：

- 快速候选。
- source time 定位。
- 视觉困难场景补证。

最终 Same / Derived 仍需要视觉证据或明确的多模态一致性。
