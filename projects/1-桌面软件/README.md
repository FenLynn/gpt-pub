## 接入顺序

1. 阅读根目录 `GPT_RULES.md`；
2. 阅读根目录 `目录.md`；
3. 阅读本文件；
4. 阅读项目 `README.md`、`阶段记录.md` 和迁移或发布资料；
5. 查看本项目的 `exp`、`stable`、PR、标签与 CI；
6. 明确本次只修改哪个项目和哪个目标分支。

## 分支模型

| 项目 | 日常开发 | 稳定候选 | 正式主线 |
|---|---|---|---|
| P101 | `p101-exp` | `p101-stable` | `main` |
| P102 | `p102-exp` | `p102-stable` | `main` |

默认流程：

```text
main 同步到 exp
→ 日常推进 exp
→ PR：exp → stable
→ 完整 Windows/Linux 与打包验收
→ PR：stable → main
→ main 标签与 Release
→ main 回流 stable / exp
```

日常串行修改可以直接推进对应 `exp`。并行、高风险或容易放弃的尝试使用短期项目分支，完成后回到 `exp`。`stable` 和 `main` 不做日常开发。

由于每条 Git 分支都包含整个仓库，P101 的长期分支相对 `main` 只能修改 P101 目录及其 CI，P102 同理。项目长期分支不得互相合并。

## 桌面软件共同规则

- 源码、测试、配置和关键说明保留在各自项目目录；
- 活动 CI 位于根目录 `.github/workflows/`，必须限制项目路径和目标分支；
- `exp` 运行快速检查，`stable` 运行完整 Windows 原生验证和正式打包；
- 构建目录、缓存、日志、自动生成测试媒体和普通中间产物不进入 Git；
- 正式 EXE、ZIP、SHA-256、manifest 和版本说明通过 GitHub Release 交付；
- 一次性迁移、视觉验收和临时发布工作流完成后删除；
- 正式版本标签只建立在 `main`。

## 迁移边界

P101 与 P102 必须分别迁移，不得在一个 PR 中同时导入两个项目，也不得把外部私有仓库完整历史作为 GPT-Pub 的祖先。

每个迁移 PR 至少验证：

- 固定源提交与过滤历史；
- 允许路径之外零文件；
- 当前文件数量、字节数和 SHA-256；
- 全历史公开安全扫描；
- GPT-Pub 新路径下的构建与测试；
- Windows 原生验证和正式产物；
- 外部旧编号、旧路径与 GPT-Pub 新编号的历史说明；
- 迁移后只在 GPT-Pub 维护，不形成跨仓双主线。
