# AtlasDesk 同类项目与设计参考

> 调研日期：2026-08-06  
> 调研范围：公开 GitHub 仓库及其官方 README  
> 用途：为 AtlasDesk 后续产品设计、功能取舍和路线边界提供长期参考

本文件不是竞品排行榜，也不是当前版本计划。它只回答三个问题：

1. GitHub 上有哪些项目与 AtlasDesk 的部分目标相近；
2. 哪些结构、交互或边界值得 AtlasDesk 借鉴；
3. 哪些方向虽然看起来强大，但会让 AtlasDesk 偏离“轻量、原生、个人、项目语境统一”的核心目标。

动态星数、下载量和短期版本号不作为长期判断依据。事实部分以调研日期时各官方仓库 README 的明确描述为准；“AtlasDesk 判断”属于本项目基于自身约束作出的设计推论。

---

## 1. AtlasDesk 的目标基线

AtlasDesk 不是以下任何一种单独产品：

- 通用浏览器；
- 完整 IDE；
- Zotero 替代品；
- Notion / Miro 替代品；
- 全功能任务管理平台；
- AI Agent 操作系统；
- 云协作平台。

AtlasDesk 的目标是一个面向个人科研与软件开发的 Windows 原生工作台，用一个稳定外壳统一组织：

```text
项目语境
├── 工作区与文件
├── 原生终端与环境
├── Dashboard 网页入口
├── Zotero 只读资料库
├── 项目—文献关联
├── 任务与本地工具
└── 显式、可控的项目上下文
```

核心差异不在于“把所有功能都重新实现”，而在于：

> 不替代成熟工具，而是让现有工具围绕同一个项目语境协同工作。

---

## 2. 总体结论

本次核对的公开项目中，没有一个同时覆盖 AtlasDesk 的全部目标。最接近的项目可以分为八类：

| 参考方向 | 代表项目 | 与 AtlasDesk 的关系 |
|---|---|---|
| 项目中心型桌面工作台 | [OpenLoaf](https://github.com/OpenLoaf/OpenLoaf) | 总体结构最接近，但明显偏向多 Agent 与项目记忆 |
| 一体化本地 AI 工作台 | [CoWork OS](https://github.com/CoWork-OS/CoWork-OS) | 功能覆盖最广，适合作为复杂度和自治边界参考 |
| 终端与文件工作空间 | [Wave Terminal](https://github.com/wavetermdev/waveterm) | 终端布局、块化工作区和文件预览的首要参考 |
| 项目任务与上下文 | [Super Productivity](https://github.com/super-productivity/super-productivity) | 项目级任务、文件、链接和命令组织的首要参考 |
| 科研写作与引用 | [Zettlr](https://github.com/Zettlr/Zettlr) | Zotero、Citation Key、Pandoc/LaTeX 工作流的首要参考 |
| 网页服务聚合 | [Ferdium](https://github.com/ferdium/ferdium-app) | Web 服务分组、工作区和会话持久化参考 |
| Dashboard 与状态入口 | [Dashy](https://github.com/Lissy93/dashy)、[Homepage](https://github.com/gethomepage/homepage) | 首页、状态、组件和打开方式参考 |
| 知识内容工作区 | [AFFiNE](https://github.com/toeverything/AFFiNE) | 内容块、画布和本地优先理念参考，也是范围膨胀边界 |

最值得长期记住的结论是：

- **OpenLoaf** 最像“以项目为中心的 AtlasDesk”；
- **Wave Terminal** 最值得指导终端、预览和多面板交互；
- **Super Productivity** 最值得指导项目、任务、文件和命令之间的关系；
- **Zettlr** 最值得指导科研引用体验；
- **Dashy / Homepage** 最值得指导首页与 Dashboard；
- **CoWork OS / AFFiNE** 更适合作为“不要无限扩张”的边界参照。

## 3. 项目逐项分析

## 3.1 OpenLoaf｜总体结构最接近

### 官方仓库事实

OpenLoaf 将自己定位为“项目中心、Local-First、多 Agent 的 AI 生产力桌面”。其 README 明确描述：

- 每个项目是独立工作区；
- 主窗口承担全局项目入口和活动时间线；
- 每个项目窗口包含文件树、终端、任务板和画布；
- 项目之间可以显式链接并共享记忆和技能；
- 数据主要保存在本机；
- 项目目录中可写入 `.openloaf` 与 `.agents` 等项目级数据；
- 项目仍处于活跃开发期，功能和 API 可能变化。

### 与 AtlasDesk 的重合

- 都以“项目”而不是单个文件或单个工具作为工作主线；
- 都希望在主窗口提供全局入口，在项目层提供具体工具；
- 都把文件、终端、任务和知识上下文组织进同一项目；
- 都强调本地数据与项目隔离。

### 值得借鉴

1. **全局主页与项目工作台分层**  
   全局页只负责最近项目、活动和入口；项目页负责文件、终端、任务和上下文。AtlasDesk v1.2.0 已开始采用这一结构。

2. **项目是完整工作单元**  
   项目不应只是目录列表，而应有状态、常用文件、命令、文献和工作入口。

3. **显式项目关联**  
   跨项目关系可以存在，但必须由用户明确建立，而不是后台自动推断。

4. **不同项目保持独立语境**  
   项目终端、Dashboard、文献和任务不应因为切换其他项目而混乱。

### 不应照搬

- 不引入 Secretary / Project / Worker 多 Agent 体系；
- 不让 AI 自动路由和执行成为产品主线；
- 不在项目源码目录中写入 `.openloaf`、项目记忆或技能文件；
- 不扩张到邮件、日历、画布、富文本编辑和内容生成平台；
- 不把“项目记忆注入”替代 AtlasDesk 当前显式索引与只读关联。

### AtlasDesk 判断

OpenLoaf 是最重要的**结构参考**，不是代码或技术栈参考。AtlasDesk 应学习它的“全局入口—项目工作台—项目工具”层次，但保持 Windows 原生、显式操作、项目目录无污染和非 Agent 优先。

## 3.2 CoWork OS｜最完整，也最容易失控

### 官方仓库事实

CoWork OS 将自己定位为 GUI 优先、CLI 可用的本地 AI Super App / Everything App。README 描述其覆盖：

- 编程、邮件、研究、浏览器测试；
- 文档、表格、演示文稿和 PDF；
- Agent、自动化、长期任务、审批与记忆；
- 真实 PTY 终端标签和 Browser Workbench；
- 生成文件在侧边工作区预览和继续修改；
- 多模型、多连接器、技能和插件能力；
- 本地优先并通过审批、沙箱和权限策略约束高自治操作。

### 与 AtlasDesk 的重合

- 都希望减少多个独立工具之间的频繁切换；
- 都包含项目、终端、浏览器、任务和文件预览；
- 都强调本地数据、可见状态和可控执行。

### 值得借鉴

1. **任务、终端、浏览器和产物并列显示**  
   用户可以在同一语境中看到“正在做什么、产生了什么、如何继续”。

2. **产物侧边预览**  
   PDF、文档、表格、演示文稿和网页不必总是跳出到外部窗口；轻量预览可提高连续性。

3. **执行过程可见**  
   长时间任务必须显示当前步骤、等待条件、审批点和最终结果。

4. **GUI 与 CLI 共享语境**  
   同一项目状态可以从图形界面和终端进入，而不是维护两套互不相干的数据。

### 不应照搬

- 不发展为 Agent 操作系统；
- 不加入大规模模型供应商、连接器、技能市场和自动化编排；
- 不承担 Word、Excel、PowerPoint、邮件和浏览器的完整替代职责；
- 不让后台自治、持续记忆和远程控制成为默认行为；
- 不为了“Everything App”牺牲 AtlasDesk 的可理解性和稳定性。

### AtlasDesk 判断

CoWork OS 主要是**复杂度边界参考**。它证明“统一工作台”可以覆盖很广，但也展示了功能、权限、模型和生命周期会如何迅速膨胀。AtlasDesk 只应借鉴可见执行、侧边预览和统一项目语境。

## 3.3 Wave Terminal｜终端与多面板工作的首要参考

### 官方仓库事实

Wave Terminal 将自己定位为跨平台、AI 集成的开源终端。README 明确列出：

- 终端、编辑器、浏览器和 AI 助手可拖放排列；
- 支持 Command Blocks；
- 支持 Markdown、图片、视频、PDF、CSV 和目录预览；
- 任意块可快速全屏并恢复原布局；
- 支持内置编辑器和远程文件；
- 支持可持续的 SSH 会话；
- 提供 `wsh` 命令与工作区交互。

### 与 AtlasDesk 的重合

- 都重视终端作为项目工作的核心入口；
- 都需要终端与文件、预览和项目状态协同；
- 都希望用户能在集中工作区内完成多数操作。

### 值得借鉴

1. **终端块而不是单一黑屏**  
   命令、输出和相关文件可以形成独立工作块，便于定位和复用。

2. **终端与预览并列**  
   项目终端、Markdown、PDF、图片或目录预览可在同一页面并列，不必不断切页。

3. **临时聚焦与恢复**  
   任意面板可以临时全屏，完成后恢复到原来的项目布局。

4. **项目级布局状态**  
   用户回到某个项目时，应尽可能恢复其终端、文件和预览组合，而不是只恢复最后一个页面名称。

### 不应照搬

- 不急于扩张完整 SSH 与远程文件系统；
- 不替换 AtlasDesk 已经稳定的 WPF + 原生 ConPTY 边界；
- 不把 AI 终端助手设为基础依赖；
- 不在没有真实需求前实现复杂自由布局系统。

### AtlasDesk 判断

Wave Terminal 是 AtlasDesk **终端交互和多面板布局**的首要参考。后续最有价值的不是复制 Wave，而是逐步加入轻量文件预览、终端/预览并列和可恢复的项目布局。

## 3.4 Super Productivity｜项目任务与上下文的首要参考

### 官方仓库事实

Super Productivity 将自己定位为支持时间盒、时间追踪和外部任务集成的高级 Todo 应用。README 明确描述：

- 使用项目、标签和子任务组织工作；
- 支持时间盒、工时统计、休息提醒和番茄钟；
- 可与 GitHub、GitLab、Jira、Trello 等平台集成；
- 项目和任务可以附加笔记、文件和书签；
- 项目级书签可以保存链接、文件甚至命令；
- 不要求账户，并强调用户决定数据存储位置。

### 与 AtlasDesk 的重合

- AtlasDesk 已有项目、任务、常用文件和显式命令；
- 二者都强调本地、明确和用户控制；
- 都需要把“项目相关的一切”放回同一语境。

### 值得借鉴

1. **任务必须归属项目语境**  
   任务中心不应只是全局列表，应能够按项目查看、筛选和恢复上下文。

2. **项目级书签模型**  
   文件、目录、网页和命令可以共享一个统一的“项目资源”概念，同时保持不同执行方式。

3. **今日视图与项目视图分离**  
   用户既需要“今天要做什么”，也需要“这个项目还有什么”。

4. **本地优先且无需账户**  
   项目任务和上下文不应依赖云账户才能工作。

### 不应照搬

- 不扩张完整工时、绩效、习惯、番茄钟和多平台 Issue 同步；
- 不把 AtlasDesk 变成专业项目管理软件；
- 不自动把外部 Issue 导入并改变本地任务；
- 不为同步功能引入新的服务器和账户体系。

### AtlasDesk 判断

Super Productivity 最值得指导 AtlasDesk 下一阶段的**项目—任务结合**。优先方向是项目任务过滤、项目页显示近期任务、任务完成后返回原项目语境，而不是完整时间管理体系。

## 3.5 Zettlr｜科研引用体验的首要参考

### 官方仓库事实

Zettlr 将自己定位为“One-Stop Publication Workbench”。README 明确列出：

- 强调隐私优先；
- 与 Zotero、JabRef 等文献管理器紧密集成；
- 支持引用工作流；
- 支持 LaTeX 和 Word 模板；
- 通过 Pandoc、LaTeX 和 Textbundle 导出；
- 支持全文搜索、代码高亮和 Zettelkasten 工作流。

### 与 AtlasDesk 的重合

- 都面向科研与写作场景；
- 都需要使用 Zotero 数据、Citation Key、DOI 和本地 PDF；
- 都希望文献不只是“可查看”，而是进入具体项目与写作工作流。

### 值得借鉴

1. **Citation Key 是一等操作**  
   应允许快速查看、复制和在项目中使用，而不是隐藏在次要详情里。

2. **引用预览应简洁**  
   标题、作者、年份、期刊、DOI 和 Citation Key 应形成清晰层级。

3. **从文献到写作工具的交接**  
   AtlasDesk 可以负责定位、复制和打开，不需要重新实现完整编辑器。

4. **项目文献集合**  
   项目工作台应能看到当前项目的核心文献，并快速打开 PDF 或在 Zotero 定位。

### 不应照搬

- 不实现完整 Markdown 学术编辑器；
- 不承担 Pandoc、LaTeX、Word 模板和完整出版流水线；
- 不维护第二套文献数据库；
- 不写入 Zotero SQLite、集合、标签、Extra 或附件。

### AtlasDesk 判断

Zettlr 是 AtlasDesk **Zotero 只读体验与科研交接**的首要参考。AtlasDesk 应做“文献入口和项目桥梁”，而不是重新制造写作软件。

---

## 3.6 Ferdium｜网页服务聚合与会话组织参考

### 官方仓库事实

Ferdium 将自己定位为把常用网页应用组合进一个桌面应用的服务聚合器。README 明确描述：

- 多个服务统一放入一个桌面应用；
- 支持 Workspaces 对服务分组；
- 提供 Todo 视图；
- 支持大量服务；
- 用户可通过 CSS 自定义界面；
- 用户数据保存在平台对应的用户数据目录。

### 与 AtlasDesk 的重合

- AtlasDesk Dashboard 同样需要长期保持网页登录状态；
- 都需要区分不同网页服务和工作语境；
- 都需要清晰处理内部网页与外部浏览器之间的关系。

### 值得借鉴

1. **网页服务按工作区组织**；
2. **登录状态和服务配置独立保存**；
3. **服务切换入口保持紧凑**；
4. **网页服务不是首页装饰，而是明确的工作入口**。

### 不应照搬

- 不把 AtlasDesk 变成通用网页套壳；
- 不建立大型服务商店和 Recipe 系统；
- 不把跨域外站全部留在内部 WebView2；
- 不重新承担完整浏览器下载、扩展和权限系统。

### AtlasDesk 判断

Ferdium 适合指导 Dashboard 的**服务分组、会话保持和入口组织**，但 AtlasDesk 仍应坚持“Dashboard 本体留在内部，复杂外部网站交给系统浏览器”的混合边界。

---

## 3.7 Dashy｜可配置 Dashboard 与打开方式参考

### 官方仓库事实

Dashy 将自己定位为高度可定制的自托管 Dashboard。README 明确列出：

- 多页面；
- 应用、链接和主机的实时状态；
- 动态组件；
- 搜索、标签和快捷键；
- Workspace View；
- 同页、新标签、剪贴板、弹窗或 Workspace 等多种打开方式；
- YAML 与 UI 配置；
- 可选认证、主题和自定义布局。

### 与 AtlasDesk 的重合

- AtlasDesk 首页和 Dashboard 都需要快速入口和状态；
- 都需要根据目标决定“内部打开还是外部打开”；
- 都需要搜索、快捷键和有限的状态组件。

### 值得借鉴

1. **打开方式是资源属性**  
   同一个入口可以指定内部、外部、复制或弹出，而不是所有链接采用同一路径。

2. **状态灯必须表达真实状态**  
   状态、更新时间和错误应清晰，但不应让首页变成监控大屏。

3. **Workspace View 思路**  
   若未来需要同时查看多个网页工具，应采用有限、明确的工作区，而不是通用浏览器标签系统。

4. **多页面但层级克制**  
   首页、项目入口和服务页可以分开，避免全部堆在一个页面。

### 不应照搬

- 不引入复杂 YAML 作为 AtlasDesk 主配置方式；
- 不把首页变成自托管服务监控中心；
- 不让用户承担大量组件和主题配置；
- 不把 Web Dashboard 反过来控制原生 AtlasDesk 的全部结构。

---

## 3.8 Homepage｜快速、安全、克制的首页参考

### 官方仓库事实

Homepage 将自己定位为静态生成、快速、安全、可定制的应用 Dashboard。README 明确描述：

- 静态生成以获得快速加载；
- 后端 API 请求通过代理隐藏密钥；
- 支持书签、搜索、天气和状态组件；
- 支持大量服务集成与 Docker 自动发现；
- 支持自定义布局、CSS 和 JavaScript；
- 强调部署到不可信网络时必须增加认证和反向代理保护。

### 与 AtlasDesk 的重合

- AtlasDesk 首页也应快速、稳定、信息密度适中；
- 都需要把书签、状态和工具入口分层；
- 都要避免在界面中暴露 Token 和 API 密钥。

### 值得借鉴

1. **首页优先快速和稳定**；
2. **入口、状态和信息组件分开表达**；
3. **外部服务凭据不进入前端展示层**；
4. **组件数量少而明确，不追求大而全**。

### 不应照搬

- 不引入 Docker 服务发现；
- 不围绕家庭服务器和自托管服务构建产品；
- 不把 AtlasDesk 首页变成依赖大量远程 API 的动态页面；
- 不增加需要长期维护的第三方服务适配矩阵。

### AtlasDesk 判断

Homepage 比 Dashy 更适合指导 AtlasDesk 的**首页克制性**：快速、少量状态、清晰书签和低维护成本。

---

## 3.9 AFFiNE｜内容工作区参考，也是范围边界

### 官方仓库事实

AFFiNE 将自己定位为隐私导向、Local-First、开源的 Notion 与 Miro 替代方案。README 明确描述：

- 文档、白板和表格融合；
- 富文本、便签、网页、多视图数据库、链接页面、形状和幻灯片可放在无边界画布；
- 支持本地优先、实时协作和自托管；
- 包含 AI 内容与画布能力；
- 目标是承载知识库、Wiki、演示和数字资产。

### 与 AtlasDesk 的重合

- 都重视本地优先和个人知识工作；
- 都需要清晰组织文档、项目和资料；
- 未来 AtlasDesk 可能需要轻量笔记、预览或项目说明视图。

### 值得借鉴

1. **内容块层级与信息组织**；
2. **文档与画布之间的切换思路**；
3. **本地优先的数据所有权表达**；
4. **复杂内容采用渐进披露，而不是一次全部展示**。

### 不应照搬

- 不实现 Notion / Miro 替代品；
- 不创建完整块编辑器、数据库、白板和协作系统；
- 不把研究资料搬进 AtlasDesk 自有内容数据库；
- 不引入云同步、实时协作和自托管服务器；
- 不让“内容创作”取代 AtlasDesk 的工具编排定位。

### AtlasDesk 判断

AFFiNE 是**内容层与范围膨胀的双重参考**。可以学习它的信息组织，但 AtlasDesk 应继续把内容留在用户原始文件和成熟应用中。

## 4. 跨项目综合原则

## 4.1 项目必须成为上下文主轴

多个项目共同证明：单纯把工具放在同一个窗口里，不等于形成工作台。AtlasDesk 应继续让以下状态围绕“当前项目”组织：

- 当前目录；
- Git 与环境；
- 终端；
- 常用文件与命令；
- 关联文献；
- 项目任务；
- Dashboard 与外部入口；
- 最近活动和可恢复布局。

## 4.2 聚合成熟工具，不重复制造工具

AtlasDesk 的合理边界是：

| 领域 | AtlasDesk 应承担 | 不应承担 |
|---|---|---|
| Zotero | 只读检索、定位、复制、项目关联 | 第二套文献数据库与写入同步 |
| 终端 | 会话组织、项目路径、环境、原生 ConPTY | 重造完整远程开发平台 |
| 写作 | 打开、定位、引用交接 | 完整 Markdown / LaTeX / Word 编辑器 |
| Dashboard | 内部主页、必要登录、项目入口 | 通用浏览器与服务商店 |
| 任务 | 项目关联、今日视图、返回项目语境 | 企业项目管理与工时平台 |
| 文件 | 工作区浏览、预览、打开 | 重造 Windows 文件资源管理器 |
| AI | 可选辅助与明确操作 | 默认自治 Agent 和后台执行系统 |

## 4.3 显式操作优先于自动化

所有参考项目中，最容易导致复杂度失控的部分都是“自动”：

- 自动扫描；
- 自动记忆；
- 自动关联；
- 自动执行；
- 自动同步；
- 自动恢复复杂状态；
- 自动调用外部服务。

AtlasDesk 应继续坚持：

```text
用户明确选择项目
→ AtlasDesk 有界读取状态
→ 用户明确点击文件、命令、文献或入口
→ 对应稳定模块执行
```

## 4.4 采用渐进披露，而不是首页堆满功能

- 首页只显示最近项目、少量状态和主要入口；
- 项目工作台显示当前项目的汇总；
- 详细文件、命令、文献和任务在需要时展开；
- 专业工具交给原应用；
- 临时聚焦使用全屏或侧边面板，完成后恢复原布局。

## 4.5 单一业务所有者

借鉴外部项目时，不能为新页面复制一套业务逻辑。例如：

- 项目工作台的命令继续由现有终端所有者执行；
- 项目文献继续由 Zotero 只读所有者定位；
- Dashboard 入口继续由现有 WebView2/外部浏览器策略处理；
- 项目上下文继续由现有原子 Data 存储管理。

新的页面可以聚合能力，但不能成为第二套生命周期和数据源。

## 5. 建议吸收顺序

以下不是固定版本号计划，而是优先级参考。

### 第一优先级｜强化已经形成的项目工作台

来源：OpenLoaf、Super Productivity、Zettlr。

- 项目页显示该项目的近期任务；
- 项目任务完成后可回到原项目语境；
- 常用文件、命令、文献和 Dashboard 统一为可筛选的项目资源；
- 项目最近活动保持简洁、可解释；
- 跨项目引用必须显式建立。

### 第二优先级｜终端与预览协同

来源：Wave Terminal、CoWork OS。

- 终端旁边打开 Markdown、PDF、图片或目录的轻量只读预览；
- 面板可临时放大并恢复；
- 项目保留有限的布局快照；
- 命令结果可以形成可定位的会话块，但不改变 ConPTY 原生边界。

### 第三优先级｜首页与 Dashboard 入口收口

来源：Homepage、Dashy、Ferdium。

- 首页继续保持快速、少量状态和最近入口；
- 每个入口明确内部、外部、复制或项目 Dashboard 打开方式；
- 网页服务按项目或用途分组；
- 不发展通用标签浏览器。

### 第四优先级｜科研交接体验

来源：Zettlr。

- Citation Key、DOI、PDF 和引用格式的一键复制与打开；
- 项目核心文献列表；
- 从项目工作台快速进入 Zotero、PDF 和实际写作文件；
- AtlasDesk 只负责交接，不接管论文编辑。

## 6. 明确不进入 AtlasDesk 主线的方向

除非用户未来重新定义产品目标，否则以下方向默认不进入主线：

- 多 Agent 组织、Secretary Agent 或 Worker Agent；
- 项目目录内写入 AtlasDesk 元数据、记忆或技能；
- 完整邮件、日历、白板、富文本、数据库和 Office 编辑器；
- 通用浏览器、服务商店和浏览器扩展体系；
- 插件市场、MCP 市场和微服务架构；
- 默认后台全盘索引；
- 自动运行项目命令；
- Zotero 写入或双向同步；
- 账户强依赖、云同步和实时协作；
- 为追求跨平台而放弃 Windows 原生稳定性。

## 7. 新功能采用检查表

任何从外部项目得到的功能建议，在进入开发前至少回答：

1. 它是否直接服务于“当前项目语境”？
2. 它是否复用现有业务所有者，而不是复制第二套逻辑？
3. 是否需要后台扫描、定时器或常驻服务？
4. 是否会写入项目源码目录？
5. 是否会破坏 Zotero 只读边界？
6. 是否会让 AtlasDesk 变成通用浏览器、编辑器或 Agent 平台？
7. 是否能在 Runtime/Data 分离架构中清楚落位？
8. 是否能通过自动回归，并清楚标记仍需实机验证的部分？
9. 功能收益是否高于新增生命周期、权限和维护成本？
10. 删除该功能后，AtlasDesk 的核心目标是否仍成立？

如果第 1、2、9 项不能给出明确肯定答案，应默认不做。
