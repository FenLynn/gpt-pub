# AtlasDesk 设计与演进

本文件记录 AtlasDesk 形成当前设计的重大原因、路线取舍和长期技术债。普通缺陷、按钮位置、颜色和一次性版本计划不写在这里。

## AD-D01｜从 Personal Workbench 到 AtlasDesk

### 原始问题

项目早期以个人工作台为核心，逐步整合 Dashboard、工作区、Zotero、终端、开发环境、任务和工具。随着能力扩展，旧名称、旧目录和历史工程结构逐渐无法准确表达产品定位。

### 最终选择

- 用户可见产品统一为 AtlasDesk。
- 仓库正式项目为 P102，路径为 `projects/1-桌面软件/102-AtlasDesk/`。
- 历史 namespace 和部分工程目录暂时保留 `PersonalWorkbench`，作为内部兼容事实，而不是产品品牌。

### 长期经验

品牌切换不应强制重写稳定内部格式。用户可见身份必须统一，内部历史名称则在有测试保护时逐步收敛。

## AD-D02｜Dashboard 使用 WebView2，但不发展为通用浏览器

### 原始问题

Dashboard 本身是网页工作台，需要保留登录状态、内部路由和已有 Web 能力，因此 WebView2 比重新实现原生页面更经济。

早期实现把 `window.open()` 和 `target="_blank"` 的所有目标都继续放进新的内部 WebView2 窗口。Google AI Studio、Editorial Manager 等复杂外部网站进入后出现 `RenderProcessUnresponsive`，并连带影响主 Dashboard。

### 比较过的路线

1. 所有网页都留在 AtlasDesk 内部：体验集中，但需要长期维护标签页、下载、权限、文件选择、OAuth、GPU 崩溃恢复和复杂网站兼容。
2. 所有点击都交给外部浏览器：稳定，但 Dashboard 内部路由和登录体验被破坏。
3. 混合模式：Dashboard 本体和必要登录留在内部，跨域外链交给系统浏览器。

### 最终选择

采用混合模式：

```text
Dashboard 同域页面、内部路由、必要身份验证
→ AtlasDesk WebView2

跨域外链
→ Windows 默认浏览器
```

### 长期经验

AtlasDesk 的价值是统一工作入口，不是重新制造浏览器。外部复杂站点应利用成熟浏览器、现有账号环境和 Bitwarden 等扩展能力。

## AD-D03｜终端采用 WPF 主程序 + 原生 TerminalHost

### 原始问题

Windows ConPTY、伪终端生命周期和原生句柄管理不适合全部塞进 WPF 业务层；但把整个终端系统拆成独立应用又会增加状态同步和用户操作成本。

### 最终选择

- WPF 主程序负责会话标签、界面、项目路径、环境选择和业务状态。
- `AtlasDesk.TerminalHost.exe` 只承担 ConPTY 和原生进程边界。
- 终端资源随公开 Runtime 发布，用户状态留在 Data。

### 长期经验

进程拆分应围绕清晰技术边界，而不是为了模块化形式。TerminalHost 不应演化成第二套业务程序。

## AD-D04｜Runtime 与 Data 完全分离

### 原始架构

v0.7.x 使用 Go 启动器，把嵌入的 WPF 主程序释放到：

```text
%LOCALAPPDATA%\AtlasDesk\App\<版本>\AtlasDesk.App.exe
```

历史上还存在 `%LOCALAPPDATA%\PersonalWorkbench\App\<版本>`。这种方式让单 EXE 看似方便，但造成：

- AppData 混入可公开 Runtime；
- 历史版本累积；
- 程序真实运行位置不透明；
- 手工更新和增量覆盖困难；
- 用户数据与程序文件边界模糊。

### 最终选择

v0.8.0 改为透明文件夹 Runtime：

```text
用户建立的 AtlasDesk/
├── AtlasDesk.exe
├── AtlasDesk.TerminalHost.exe
├── Assets/
└── 公开依赖
```

私人数据分为：

```text
%APPDATA%\AtlasDesk
→ 轻量、重要、可备份

%LOCALAPPDATA%\AtlasDesk
→ 机器相关、较重、可重新生成
```

### 迁移策略

旧数据迁移由独立 PowerShell 工具完成，不把一次性迁移逻辑永久写进产品。迁移先完整备份，再移动 WebView2、终端状态、日志和启动状态，最后清理旧 Runtime。

### 长期经验

“Runtime/Data 分离”是逻辑边界，不需要再创建多余的 `Runtime` 或 `Data` 子目录。可执行目录本身就是 Runtime 根，两个 AppData 根本身就是 Data 根。

## AD-D05｜本地安全中心采用分层授权

### 原始需求

用户希望本地保存密码、Token 和密钥，但不希望 AtlasDesk 变成完整密码管理器，也不希望日常每次启动都输入长主密码。

### 最终选择

- Bitwarden 浏览器插件可保存 AtlasDesk 主密码和恢复材料。
- Google Authenticator 保存 TOTP。
- AtlasDesk 本地使用主密码派生密钥，加密 `vault.bin`。
- TOTP 只作为二次授权，不作为加密密钥。
- 可选四位数字只用于用户主动触发的临时界面遮挡；默认可以关闭，不参与加密。
- 普通使用默认不锁定。

### 长期经验

便利层和加密层必须分开。四位数字可以防止临时旁观，但不能成为保险库安全根。

## AD-D06｜项目、环境和终端必须保持独立职责

### 原始演进

开发模块最初只有环境和终端。加入项目中心后，“项目/环境”被放进 TabControl，但旧终端修正层仍监听开发导航，并把 `DevelopmentControl` 隐藏后把终端移入旧容器。

旧容器已经脱离当前视觉树，结果是环境页只剩 Tab 标题，内容完全空白。

### 最终选择

- 项目中心和环境发现作为并列页面。
- 环境页主动加载 Python 环境，不只依赖 `IsVisibleChanged`。
- 终端使用全局底部抽屉或独立窗口，不再替换环境页面。

### 长期经验

模块重构后必须清理旧生命周期监听器。把控件从一个父容器迁移到另一个容器时，应检查所有历史增强层是否仍在操纵旧父级、可见性和 Grid 行列。

## AD-D07｜主壳从大卡片式转向连续平面布局

### 原始问题

早期为了营造桌面工作台视觉，主壳逐步加入外层留白、左右独立圆角 Border、描边、阴影和中间空槽。多个修正层又继续增加底色和卡片，最终导致层次过多、视觉割裂。

### 最终选择

主壳采用接近现代 Web 工作台的连续布局：

```text
左侧导航
│ 1 px 分割线
右侧内容
```

外层不再使用两个大卡片框。局部卡片只在真实信息分组时保留，并弱化装饰。

### 长期经验

边框、底纹和阴影是信息结构工具，不是默认装饰。需要区分区域时，优先使用间距、对齐和单一分割线。

## AD-D08｜自定义标题栏必须服从 Windows WorkArea

### 原始问题

旧修正层通过 `WindowChrome` 取消系统标题栏，再自行增加标题栏。最大化时只把内部 Margin 改为 0，没有正确处理当前显示器 WorkArea、任务栏、隐藏边框和 DPI，导致顶部文字偏移、顶部裁切和底部消失。

### 最终选择

最大化尺寸应基于当前显示器 WorkArea 计算，并正确处理 `WM_GETMINMAXINFO`、DPI、多显示器和任务栏位置。

### 长期经验

自定义窗口边框不是纯视觉功能。只调整 Margin 无法替代 Windows 最大化边界处理。

## AD-D09｜历史 Enhancer 层属于待收敛技术债

### 形成原因

项目在快速迭代中形成多个 `V06x`、`V07x` Enhancer。每层通常只修正上一版暴露的问题，短期降低了修改风险，但长期产生：

- 同一控件被多层重复移动、隐藏和重新绑定；
- 生命周期事件顺序难以推断；
- 新模块已经替换界面，旧增强层仍操纵失效容器；
- UI 根因被新的修正层遮盖。

### 当前策略

不进行无测试保护的整体重写，但后续修复应逐步：

1. 找到真正控制源；
2. 合并重复职责；
3. 删除失效事件和旧容器路径；
4. 为模块切换、可见性和窗口适配补回归测试；
5. 避免继续增加版本命名修正层。

### 长期经验

兼容层适合短期过渡，不应成为永久架构。新的功能中心建立后，旧增强层必须经过一次职责清查。

## AD-D10｜增量更新优先，结构变化才完整交付

### 原始问题

用户希望更新透明、可控，不希望每次下载完整大包，也不希望程序目录和私人数据混合。

### 最终选择

- 只修改主程序时，交付 `AtlasDesk.exe`。
- 多文件变化时，仅打包变化文件并保留 Runtime 相对路径。
- Runtime 架构、主要依赖或资产整体改变时，才交付完整 Runtime ZIP。
- 更新包不包含任何 Data。

### 长期经验

增量更新不需要复杂自更新服务。对于当前规模，清晰文件边界、manifest、哈希和手工覆盖已经足够可靠。
