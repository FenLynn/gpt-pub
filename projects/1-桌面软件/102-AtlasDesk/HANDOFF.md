# AtlasDesk 对话接续入口

本文件用于在更换 ChatGPT 对话后恢复 AtlasDesk 项目上下文。

- 仓库：`FenLynn/gpt-pub`
- 项目编号：`P102`
- 项目路径：`projects/1-桌面软件/102-AtlasDesk/`
- 日常开发分支：`p102-exp`
- 稳定候选分支：`p102-stable`
- 正式主线：`main`

本文件只规定固定接续流程，不重复维护当前版本、提交、PR、CI、Artifact、待办和实机反馈，因此不需要随每轮对话更新。

## 接续方式

用户可能会同时提供上一轮对话的交接记录，也可能只提供本文件链接。

### 用户提供了上一轮记录

先阅读用户提供的记录，用于快速了解最近完成的工作、当前断点、实机现象和待处理事项。

随后仍须按照下面的固定顺序读取项目文档，并检查 GitHub 的真实状态。不要要求用户重复已经在交接记录中说明的内容，也不要把旧聊天记录直接当作最终事实。

### 用户没有提供上一轮记录

直接按照下面的固定读取顺序从仓库恢复上下文，不要求用户重新回忆或转述之前的工作。

## 固定读取顺序

依次读取：

1. 仓库根目录 `GPT_RULES.md`
2. 仓库根目录 `目录.md`
3. `projects/1-桌面软件/开发约束.md`
4. 本项目 `开发约束.md`
5. 本项目 `README.md`
6. 本项目 `阶段记录.md`
7. 本项目 `工作记录.md`
8. 与当前任务有关时再读取 `设计与演进.md`、版本说明、测试记录、迁移记录或其他专题文档

完成文档读取后，必须继续核对：

- `main`、`p102-stable`、`p102-exp` 的最新提交和相互关系；
- 与 AtlasDesk 有关的开放 PR、最近合并 PR 和准确 head SHA；
- 相关 GitHub Actions、测试结果和 Runtime Artifact；
- 正式标签与 Release 是否真实存在；
- 用户最近实机验证已经确认了什么，仍有哪些内容只通过了代码或 CI 验证。

## 正式基线与开发候选

AtlasDesk 的正式主线与当前开发候选可能不同：

- `main`、正式标签、Release 和 `阶段记录.md` 用于判断当前正式版本；
- `p102-stable` 用于判断已经完成 CI、等待或正在进行实机确认的稳定候选；
- `p102-exp` 用于判断当前连续开发状态；
- `工作记录.md` 用于恢复当前看板，但可能暂时落后于最新 PR、CI 或实机反馈。

不得因为 `main` 的版本较低，就忽略 `p102-stable` 或 `p102-exp` 中已经完成的候选；也不得因为候选版本较高，就把它误报为已经正式发布。

## 信息使用原则

事实源按以下方式使用：

```text
实现事实 → 源码
验证事实 → 测试与 CI
历史事实 → Git、PR、标签与 Release
当前规则 → A/B/C 开发约束
当前状态 → README、阶段记录与工作记录
实机表现 → 用户最近一次明确反馈
```

用户提供的上一轮记录和旧聊天内容用于快速定位，但不替代仓库核验。

如果交接记录、项目文档和 GitHub 实际状态不一致，应：

1. 以源码、Git、PR、CI、Artifact、标签和 Release 的实际状态为准；
2. 明确指出哪一份记录已经滞后；
3. 避免重复已经完成的工作；
4. 不把自动测试结果夸大为真实登录、显卡、DPI、多显示器或用户输入已经通过实机验证。

## 接续后的首次回复

完成读取和核对后，首次回复应先说明：

- 当前正式版本和正式主线状态；
- 当前稳定候选或开发版本；
- `main`、`p102-stable`、`p102-exp` 的真实关系；
- 最近已经完成的工作；
- 尚未完成或尚待实机验证的内容；
- 准确的继续工作断点；
- 本次是否进行了任何写入。

用户只要求接续、确认状态或询问是否已经接上时，不得修改代码、文档、分支、PR、CI、标签或 Release。

## 写入前要求

用户明确要求继续修改后，仍须：

1. 根据当前任务重新确认允许修改范围；
2. 从正确基线创建任务分支，不得直接写入 `main`、`p102-stable` 或 `p102-exp`；
3. 修改前读取同一分支上的最新文件和 SHA；
4. 保持 P102 范围，不得夹带 Mediova 或其他项目变更；
5. 完成后按项目约束执行 PR、CI、Artifact、分支回流和实机验证边界。

当前工作内容、提交、CI、Artifact 和后续计划继续记录在原有 README、阶段记录、工作记录、设计与演进及对应 PR 中，不在本文件重复维护。
