## 已复现的触发链

独立 Windows STA 驻留进程已经把问题从推测缩小为可重复事件链：

1. 创建唯一 WPF `Application`；
2. 构造真实 `MainWindow` 并挂载完整 `WorkbenchFeaturePipeline`；
3. 显示窗口并稳定驻留 10 秒，窗口未关闭，环境检测保持空闲；
4. 点击左侧“开发”，目标是默认“项目”页；
5. WPF 开发 Tab 在显隐/布局过程中产生一次非用户触发的临时“环境”选择；
6. 原实现把该内部选择当作用户选择，调用 `DevelopmentControl.EnsureLoadedAsync()` 并启动 Conda/Python 检测。

因此，Dashboard 和普通启动驻留本身不是本次自动复现的失败点；真正被门禁捕获的是“打开开发项目页却隐藏启动环境检测”。这与 v0.8.2 加入更重的并行、可取消、多项目环境扫描后出现实机回归高度一致。由于没有用户机器的崩溃转储，仍不声称该隐藏检测是唯一可能的进程终止原因，但它是已复现、已修复的直接回归路径。

## v0.8.3 已实现内容

- 环境发现不再订阅 `IsVisibleChanged`；控件重挂载和可见性变化不会启动外部工具。
- 新增 `DevelopmentLifecycleGuard`，关闭 `MainWindow` 中已被三 Tab 页面取代的旧 Python 发现入口，确保只有一个环境检测所有者。
- `DevelopmentControl` 对每次加载请求执行交互来源验证：
  - 开发 Tab 内具有键盘焦点，或鼠标正在开发 Tab 上选择时，允许环境检测；
  - 点击左侧“开发”等外部操作导致的内部 Tab 选择被拒绝；
  - 若内部事件临时选中“环境”，立即恢复到“项目”页。
- `PythonEnvironmentService` 恢复 v0.8.1 已验证的串行、有界检测顺序。
- 撤回 v0.8.2 的四路并行解释器探测、一级项目目录扫描和可取消进程树检测。
- 保留必要修复：先通过 `where.exe` 定位可选 `py.exe`；未安装时静默跳过，不产生 Win32Exception 堆栈。
- 日志新增 WPF `Application Exit`、CLR `ProcessExit`、主窗口 `Closing` 与 `Closed`。
- 新增独立项目 `personal-workbench-residency-smoke`，在独立 Windows 进程中运行真实窗口驻留测试。
- 驻留测试作为单独 GitHub Actions 步骤运行，具有独立超时和完整阶段日志，不再嵌入 MSBuild 或模块初始化器。

## 维护规则

- 自动 CI 不能替代真实 Windows 驻留、交互和长时间运行测试。
- 启动或窗口生命周期相关改动必须在独立进程中显示真实窗口、泵送 Dispatcher 并验证持续存在。
- 自动验证完成但仍缺真实 Windows 视觉、网页或长期运行确认时，状态保持“待验证”。
- 正式发布后移除已完成活跃项；历史由 Git、PR、标签和 Release 保存。
