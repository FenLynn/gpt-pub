## 部署本身是否需要改仓库

**临时静态部署不需要额外修改运行时代码。** 同一个已通过验证的程序 ZIP 既可解压本地使用，也可原样用于 Pages 的 Direct Upload。无需 Worker、Functions、数据库、在线 API、框架重构、Cloudflare 密钥或另一套线上源码。

Cloudflare 官方文档支持在 Dashboard 拖放 ZIP 或文件夹；Wrangler 则只接受文件夹。这个项目的纯程序包远低于拖放的 1000 文件及单文件 25 MiB 上限。[Direct Upload 文档](https://developers.cloudflare.com/pages/get-started/direct-upload/)

本次代码修改是修复复查中确认的操作/恢复问题，并澄清网站与本地升级；不是为了适配 Cloudflare 添加另一套产品。

## 推荐的临时部署步骤

1. 选用本次**程序升级 ZIP**，不是“完整便携项目 ZIP”或“项目备份 ZIP”。后两者含业务数据，不能作为网站上传。
2. Cloudflare Dashboard → Workers & Pages，选择创建 Pages 的 Direct Upload / 拖放上传方式。若界面调整，以“Pages + 上传静态资源”入口为准。
3. 上传程序 ZIP，或者上传它完整解压的纯程序目录。部署根层必须直接有 index.html 和 src，不能多套一层父文件夹。
4. 保持程序文件原样；不启用 Web Analytics 等脚本注入，也不增加自定义长时间缓存。无需配置复杂重写、额外 MIME 或前端路由。
5. 部署后用固定的项目 `pages.dev` 地址访问，核对帮助中的版本和发布清单，再用虚构测试项目验证导入、保存、重开和导出。

Pages 的默认缓存采用 ETag/重新验证，官方建议大多数场景保留默认缓存，额外自定义域名缓存可能造成旧资源。[Pages 服务与缓存说明](https://developers.cloudflare.com/pages/configuration/serving-pages/)

Web Analytics 一旦启用，会在下次部署自动添加 JavaScript 片段；为保持线上响应与离线包一致，本方案不启用该功能。[Web Analytics 说明](https://developers.cloudflare.com/pages/how-to/web-analytics/)

Direct Upload 项目以后不能原地切为 Git 集成，需要另建 Git 集成项目。临时预览采用 Direct Upload 很合适；长期自动化可以在新项目接 Git，或仍将通过 CI 的同一个程序目录通过 Wrangler 部署。[Direct Upload 的方式限制](https://developers.cloudflare.com/pages/get-started/direct-upload/)

## 怎样保证线上与离线一致

使用同一准确提交生成**一个候选 ZIP**，分别用于离线交付和线上部署，而不是分别构建“web 版”和“offline 版”。

1. 固定提交、版本与 ZIP SHA-256。
2. ZIP 自带 p109-release-manifest.json，列出每个运行文件的字节数和 SHA-256。
3. 上传同一 ZIP 或其原样解压目录，部署前逐文件核验。
4. 部署后取得站点发布清单，逐文件读取 HTTP 解码后的响应字节，核对清单。Gzip/Brotli 属于传输编码，解码后的资源内容才与 ZIP 比较。
5. 浏览器里再检查版本及关键流程；已有旧标签页先保存工作后重开。新部署不会把正在运行的旧页面 JavaScript 自动换成新版本。

仅看页面写着 R86 不足以证明文件完全一致；相同版本标签也可能配上旧脚本。分别从 Git 在 Windows/Linux 打包还可能因 CRLF/LF 不同导致哈希不同，使用同一个 ZIP/Artifact 可以避免这类字节差异。

无需为了缓存临时新增 _headers。若以后增加部署元文件，应仅作为发布层输入，不能直接混入当前只允许 index.html、README.md 与 src 的程序升级清单，否则旧升级器会拒绝额外根文件。

## 如果以后选择 Git 自动构建

可以继续维护同一 p109-exp，不需要 Cloudflare 专用长期分支。建议配置：

| 项目 | 值 |
|---|---|
| 分支 | p109-exp |
| Framework preset | None |
| Root directory | projects/1-桌面软件/109-AttendScope |
| Build command | python3 tools/package-release.py . /tmp/p109-runtime.zip && python3 -m zipfile -e /tmp/p109-runtime.zip dist |
| Build output directory | dist |

此命令复用现有打包器，不将源码项目中的 config/data/tests/tools 发布。Cloudflare 的根目录和输出目录语义见[构建配置文档](https://developers.cloudflare.com/pages/configuration/build-configuration/)。

但普通 Git 集成在 push 后就可构建，不天然等待 GitHub P109 CI 成功。需要严格一致和准入时，应“通过 CI → 取同一候选 Artifact → 离线交付和上传 Pages”，避免 Cloudflare 发布未验证 head。此阶段不增加自动部署 Secrets 或新工作流。

## 同样的程序，环境仍有区别

| 内容 | 线上网站 | 离线文件 |
|---|---|---|
| 分析、业务数据格式 | 同一程序文件与算法 | 同左 |
| 项目数据存放 | 用户本机目录或下载 ZIP；当前没有云同步 | 同左 |
| 最近项目和权限 | 归属站点 origin，首次需重新授权 | 属于本地打开环境，不自动复制到 HTTPS 域名 |
| 目录写入能力 | 浏览器必须支持并授权；不支持则便携模式 | 同样受浏览器能力限制 |
| 程序更新 | 部署者重新部署网站；用户保存后重开 | 升级 ZIP 更新本地程序目录 |
| 断网首次打开 | 无 Service Worker，不承诺未缓存站点能打开 | 完整解压包可断网打开 |
| 本机程序绝对路径 | 网页没有这项本机程序路径 | 从 file URL 提取程序文件夹 |

File System Access 仅在支持的安全环境中通过用户授权访问本地文件，网站托管不会授予它任意磁盘权限。[Chrome 文件系统说明](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)

换域名、协议或预览子域意味着不同来源，浏览器历史与授权可能需要重建；建议长期使用同一个项目地址。打开网页只从 Cloudflare 获取程序资源；现有应用代码没有业务上传接口，导入操作在当前浏览器处理。不要把“在线访问”理解为“考勤资料已自动云备份”。

## 仍需明确的操作边界

- 当前没有跨窗口、跨 origin 或多人的并发编辑锁。一个项目同时由多个页面改写，后保存者可能覆盖先保存者的工作；应保存并关闭旧页面后再换环境。
- 便携包是显式转移文件，不提供实时同步、自动合并或下载完成的系统级回执。
- Windows 外部目录授权、浏览器下载策略及手机/Safari/Firefox 的功能支持，不能以 OPFS/Chromium 自动化代替实机验收；能力不足时使用便携与 CSV 路径。
- 本轮未创建 Cloudflare 站点、未连接账户、未公布线上地址；真实部署成功与逐文件核验后，才能称线上已经与离线一致。
