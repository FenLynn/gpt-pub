## 一、结论

**目前可以将 P109 当作“离线月度考勤分析工作台预览版”，但不能将其视为完整的、可安全长期升级迁移的独立发行软件。**
R63 的月度事实层、导入、分析、修订、保存、冻结、PNG 和 PDF 已较完整；R64 进一步证明基础写盘和搬迁机制可用。
缺口集中在正式可分发 ZIP、一键空白初始化、人员名册/列映射的可选固定、权威配置同步、历史冻结后的隔离修改、跨版本数据迁移、完整项目备份恢复与 Windows 原生实机验收。

## 三、具体缺口

### P0-1｜尚无正式 P109 发行包与空白初始化向导
- 仓库项目根存在 index.html、src、project.json、config 和 data，但 releases 列表中没有 P109 对应 ZIP。
- 仅能手工从仓库单独取目录或运行 CI 临时产生测试压缩包；无版本化 manifest、资产哈希、稳定发行下载入口。
- 首次启动固定使用 2026-10 演示数据。建议首次选“创建空白项目 / 打开已有项目 / 体验演示”，演示人员绝不能成为真实配置来源。

### P0-2｜配置存在权威性冲突
- src/app/00-state.js 默认时段：08:30–11:40 / 13:30–17:10。
- 随包 config/work_rules.json 仍是 legacy 对象 morning 08:30–12:00、afternoon 14:00–17:30，当前读取器只消费扁平 amStart、amEnd、pmStart、pmEnd 等字段；预置文件不代表当前实际规则。
- config/employees.json 是固定模拟 50 人；导入真实考勤后的新名册在月度 working 中，没有在“保存”时同步更新此全局文件。
- config/analysis_rules.json 也是旧格式样例，缺少统一迁移与权威配置策略。
- 建议唯一权威链：项目级 profile（可选固定的人员/识别规则/映射/考勤参数）→ 新月份显式继承 → 月度 working 保存覆盖与修订，旧版兼容进入迁移层；去掉同名异构的样例文件。

### P0-3｜冻结不是完整的版本分支系统
- freezeSnapshot() 确保 ID 不重复，并新增 snapshot.json，原地工作状态不变。
- restoreWorkingFile() 可读取 snapshot.working，但恢复时写入原月份 monthStores，再用 saveWorking() 会覆盖该月份可变工作状态；不存在按 snapshotId 隔离的 branch 工作空间。
- 建议“从快照派生工作副本”先生成 branchId，修订保留 parentSnapshotId、独立 working，再冻结成为新的 snapshot；禁止静默覆盖旧 working。

### P0-4｜缺少自动安全升级/完整备份与数据迁移
- appVersion 多处固定为 0.1.0-preview；各类 schemaVersion 固定但无完整 migration registry。r62MigratePayload() 只完成部分旧身份映射，不等于未来格式升级。
- 同版本覆盖源文件不会破坏 current working 的测试已通过，但不存在“升级前完整 ZIP 备份→清单校验→schema 迁移→验收→失败回滚”流程。
- 目前没有用户界面级项目整包 ZIP 导出/恢复与一致性验证。应以 projectId + dataSchemaVersion + manifest checksums 校验来源和 raw 完整性，避免把截图和 derived 当成必要恢复数据。
- 一键备份应包括 config、raw、working、snapshots、revisions、import manifest，是否包含历史 output 可选；代码可以独立分发避免将升级包覆盖数据。

### P1-1｜可选固定与模板缺失
- 当前 importProfile 存储 direction 规则，但不存每种文件的 column mapping、header/skip、编码模板，也没有“锁定人员名册/默认规则”与“下一月继承”模式。
- 下一月份会复制当前月 EMPLOYEES、prefs 和规则，但这是隐式继承，不等于用户明确选择固定。
- 建议只保留一个默认案例，增加可选“将本次列映射/闸机规则设为默认”“固定当前名册”选项；保留人工覆盖。

### P1-2｜目录可简化而不丢追溯性
- 当前 data/YYYY/MM/working/state.json 与 raw/attendance/importId/filename 层次较深，但是工作逻辑清晰。
- 建议未来发行目录采用 index.html + src/ + config/ + months/YYYY-MM/ + backups/（或 app/ + workspace/ 双区），只减少无谓的年份/月份双层目录，保留 importId 隔离和不可变快照。
- 迁移须提供旧目录自动发现与安全复制、校验和回退；不要仅因为“扁平”而破坏旧数据的相对路径与 raw 可追溯性。

### P1-3｜环境/恢复边界
- 当前 CI 证明 Chromium file:// 和 Node-backed 模拟 File System Access 的实际磁盘写入/重连。仍然缺 Windows 真机目录选择器、权限、跨机器移动、更换浏览器、路径中文/长路径及离线系统更新验收。
- 部分异常导入可能在 raw 文件复制成功但 working 尚未保存时留下孤儿原始导入目录；需事务日志或导入 manifest 恢复机制。

## 四、建议先后次序（坚持奥卡姆原则）

1. **R65：最小可用离线发行包 + 首启向导 + 统一配置/可选固定**。先保障“一个 ZIP、一个入口、打开就知道如何开始”，不新增多余菜单。
2. **R66：冻结派生副本与项目整体 ZIP 备份/恢复**。采用 immutable snapshot + working branch + 校验。
3. **R67：目录迁移与升级事务**。逐版本迁移规则、先备份/后升级、出错回滚；仅在验证通过后可考虑改为 months/YYYY-MM。
4. **R68：Windows 真机全生命周期验收**。首次空白、全量导入、跨月、重启、迁目录、重装浏览器/升级版本，保存实际文件清单、截图与 SHA-256。

不要在未创建备份和数据迁移器时直接改变正在使用的 data/YYYY/MM 结构。全量文档/开发规则与配置模板后续保持一致，且不接触 P108/main/stable/共享 Pages 逻辑。
