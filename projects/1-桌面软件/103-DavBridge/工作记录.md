## 本轮用户确认的长期逻辑

1. InfiniCLOUD 是唯一权威源，坚果云保存 StrongVerified 镜像子集。
2. 每个真实坚果云额度周期开始后自动做源端对账。
3. Cycle 编号不用抽象序号，使用启动该周期的重置日期 `yyMMdd`，例如 `260907`。
4. 已 StrongVerified 文件只在源 metadata 变化时重新读取 InfiniCLOUD 并计算 SHA256。
5. SHA 真变化的历史副本优先刷新。
6. 新增对象进入普通 backlog，不提高优先级。
7. 完整历史组第一次从源消失，只进入逻辑回收站观察，目标不动。
8. 后续已确认 Cycle 仍消失，才要求人工审查。
9. 人工可以删除或本周期保留。保留项下个 Cycle 仍消失时再次审查，允许跨很多周期存在。
10. DELETE 永远不能后台自动执行。
11. 人工删除前必须重新确认源仍缺失和目标身份仍对应历史 StrongVerified。

## 本轮实现

### Cycle 与对账状态

新增 `ReconciliationModelV030` 与独立 `reconcile.json` sidecar。

Cycle 从 `NextResetAt` 的日历日期向前一个月推导，明确禁止通过运行机器时区先转换日期。第一轮 CI 正好发现过一次 UTC Runner 把 `260907` 错换成 `260906`，随后已修正并增加回归测试。

### 源端变化

周期对账读取完整 InfiniCLOUD manifest。

历史 StrongVerified 对象 metadata 未变时零内容下载。

metadata 变化时读取当前源并做 SHA256：

- SHA 相同，只更新 metadata；
- SHA 不同，标记 `SourceChanged`；
- 新目标重新 StrongVerified 前继续保留旧历史核准基线，避免目标身份判断失去依据。

### 回收站

首次完整缺失只记 `FirstMissingCycleId`。

部分 zip / prop 可见不允许推断整组删除，转为明显人工异常。

人工“本周期保留”从状态策略和删除核心两层生效，不只是 UI 隐藏按钮。

删除前再次读取每个准确源路径：

- 全部恢复，自动取消删除；
- 部分恢复，阻止删除；
- 全部仍缺失，才继续目标身份核验。

目标 ETag 无法证明历史身份时，只有下载安全额度足够才重新 GET 目标并比较历史 Target SHA256。

DELETE 的网络错误和非用户取消超时都先查询目标实际是否仍存在，不盲目重发。

删除成功后目标准确路径再次确认不存在，并把历史记录置为 `SourceChanged` 恢复语义，同时保留 SHA 证据。因此源端以后重新出现时能重新建立目标。

对账、人工保留、人工删除使用同一互斥门，避免审查操作与后台对账并发修改 sidecar。

### UI

运行时取消 v0.2.x 多层 dashboard / activity / refinement / route patch 挂载，改为单一 `UiShellV030`。

主导航：

```text
总览 | 转移 | 回收站                     ⚙
```

没有宽左栏。

总览：Cycle、双右箭头、周期状态、镜像覆盖、当前任务、流量、人工介入横幅。

转移：优先修复与普通任务两池。

回收站：待观察、待审查、已处理。

审查表默认不选任何行，并且不再由 250 ms 动画刷新循环重建，避免选择丢失或默认误选。

## 安全复核中主动发现并修正的问题

本轮不是只按最初方案照写，而是实现后继续做事故路径复核，实际修正：

- Cycle ID 时区换日；
- 源 SHA 改变后过早覆盖历史核准 metadata；
- Zotero zip / prop 部分可见误判；
- 点击删除前源端部分恢复；
- 本周期人工保留只在 UI 生效而核心仍可删除；
- DELETE 超时结果未知；
- 人工删除成功后旧 TransferRecord 仍表面 StrongVerified；
- 对账与人工删除并发；
- 回收站表格动画刷新导致选择丢失；
- UI 250 ms 刷新循环重复创建 Font。
