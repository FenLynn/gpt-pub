# DavBridge 设计与演进

本文件只记录后续很可能被重新提出、且影响长期实现边界的重大设计决定。早期决策如果后来被 v0.4 明确修订，会保留原问题背景并写明当前结论。

## D-01｜为什么核心使用 C# / .NET

DavBridge 需要长期托盘常驻、开机自启动、轻量部署、DPAPI 和稳定 Windows 集成，因此核心和 Windows 宿主采用 C# / .NET 8。早期业务 UI 也使用 WinForms，从 v0.4 起业务显示层已改为 Vue 3 + TypeScript + WebView2，但核心迁移与安全链继续留在 C#。

## D-02｜为什么使用 framework-dependent 单文件

DavBridge 优先保持轻量 Windows 交付，因此继续使用 `--self-contained false + PublishSingleFile`。v0.4 需要系统已有 .NET 8 Desktop Runtime 和 Microsoft Edge WebView2 Evergreen Runtime，但不把完整 .NET Runtime 或浏览器打入默认 EXE。目标机缺少依赖时应明确提示，而不是默认扩张为百 MB 级自包含包。

## D-03｜为什么不用 Windows Service

DavBridge 需要用户偶尔查看状态、人工校准坚果云流量、修改连接和执行最终交割。普通托盘程序已经能提供登录后自动启动、后台常驻和低资源等待，不需要 Service 带来的权限、安装和调试复杂度。

## D-04｜为什么不按 700 个文件建立远端子目录

坚果云的 750 项限制是一次目录列举返回量，不是单目录总容量。Zotero 的远端对象应保持标准 `/zotero` 结构。迁移批次只存在于本地状态，不改变远端路径，避免最终再做大规模 MOVE，也避免破坏 Zotero 对远端存储布局的预期。

## D-05｜为什么确认单个文件不依赖大目录扫描

DavBridge 已知刚上传对象的准确路径，因此直接对准确资源 URL 执行 Depth:0 属性查询和 GET。即使 `/zotero` 已有上万个对象，单文件确认也不需要重新列举整个目录，因此不受 750 条列表返回限制影响。

## D-06｜为什么每个对象都从目标端重新 GET

用户遇到过通用同步器显示上传成功但目标云端实际无数据的问题。DavBridge 的核心价值就是消除这种假成功。坚果云下载额度高于上传额度，因此在每次迁移时重新 GET 并比较 SHA-256，是用额外下载换取可证明可靠性的合理取舍。

## D-07｜为什么最终不一次性重新下载全部库

十余 GB 的最终全量重下载会超过坚果云单周期下载额度。强校验在每个对象迁移时完成并持久化。最终交割只重新检查源变化、目标属性变化和失效记录，仅对变化或不可确认对象再次下载。

## D-08｜为什么采用 50 MB 普通预留与周期末冲刺

普通阶段始终为其他坚果云服务预留 50 MB，避免 DavBridge 抢占全部额度。距离官方重置时间不足 24 小时时可进入冲刺，将安全余量降至默认 5 MB。额度耗尽响应在真实账户验证前不写死，冲刺仍以可恢复和不误判为优先。

## D-09｜为什么允许人工校准流量

当前没有找到面向普通坚果云 WebDAV 用户、公开稳定且文档化的账户实时流量 API。逆向网页登录接口会引入 Cookie、兼容性和长期维护风险，因此采用“官方页面人工校准点 + DavBridge 后续保守计量”。这不会阻塞后台自动迁移。

## D-10｜为什么迁移期间 Zotero 继续使用 InfiniCLOUD

迁移可能跨多个流量周期。若 Zotero 同时写目标坚果云，会让目标对象来源和冲突判断失去确定性。迁移期间唯一权威源保持 InfiniCLOUD，DavBridge 单向追赶。最终验收完成后再一次性切换 Zotero WebDAV 服务。

## D-11｜为什么允许接管 GoodSync 已有目标文件

用户的坚果云 `/zotero` 中已经存在数百个此前由 GoodSync 复制的文件。全部删除后重传会浪费有限的上传额度，也没有必要。DavBridge 不依据文件名存在或 GoodSync 的成功记录判断完成，而是重新下载目标对象并计算 SHA-256。目标实际内容与当前 InfiniCLOUD 源对象完全一致时，允许直接标记为强校验完成并接管已有副本，不执行 PUT；内容不同、损坏或无法证明一致时停止为冲突，不自动覆盖。

这项设计同时意味着下载额度也必须成为硬安全边界。既有目标文件的验收会消耗坚果云下载流量，因此同时维护上传和下载配额。组级上传预算只预留目标端缺失成员，已有成员先进行目标 GET 验收；若确认是 DavBridge 自己先前写入且允许更新的旧版本，则在真正 PUT 前再次执行上传额度检查。

## D-12｜产品定位只做单向迁移、备份和镜像

DavBridge 不发展为双向同步器。底层可以保留通用任务、端点和策略抽象，但近期产品目标是把已经真实运行的 Zotero 单向任务做好。双向删除传播、双向冲突合并、双向 rename detection 和循环同步不进入近期路线。

## D-13｜冻结功能扩张，优先完成当前任务体验

当前不开放“新建任务”，不增加普通 WebDAV 任务，不增加新的端点类型。当前工作优先改善已有主页、状态表达、进度、周期流量、暂停与继续、托盘、设置、诊断、异常提示和窗口自适应。已验证的迁移引擎与 Data 契约继续冻结。

## D-14｜主页只回答五类问题

日常主页只需要让用户快速知道：从哪里迁到哪里、现在是什么状态、总体完成多少、当前正在处理什么、本周期还能传多少。首次初始化、连接诊断、扫描、安全验证和维护操作全部退到二级入口。初始化完成后不再把开发阶段按钮长期暴露在主页。

## D-15｜总体进度以源清单和 StrongVerified 逻辑组为真值

总体进度不得使用坚果云目录当前列举数量推算，因为单次列表可能停在 750 项。可靠进度定义为源端当前逻辑组总数，以及其中已经完成目标端强校验的逻辑组数。界面可以同时显示已处理文件对象数，但百分比优先按逻辑组计算。目标端只显示已核验多少组，不声称这是目标目录的完整枚举总数。

## D-16｜当前文件进度必须是真实字节进度

主页显示当前文件百分比和文件内进度时，百分比必须来自真实 GET 或 PUT 的已处理字节数。不能把读取源文件、上传目标、重新下载校验等阶段人为折算成虚假的 20%、50%、80%。进度观测层可以扩展传输流回调，但不得改变 SHA-256、配额、PUT、GET 和强校验语义。

## D-17｜上传和下载额度必须分别可视化

上传和下载是两个独立额度，主页使用两个独立进度条。正常余量、接近安全边界和接近停止阈值需要有清晰视觉差异。安全预留与重置语义应明确，但不能把本地估算冒充官方实时流量。

## D-18｜主页主控制只保留一个动态主操作

主操作根据状态变化。运行中显示暂停，暂停时显示继续，需要人工时进入审查，等待额度或网络时显示对应真实状态。诊断不长期占据主页主操作区。

## D-19｜托盘优先，完整主窗口是低频管理界面

DavBridge 的常态是右下角后台运行。完整主窗口用于低频查看和配置。任何托盘轻量状态能力都不得复制完整主窗口，也不得承载初始化或危险操作。

## D-20｜设置继续由原生宿主承载敏感操作

v0.4 主业务 UI 已迁移到 WebView2，但设置仍由 C# 原生宿主打开。敏感配置、凭据、DPAPI 和危险最终确认不进入 JavaScript。未来即使重做设置视觉，也必须先审查权限边界。

## D-21｜响应式布局不能依靠持续压窄侧栏

v0.4.3 已采用固定左侧栏。窗口缩小时应优先让内容合理重排或使用明确的紧凑策略，而不是无限压窄导航。任何常见 Windows DPI 和正常工作尺寸下都不得出现按钮遮挡、文字覆盖或关键状态被裁掉。

## D-22｜继续和暂停需要瞬时过渡状态

用户点击继续后，后台仍需要恢复配置、读取源端清单并建立本轮执行上下文，因此不能让界面在短暂等待期间继续显示已暂停。点击暂停后也应先进入安全暂停过程，待当前运行实例完成取消和断点保存后再显示已暂停。这些瞬时状态只属于 UI，不应为了显示便利破坏旧 Data 兼容。

## D-23｜为什么 v0.4 改用 Vue + WebView2

v0.3 的多轮实机精修证明，继续通过 WinForms TableLayout、运行时 overlay、reparent 和自绘补丁实现现代信息层级，维护成本高且容易出现布局回归。v0.4 因此只替换显示层，用 Vue 负责业务页面布局和视觉，用 WebView2 承载本地静态 UI，用 C# 宿主守住 Windows 能力和安全边界。

这个决策不是重写产品。DavBridge.Core、WebDAV、StrongVerified、quota/Cycle、reconciliation、DELETE 和 Data 继续留在 C#。

## D-24｜为什么采用固定左侧导航

v0.4.3 将主要导航固定到左侧，原因是 DavBridge 是低频管理、长期后台运行的软件，页面数量稳定，侧栏可以让总览拥有更连续的纵向信息空间，并让设置、关于和运行状态有稳定位置。

总览不再堆叠解释性说明，而是固定为迁移路径、三阶段、覆盖率、当前任务、流量预算和底部主控制。定义性信息进入 tooltip 和文档。

## D-25｜最终 UI 判断必须来自真实 Windows

浏览器视觉预览、Vue 构建、native-host self-test 和布局自动门只能证明结构、编译与边界，不能完整代表 WebView2 字体、Windows DPI、窗口装饰和真实交互感受。每个明显 UI 候选在提升 stable 前仍需要用户真实 Windows 验收。
