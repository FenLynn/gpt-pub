# DavBridge 设计与演进

本文件只记录后续很可能被重新提出、且影响长期实现边界的重大设计决定。

## D-01｜为什么不是 Python

DavBridge 需要长期托盘常驻、开机自启动、轻量部署和稳定 Windows 集成。首阶段采用 C# / .NET 8 / WinForms，避免 Python 运行环境和常见打包体积问题。

## D-02｜为什么使用 framework-dependent 单文件

AtlasDesk 已验证 `--self-contained false + PublishSingleFile` 可以显著降低 Runtime 体积。DavBridge 功能更单一，不需要携带 WebView2、FFmpeg 或原生宿主，因此优先沿用轻量发布路线。目标机若缺少对应 .NET Desktop Runtime，程序应明确提示，而不是打包百 MB 级 Runtime 作为默认交付。

## D-03｜为什么不用 Windows Service

DavBridge 需要用户偶尔查看状态、人工校准坚果云流量、修改连接和执行最终交割。普通托盘程序已经能提供登录后自动启动、后台常驻和低资源等待，不需要 Service 带来的权限、安装和调试复杂度。

## D-04｜为什么不按 700 个文件建立远端子目录

坚果云的 750 项限制是一次目录列举返回量，不是单目录总容量。Zotero 的远端对象应保持标准 `/zotero` 结构。迁移批次只存在于本地状态，不改变远端路径，避免最终再做大规模 MOVE，也避免破坏 Zotero 对远端存储布局的预期。

## D-05｜为什么确认单个文件不依赖大目录扫描

DavBridge 已知刚上传对象的准确路径，因此直接对准确资源 URL 执行 Depth:0 属性查询和 GET。即使 `/zotero` 已有上万个对象，单文件确认也不需要重新列举整个目录，因此不受 750 条列表返回限制影响。

## D-06｜为什么每个对象都从目标端重新 GET

用户遇到过通用同步器显示上传成功但目标云端实际无数据的问题。DavBridge 的核心价值就是消除这种假成功。坚果云下载额度高于上传额度，因此在每次迁移时重新 GET 并比较 SHA-256，是用额外下载换取可证明可靠性的合理取舍。

## D-07｜为什么最终不一次性重新下载全部库

十余 GB 的最终全量重下载会超过坚果云单周期下载额度。强校验在每个对象迁移时完成并持久化。最终交割只重新检查源变化、目标属性变化和失效记录，仅对变化或不可确认对象再次下载。

## D-08｜为什么采用 50 MB 普通预留与周期末冲刺

普通阶段始终为其他坚果云服务预留 50 MB，避免 DavBridge 抢占全部额度。距离官方重置时间不足 24 小时时可进入冲刺，将安全余量降至默认 5 MB。额度耗尽响应在真实账户验证前不写死，冲刺仍以可恢复和不误判为优先。

## D-09｜为什么允许人工校准流量

当前没有找到面向普通坚果云 WebDAV 用户、公开稳定且文档化的账户实时流量 API。逆向网页登录接口会引入 Cookie、兼容性和长期维护风险，因此采用“官方页面人工校准点 + DavBridge 后续保守计量”。这不会阻塞后台自动迁移。

## D-10｜为什么迁移期间 Zotero 继续使用 InfiniCLOUD

迁移可能跨多个流量周期。若 Zotero 同时写目标坚果云，会让目标对象来源和冲突判断失去确定性。迁移期间唯一权威源保持 InfiniCLOUD，DavBridge 单向追赶。最终验收完成后再一次性切换 Zotero WebDAV 服务。

## D-11｜为什么允许接管 GoodSync 已有目标文件

用户的坚果云 `/zotero` 中已经存在数百个此前由 GoodSync 复制的文件。全部删除后重传会浪费有限的 1 GB 上传额度，也没有必要。DavBridge 不依据“文件名存在”或 GoodSync 的成功记录判断完成，而是重新下载目标对象并计算 SHA-256。目标实际内容与当前 InfiniCLOUD 源对象完全一致时，允许直接标记为强校验完成并接管已有副本，不执行 PUT；内容不同、损坏或无法证明一致时停止为冲突，不自动覆盖。

这项设计同时意味着下载额度也必须成为硬安全边界。既有目标文件的验收会消耗坚果云下载流量，因此 v0.1.2 起同时维护上传和下载配额。组级上传预算只预留目标端缺失成员，已有成员先进行目标 GET 验收；若确认是 DavBridge 自己先前写入且允许更新的旧版本，则在真正 PUT 前再次执行上传额度检查。
