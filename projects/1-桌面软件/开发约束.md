# 桌面软件开发约束

> 约束层级：B｜分类级  
> 适用范围：`projects/1-桌面软件/` 下所有正式项目  
> 上位规则：A｜`/GPT_RULES.md`  
> 下位规则：各项目 `开发约束.md`（如存在）

本文件只规定桌面软件共同需要的分支、CI、发布、Runtime/Data 和真实环境验证边界。项目约束可以增加更严格的要求，但不得放宽本文件或 `GPT_RULES.md`。

《软件设计记录建议书》是参考建议，不是本文件的替代品。

## B-01｜长期分支模型

进入持续维护和正式发布流程的项目统一使用：

| 分支 | 作用 | 允许内容 |
|---|---|---|
| `pNNN-exp` | 日常开发与连续集成 | 当前项目的开发提交 |
| `pNNN-stable` | 冻结的稳定候选 | 只接收对应 `exp` 的提升 PR |
| `main` | 全仓稳定且可发布的共同主线 | 只接收项目 `stable` 或独立仓库级 PR |

固定流程：

```text
最新 main
→ 项目 exp
→ PR：exp → stable
→ 完整准入验证
→ PR：stable → main
→ 从 main 建立标签和 Release
→ main 回流 stable / exp
```

禁止：

- 直接在 `stable` 或 `main` 开发功能；
- `exp`、临时任务分支或外部分支直接进入 `main`；
- P101 分支合并 P102 分支，或任何项目长期分支互相合并；
- 用强制重置、强推或历史改写“整理”长期分支。

## B-02｜开始开发与主线同步

每次开始新阶段前，先比较 `main`、项目 `exp` 和项目 `stable`：

- `exp` 没有独有提交时，快进到最新 `main`；
- `exp` 已有继续开发的独有提交时，将最新 `main` 正常合并进 `exp`，不得强制覆盖；
- `stable` 只保存当前候选，不承载下一版本开发；
- 提升 `exp → stable` 前，`exp` 必须已经包含最新 `main`；
- 提升 `stable → main` 前，必须重新确认候选相对最新 `main` 的差异只属于当前项目。

项目进入 `main` 后：

- `stable` 没有独有提交时快进到最新 `main`；
- `exp` 没有继续开发时同样快进到最新 `main`；
- `exp` 已进入下一阶段时，将最新 `main`合并进 `exp`；
- 其他项目分支可以等到下一次开发前再同步，但不得在过时基线上直接提升。

## B-03｜临时分支与仓库级分支

普通串行开发直接在项目 `exp` 推进。只有高风险、并行、容易推翻或需要独立审查的工作才建立临时分支：

```text
pNNN-简短任务名
```

根规则、分类规则、共享入口和仓库基础设施使用：

```text
repo-简短任务名
```

临时分支必须从正确基线建立，并通过 PR 回到对应 `exp` 或 `main`，不得绕过既定层级。

长期分支不得删除。临时分支只有在用户明确授权、PR 已完成并确认没有独有提交后才能删除；不得使用通配符批量删除分支。

## B-04｜PR 路径与范围门禁

一个 PR 只能属于以下一种：

| 来源 | 目标 | 用途 |
|---|---|---|
| `pNNN-任务` | `pNNN-exp` | 独立任务回到日常开发线 |
| `pNNN-exp` | `pNNN-stable` | 冻结并验证稳定候选 |
| `pNNN-stable` | `main` | 正式准入与发布基线 |
| `repo-任务` | `main` | 根规则、分类规则或仓库设施 |

项目 PR 相对目标分支的有效差异只允许包含：

```text
对应项目目录
对应项目 CI
当前项目确有必要的共享目录或状态行
```

根规则、分类约束或无关仓库设施不得夹带在产品版本 PR 中；产品源码也不得夹带在普通 `repo-*` PR 中。

**范围门禁是强制项。** 每个项目的 PR CI 必须通过 `git diff <base>...HEAD` 检查允许路径，发现越界立即失败。现有工作流尚未具备自动范围门禁时，只能临时在 PR 中记录完整差异复核，并必须在下一次 CI 调整时补齐自动检查。

PR 正文至少写明：

```text
目标
源分支与目标分支
允许修改范围
实际修改范围
验证结果
产物或证据
风险与尚缺内容
合并后的同步或清理动作
```

## B-05｜CI 分层

每个正式项目应尽量保留一个稳定的长期 CI 工作流；版本专用、迁移专用或修复专用工作流只能短期存在。

### 1. `exp` 快速验证

`pNNN-exp` 的 push 或相关 PR 至少运行：

- 范围门禁；
- 源码或依赖清单校验；
- 单元测试和关键回归测试；
- 静态检查、格式或编译检查；
- 基础目标平台构建。

目标是尽快发现代码错误，不要求每次生成正式发布包。

### 2. `exp → stable` 完整验证

进入 `stable` 前必须运行当前项目规定的完整准入，包括：

- 范围门禁；
- 全量测试和关键竞态、静态或安全检查；
- 目标操作系统原生构建；
- 原生 smoke、自检或端到端验证；
- 真实运行依赖验证，不能只用空壳或模拟文件证明成功；
- 正式候选打包；
- Runtime/Data、隐私和敏感文件扫描；
- 版本号、产品名、资源和文件名一致性检查；
- 候选 Artifact、清单和 SHA-256。

涉及 UI、DPI、窗口、安装、播放器、硬件编码或其他自动化难以完整覆盖的变化，还必须明确记录实机验收项；尚未实机确认时只能标为“待验证”。

### 3. `stable → main` 正式准入

进入 `main` 前必须在**当前 PR 的准确 head SHA** 上重新通过：

- 范围门禁；
- 必需的完整项目 CI；
- 版本与发布信息核对；
- 正式产物生成条件核对。

不得用另一分支、旧提交或不同 SHA 上的绿色运行代替当前候选。必需检查失败、仍在运行或意外跳过时不得合并。

### 4. 标签与 Release

正式 Release 必须从 `main` 上的准确标签提交构建或复核。不得把未进入 `main` 的临时产物直接作为正式发布。

## B-06｜CI 安全与可靠性

所有长期 CI 必须遵守：

- 默认 `permissions: contents: read`，只在独立发布或维护任务中授予最小必要写权限；
- 公共 PR 不向不可信代码暴露 Secrets；
- 不使用 `pull_request_target` 执行 PR 中的代码；
- 项目工作流使用严格路径过滤，避免无关项目触发重量 CI；
- PR 范围检查必须使用目标分支与 PR head 的真实差异；
- 每个长任务设置合理 `timeout-minutes`；
- `exp` 和普通 PR 使用并发取消，新的提交应取消旧运行；标签与正式发布运行不得被后续普通提交取消；
- 必需检查不得使用 `continue-on-error` 掩盖失败；
- 不得反复重跑失败工作流直到偶然变绿，必须解释并修复根因；
- 外部下载仅允许对明确的瞬时网络错误有限重试，构建、测试和校验失败不得自动忽略；
- 使用明确版本的官方 Action，升级后重新验证；
- 构建目录、缓存、日志和测试输出不提交到普通 Git 历史；
- Artifact 只保存必要证据和候选产物，并设置有限保留期。

CI 工作流本身发生修改时，至少验证 YAML 可解析、触发分支正确、路径过滤正确、权限最小、范围门禁有效，并避免因改名破坏已有必需检查。

## B-07｜自动化不得擅自改写仓库

普通测试和构建工作流只能读取仓库并上传 Artifact，不得：

- 推送代码或修改分支引用；
- 强制更新 `main`、`exp` 或 `stable`；
- 自动合并未经审查的 PR；
- 批量删除分支、标签或 Release；
- 修改其他项目目录或 CI。

确需执行发布、回流或清理的自动化时，必须使用独立工作流，并满足：

1. 当前任务已经明确授权；
2. 写权限最小；
3. 操作对象使用精确分支、标签和文件白名单，不使用宽泛通配符；
4. 更新引用前先比较提交关系；
5. 禁止强推长期分支；
6. 失败时停止，不继续执行后续破坏性步骤；
7. 结果记录到 PR、Release 或阶段记录。

## B-08｜正式发布与产物

正式发布至少固定：

- `main` 上的源提交；
- 版本号和不可移动标签；
- 目标平台与架构；
- CI、原生自检和实机验证结论；
- Artifact 或 Release 资产；
- 文件大小和 SHA-256；
- 版本说明、已知限制和签名状态。

版本号必须有明确单一来源，代码、资源、窗口、构建脚本、文件名、阶段记录和 Release 不得互相矛盾。

单文件交付至少记录文件名、大小和 SHA-256。多文件 Runtime 必须生成清单，记录相对路径、大小和 SHA-256，并在压缩后重新解包复核。

正式标签建立后不得移动或复用。Release 资产必须对应标签的准确源码，不得手工替换为不同提交生成的同名文件。

## B-09｜Runtime、Data 与迁移

- Runtime、源码、CI、Artifact 和 Release 不得包含用户配置、密码、Token、Cookie、日志、缓存、任务历史、浏览器 Profile 或其他私人 Data；
- 程序运行时产生的数据不得写回公开 Runtime，除非项目 C 级约束明确规定为公开且可再生的文件；
- 数据迁移必须先备份或保留旧数据；
- 默认只复制缺失内容，不静默删除旧数据，不覆盖已经存在的新数据；
- 不可逆清理必须由用户明确触发，并提供清楚的范围与结果；
- 项目特有的数据目录、格式、加密和兼容规则写入项目 C 级约束。

## B-10｜真实环境与用户验收

开发者和自动化必须承担主要验证责任，不得把用户作为基本功能测试器。

根据修改范围准备自动样本、故障注入和回归测试。涉及下列内容时，应在目标 Windows 环境完成相应验证：

- 原生启动、退出、托盘和多实例；
- 不同窗口尺寸、最大化、DPI 和多显示器；
- 中文、空格和长路径；
- Runtime 覆盖更新与 Data 保留；
- 真实外部依赖、播放器、编码器、浏览器组件或硬件能力；
- 长时间运行、并发、取消、失败恢复和资源释放。

自动验证无法证明的视觉或硬件结果必须明确列为“待验证”，不能用“构建成功”替代。

## B-11｜一次性工作流与收尾

迁移、截图、发布、回流、修复和清理等一次性工作流必须：

- 文件名明确包含项目与用途；
- 使用手动触发或严格限定的触发条件；
- 不与长期 CI 使用相同名称；
- 只访问当前任务允许的路径和引用；
- 任务完成后删除工作流及临时触发文件，只在 Git 历史保留；
- 不得长期留在 `main` 继续响应普通 push 或 PR。

临时 PR 完成后应关闭；临时分支是否删除仍服从 A-06，必须取得用户明确授权并确认无独有提交。

## B-12｜合并与发布停止条件

出现以下任一情况，必须停止提升、合并或发布：

- 项目分支未包含最新 `main`；
- PR 混入其他项目或无关仓库修改；
- 范围门禁、测试、构建、自检或隐私扫描失败；
- 必需检查被意外跳过；
- 版本、资源、标签、产物或哈希不一致；
- Artifact 缺失、无法解包或内容不完整；
- 自动化准备执行强推、批量删除或未授权引用更新；
- 尚有未说明的实机、兼容或数据迁移风险。

停止后先修正根因并重新验证，不得通过删测试、放宽门禁、改写分支历史或手工替换产物制造“通过”。
