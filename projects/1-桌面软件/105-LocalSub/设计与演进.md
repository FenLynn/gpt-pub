# P105｜LocalSub 设计与演进

> 记录影响长期维护的架构选择及其原因。执行硬约束以 `开发约束.md` 为准。

## D-01｜正式编号纠正为 P105

**决策：** LocalSub 在 GPT-Pub 中正式编号为 `P105`，路径固定为 `projects/1-桌面软件/105-LocalSub/`。

**原因：** P101、P102、P103、P104 均已有其他软件。此前 LocalSub 迁移误用了 P103，造成 `103-DavBridge` 与 `103-LocalSub` 在开发分支并存，并在 main 留下了错误命名的 LocalSub workflow。

**处理原则：**

- P103 DavBridge 的目录、分支与 CI 不改名、不覆盖。
- P105 从最新 main 新建长期分支，不直接继承错误 P103 LocalSub 分支 ancestry。
- Phase 1A 源码从固定历史 head 抽取到 P105 正式路径。
- 历史 PR/commit 保留用于追溯，但关闭错误编号的活动 PR，不再作为维护入口。
- main 中错误的 P103 LocalSub workflow 删除，正式 CI 改为 P105 命名。

## D-02｜采用轻量 Shell + 独立 Core，而不是一次性重写

**决策：** 保留 C#/.NET 8 和已经验证的 Windows/ASR 底层资产，先建立进程隔离，再迁移 UI。

**原因：** LocalSub 已积累 Process Loopback、raw COM、PotPlayer 恢复 supervisor、sherpa native C API、模型管理和 WebView2 Overlay 等高风险 Windows 专用实现。直接全量改成另一技术栈会把进程隔离、底层重写和 UI 重写混成一个不可诊断的大迁移。

目标结构：

```text
LocalSub.exe
轻量 Windows Shell
├─ window / tray / lifecycle
├─ overlay
├─ WebView2 host（Phase 2）
└─ Named Pipe IPC
        ↓
LocalSub.Core.exe
├─ media decode
├─ WASAPI / PotPlayer process loopback
├─ sherpa-onnx
├─ streaming/offline ASR
├─ VAD
├─ model heavy work
└─ background transcription
```

## D-03｜Core 失败必须显式，不做静默 fallback

**决策：** 某类能力迁入 Core 后，Shell 不再保留可自动接管该重任务的完整实现。

**原因：** 如果 Core 异常后 GUI 又偷偷在本进程执行同样任务，表面上提高了“可用性”，实际上破坏了进程隔离目标，最难复现的 GUI 卡死会重新出现。

因此 Phase 1A 对后台媒体分析与后台转写采用编译期排除 + Proxy，而不是运行时优先级选择。

## D-04｜IPC v1 选用 Windows Named Pipe + JSON

**决策：** IPC v1 采用 Windows Named Pipe、UTF-8、newline-delimited JSON。

**原因：**

- Windows 单机双进程，无需网络监听或额外服务。
- 便于人工日志诊断和 CI 真连接测试。
- C# 两端实现成本低。
- 后续 WebView2/Vue 只需要通过 Shell bridge 消费稳定消息，不依赖 Core 内部实现。

v1 方法固定为 `ping / analyze / transcribe / cancel / shutdown`，协议扩大时优先向后兼容和可诊断失败。

## D-05｜从严格串行改为 Contract-first 交错迁移

**决策：**

原来的严格顺序：

```text
Phase 1A
→ Phase 1B 全部完成
→ Web UI
→ 删除 WinForms
```

调整为：

```text
Phase 1A
→ Phase 1B.0 Application Contract
→ Phase 1B.1 实时链迁入 Core
→ Phase 2A Web Shell
→ Phase 1B.2 模型重任务迁入 Core
→ Phase 2B 逐页迁移
→ Phase 3 删除旧 WinForms 业务页
```

Phase 1B 后续与 Phase 2 可以在稳定 DTO、命令白名单和 session 契约下交错推进，不要求等待所有 Core 工作全部完成。

**原因：**

- Phase 1A 已建立真实 Shell/Core 双进程、generation 恢复和后台重任务隔离，Web UI 不再面对最初完全耦合的单进程状态。
- LocalSub 已经长期使用 WebView2 字幕 Overlay，因此主 Web UI 不再意味着引入全新的运行时。
- 当前真正的大耦合点已经集中到 `LiveAsrPipeline`，可以先独立迁入 Core。
- 如果继续等待模型管理等全部重任务迁移完成才开始 UI，会让明显落后的 WinForms 业务界面长期阻塞产品体验。
- Web UI 只要严格依赖稳定契约，就可以和后续 Core 迁移并行而不复制底层逻辑。

仍然禁止一次性重写全部 UI、实时链、模型链和后台链。

## D-06｜基础包保持轻量，运行时与模型外置

**决策：** 两个 EXE 进入基础绿色目录，但模型、FFmpeg、ONNX Runtime 和 sherpa native runtime 继续外置。

**原因：** 模型与 native runtime 体积大、更新节奏不同，用户已有完整 `ASR/`、`ASR/_runtime/` 与 Mediova FFmpeg 环境。日常补丁只替换程序文件可以显著减少下载、CI Artifact 和误覆盖风险。

## D-07｜CI 证明边界存在，实机证明 GUI 体验

**决策：** 自动化和用户实机测试分工明确。

CI 必须真实启动 Shell/Core、连接 Pipe、做 native runtime/ASR 烟测并检查包边界；但“后台高负载时窗口是否持续响应”和“强杀 Core 后 GUI 是否仍自然可用”必须保留真实 Windows 实机验收。

自动化不能把尚未用户确认的响应性结论写成“已验证”。

## D-08｜连接恢复使用 generation 隔离，不复用半失效 IPC

**决策：** 从 v0.1.1-dev 起，每次 Shell 成功建立 Core Pipe 都分配独立 connection generation。reader loop、pending request 和断开回调只作用于自己的 generation。

**原因：** 仅依赖 `_pipe.IsConnected` 和全局 reader/writer 存在竞态。旧 Core 退出时，旧 reader loop 的 finally 可能晚于新 Core 重连，如果它直接失败全局 pending 请求，就有机会误伤已经属于新连接的任务。

因此采用以下恢复原则：

- 每个 pending request 绑定创建它的 generation。
- 旧 generation 断开只失败旧 generation 的 pending request。
- 当前 generation 一旦标记 broken，下一请求不得继续写旧 Pipe，而是重新启动 Core。
- 用户取消先走协议 `cancel`；如果 1.5 秒后任务仍未收敛，则回收当前 Core，避免 native 卡死长期占住唯一重任务槽。
- 正常退出优先走主动 `shutdown`，parent watcher 继续作为 Shell 异常消失时的兜底。
- Shell 侧单独写 `core-client.log`，与 Core 自身 `core.log` 分离，便于判断问题发生在 supervisor/IPC 还是 Core 内部。

CI 对这一状态机采用真实 fault injection：在一个延迟 ping 请求仍处于 pending 时结束第一 Core，必须看到该请求失败，然后同一 client 重新启动第二 Core 并再次 ping 成功。这个自动门禁证明恢复逻辑，不替代真实 GUI 高负载体验。


## D-09｜冻结 Application Contract，UI 不直接拥有业务核心

**决策：** 新一轮迁移先固定 `docs/APP_CONTRACT.md`，再修改实时链和主 UI。

契约明确三层所有权：

```text
Vue
只表达状态和用户意图
        ↓
LocalSub.exe
Windows Shell、WebView2、Overlay、生命周期、Core supervisor
        ↓
LocalSub.Core.exe
音频捕获、ASR、媒体分析、模型重任务
```

Web UI 只允许读取 DTO、发送白名单命令和接收白名单事件，不得直接打开 Named Pipe、访问 WASAPI、操作 PotPlayer HWND、读取内部日志或复制 C# 业务核心。

**原因：** 如果只是把 `MainForm` 的事件处理函数逐条翻译成 Vue，耦合只会从 WinForms 转移到 JavaScript，并不会获得真正可维护的 UI 架构。Application Contract 先于页面迁移，可以让旧 WinForms 与未来 Vue 在过渡期共享同一业务事实源。

## D-10｜实时链使用 session，而不是长时间普通请求

**决策：** Phase 1B.1 将实时识别建模为显式 session。

`live.start` 成功后立即返回 `sessionId`，随后通过事件持续推送：

```text
live.status
live.level
live.partial
live.final
live.discontinuity
live.failed
```

`live.stop` 明确结束当前 session。

音量事件默认限频到约 10 Hz，避免音频 callback 原始频率穿过 Named Pipe、Shell、WebView2 和 Vue。

**原因：** 实时字幕可能连续运行数小时，不适合沿用 `analyze/transcribe` 的一次请求一次最终响应模型。显式 session 更容易处理停止、Core 重启、状态恢复和 UI reconnect。
