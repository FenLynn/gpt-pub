# Mediova 运行期持久化、便携模式与状态反馈续审记录

## 记录范围

本文承接《持久化与组件边界续审记录》，登记 2026-08-03 继续完成的三轮实验线工作：

1. 启动后发生磁盘写满、权限变化或安全软件占用时的即时持久化反馈；
2. 普通 AppData 与 `MediovaData` 并存时，便携模式切换的数据权威性；
3. 多条运行环境提醒在窄状态栏中的摘要、完整详情与诊断报告收口。

全部成果仅进入 `p101-exp`。不改变 v4.5.0 版本号、正式标签、Release 或正式 EXE。

---

## 第一轮｜运行中持久化失败即时反馈与补偿

### 复核发现

启动前写入预检只能确认当时的数据目录状态。软件运行后仍可能出现磁盘写满、NTFS 权限变化、安全软件临时独占、网络或同步软件锁定文件等情况。

原有配置保存调用中存在直接忽略错误的路径；会话保存失败主要写入运行诊断；历史追加失败也可能缺乏立即可见反馈。若逐处修改几十个调用点，不仅容易遗漏，也会增加主窗口大文件的维护风险。

### 已实施

- 新增配置、任务会话和历史记录的运行期内容指纹；
- 仅在内容发生变化时复核持久化，不持续重写业务文件；
- 明确排除实时 `Progress` 字段，转换过程中不会因进度变化高频重写 `session.json`；
- 配置保存失败时保留待保存状态，并通过主 UI 线程定时器继续重试；
- 队列结构、状态、参数或终态变化后复核会话快照；
- 新终态任务先比对现有历史，确认缺失后才补写，正常成功路径不会制造重复记录；
- 历史文件读取异常时不把空集合写回，不覆盖原文件；
- 同一文件类别、操作和错误指纹在 30 秒内去重；
- 不同类别或不同错误立即显示；
- 写入恢复后只提示一次“最新更改已经写入”；
- 提示写入状态栏并保留在 `runtimeNotice`，不使用阻断式弹窗；
- Windows 端使用 UI 线程 `SetTimer` 回调，不增加后台轮询 goroutine 或 ticker；
- self-test 和 UI 截图模式不启动运行期守护；
- 新增 `RUNTIME_PERSISTENCE_GUARD_FILES_SHA256.txt` 固定清单。

### 自动验证矩阵

- 配置内容指纹稳定性；
- 队列内容变化触发指纹变化；
- 实时进度变化不改变会话指纹；
- 首次失败显示；
- 30 秒内相同错误去重；
- 不同文件类别不互相抑制；
- 写入恢复提示只消费一次；
- 完成、失败、跳过和停止任务的历史记录映射；
- 已有历史匹配时不重复追加；
- Windows 源码契约禁止后台轮询。

### 门禁发现与自纠

第一候选将完整任务对象纳入指纹，意味着实时进度会让转换过程中约每 1.5 秒重写会话文件。该候选虽然能够通过编译和竞态验证，但行为不符合低频持久化目标，因此未作为合并依据。

随后明确清零指纹副本中的 `Progress`，并增加“进度变化不改变会话指纹”测试。

### 证据

- PR：`#311`
- 旧候选：`711092ceb1762324d7ad7a40dbcf17e23a96b2be`
- 旧候选 CI：`30800008824`，不作为合并依据；
- 最终候选：`912cef409791370014a856e79fc9d9bc03babaf8`
- 最终 CI：`30800337328`
- 合并：`ec59bfd5c44508646e0e6bbb13319020c62435db`

## 第二轮｜便携模式切换的数据权威性

### 复核发现

原便携模式操作主要改变 `portable.mode` 标记。若普通 AppData 与 EXE 同目录的 `MediovaData` 同时存在，重启后目标位置的旧配置、旧任务或旧历史可能突然成为权威。

此外，标记一旦提前改变，重启前的后续保存也可能转入目标目录；运行中的转换若同时切换数据位置，还会使配置、会话和历史分别落入不同位置。

### 设计原则

- 当前正在使用的数据永远是切换来源和最终权威；
- 目标旧数据不得静默覆盖当前数据；
- 目标旧数据先备份，再替换；
- 源目录不删除；
- 非托管缓存和用户文件不参与模式切换；
- 只有完整准备成功后才改变模式标记。

### 已实施

- 接管现有“便携模式”菜单命令；
- 转换任务运行中禁止切换；
- 切换前先刷新当前配置；
- 启用会话恢复时先写入当前任务会话；
- 目标托管文件先备份到 `.mode-switch-backups/<时间戳>`；
- 权威集合覆盖：
  - `config.json`
  - `config.json.bak`
  - `config.json.lastgood`
  - `config.json.legacy`
  - `session.json`
  - `session.json.tmp`
  - `session.json.bak`
  - `history.json`
  - `history.json.lastgood`
  - `history.json.bak`
- 目标文件按当前来源精确替换；
- 来源不存在的目标旧会话、历史或恢复副本从主路径清理，但完整保留在备份中；
- 非托管缓存、用户文件和源目录保持不变；
- 目标路径被普通文件占用或准备失败时，标记保持不变；
- 使用专用 `.mode-switch-old` 完成原子替换；
- 只有刷新、分阶段准备、目标备份和替换全部成功后，才调用 `SetPortableMode`；
- 标记写入失败时继续使用原数据位置；
- 完成提示说明目标位置、备份状态和重启要求；
- Windows 端在主 UI 线程接管命令，不增加后台线程；
- 新增 `PORTABLE_MODE_AUTHORITY_FILES_SHA256.txt` 固定清单。

### 自动验证矩阵

- 当前普通模式数据覆盖目标便携旧数据；
- 当前便携数据写回普通 AppData；
- 目标旧配置、会话和历史完整备份；
- 源缺失的目标托管文件被安全清理；
- `config.json.bak` 与 `session.json.tmp` 不在切换后重新夺权；
- 非托管缓存保持不变；
- 源数据保持不变；
- 目标被普通文件占用时无损失败；
- 完成摘要包含写入、清理、备份和重启信息；
- Windows 源码契约禁止后台线程和源目录删除。

### 门禁发现与自纠

#### 1. 瞬态恢复副本遗漏

初始托管集合只覆盖主文件和长期有效副本。复核发现，目标残留的 `config.json.bak` 或 `session.json.tmp` 仍可能被后续恢复逻辑读取，使旧模式数据重新取得权威。

因此将两类瞬态副本纳入备份、替换与清理集合，并增加直接测试。

#### 2. 通用原子写入与真实 `.bak` 冲突

通用 `atomicWrite` 会使用 `<主文件>.bak` 作为临时备份名。便携模式事务本身又需要把 `config.json.bak`、`session.json.bak` 等作为真实托管数据处理；若复用通用原子写入，写主文件时可能误删刚迁移的真实恢复副本。

因此改用专用 `.mode-switch-old` 临时名，实现独立原子替换。

### 证据

- PR：`#312`
- 最终候选：`4714a108b2502b39bb9cf08451890ff489a7fb05`
- 最终 CI：`30801844980`
- 合并：`6bb04742372522f4bf309a3606690f55e1a41661`

## 第三轮｜状态栏诊断摘要、完整详情与诊断报告

### 复核发现

既有底部布局已经通过 900–1920 逻辑像素连续宽度矩阵，按钮、进度条和状态区本身没有几何重叠。继续移动按钮会增加回归风险。

真正剩余的问题是：Runtime、配置、会话、历史、数据目录和便携模式多条提醒合并后，长文本在窄状态区中难以阅读；但直接截断又会丢失问题类别和详情入口。

### 已实施

- 不修改底部按钮坐标和现有空间预算；
- 将诊断信息分类为：
  - Runtime
  - 配置
  - 会话
  - 历史
  - 数据目录
  - 便携模式
- 识别失败、错误、异常、损坏、不可写、不可用、只读、未能、无法、警告和提醒等严重度；
- 仅对运行环境和持久化诊断文本生成摘要；
- 转换进度、队列暂停、任务失败、参数应用等活动状态原样显示；
- 摘要按状态控件实际宽度动态生成；
- 覆盖 80–900 像素连续宽度矩阵；
- 最窄状态区使用 `4项·详情`、`提醒·详情` 等无空格短摘要；
- 宽状态区显示主要类别及“点击查看详情”；
- 点击或右键诊断摘要可查看完整 `runtimeNotice`；
- 接管“帮助 → 诊断报告”；
- 诊断报告新增：
  - 完整运行状态；
  - 诊断类别；
  - Runtime 与 Roaming/Local 数据目录；
  - Runtime Manifest 状态；
  - FFmpeg、FFprobe、GPU 与播放器；
  - 配置和任务快照；
  - 最近崩溃记录；
- Windows 端在主 UI 线程子类化状态控件，不增加后台线程；
- self-test 与 UI 截图模式不安装接管；
- 新增 `STATUS_DIAGNOSTIC_SUMMARY_FILES_SHA256.txt` 固定清单。

### 自动验证矩阵

- 六类诊断分类；
- 信息和警告严重度；
- 80–900 像素连续宽度；
- 摘要始终保留“详情”入口；
- 单类别和多类别摘要；
- 活动任务状态保持原文；
- 完整详情包含诊断报告入口；
- Windows 源码契约包含状态控件子类化、点击详情和完整诊断；
- Windows 源码契约禁止后台 goroutine、ticker 和旧 UTF-16 API。

### 门禁发现与自纠

#### 1. 最窄宽度丢失详情入口

CI `30802567981` 发现 80 像素预算下，原摘要 `4项提醒 · 详情` 被截成省略号，详情入口消失。

改为无空格的 `4项·详情`，并对全部宽度要求摘要必须包含“详情”。

#### 2. Windows UTF-16 API 不兼容

普通测试和全量竞态通过后，CI `30802957445` 在 Windows 交叉构建发现当前 Go/Windows 目标不提供 `syscall.UTF16PtrToString`。

改为：

- 对零结尾 UTF-16 指针进行最多 32768 单元的有界扫描；
- 使用 `unsafe.Slice` 形成只读单元切片；
- 使用 `unicode/utf16.Decode` 解码；
- 源码契约明确禁止旧 API 回归。

### 证据

- PR：`#313`
- 80 像素缺陷 CI：`30802567981`
- Windows API 缺陷 CI：`30802957445`
- 最终候选：`ba8a4e07bd5ba4ec7847a25aac10717987c897fc`
- 最终 CI：`30803404778`
- 合并：`c102f8cf064a31fc01b31fac5e172f34c0919e8b`

## 当前结论

当前 `p101-exp` 已具备：

- 启动后保存条件变化时的即时可见反馈；
- 配置、会话和历史保存失败后的待保存状态与重试；
- 运行期历史补偿不覆盖损坏文件、不制造重复记录；
- 便携模式切换时当前数据具有明确权威；
- 目标旧数据先备份，源数据和非托管文件保持不变；
- 主文件、长期有效副本和瞬态恢复副本采用同一权威集合；
- 多条诊断在窄状态栏中显示可读摘要；
- 完整诊断可通过状态栏点击和诊断报告获取；
- 活动任务状态不被诊断摘要抢占；
- 正式 v4.5.0 基线保持不变。

## 提升稳定线前仍需执行

以下内容仍属于 Windows 原生稳定线门禁，不以 Linux 竞态或交叉构建替代：

- 真实 NTFS 只读 ACL；
- 运行中磁盘写满；
- 安全软件或同步软件独占配置、会话和历史文件；
- 普通模式与便携模式双向切换的真实桌面操作；
- 目标旧数据备份目录的真实路径展示；
- 状态栏 100%、125%、150%、175%、200% DPI 截图；
- 诊断摘要点击、右键和“帮助 → 诊断报告”的实际交互；
- 完整 Runtime 下的 Windows 原生竞态与退出清理。

当前不生成正式 EXE，不启动 v4.5.1，也不改变 v4.5.0 正式标签和 Release。
