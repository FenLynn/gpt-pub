# Mediova 安装与配置继承审查

## 范围边界

本审查只覆盖两类场景：

1. 全新安装后的默认行为、首次保存与再次启动；
2. 用户已有原软件配置时，对配置内容、组件路径和使用偏好的继承。

产品旧名称、目录改名和品牌迁移不再作为后续开发问题，也不再为此增加新的兼容分支。已有兼容代码保持不动，除非它实际阻断新装或原配置继承。

当前所有成果仅进入 `p101-exp`。正式 v4.5.0 标签、Release、版本号和正式 EXE 均不改变。

## 第一阶段｜原配置内容继承

### 已发现问题

早期软件构建曾以 Go 导出字段名保存配置，例如 `Resolution`、`Codec`、`Concurrency`、`UseGPU` 和 `RestoreSession`。原加载器先创建新版本默认配置，再仅在当前值为空或为零时复制旧字段，导致大量非空默认字段可能覆盖用户原有选择。

### 已实施

- 仅当配置中实际存在旧版 Go 字段名时执行一次性升级；
- 现代 snake_case 配置保持字节级不变；
- 全新安装不主动制造配置或迁移标记；
- 旧字段中的 `false`、`0`、空列表和非默认值均按明确用户选择处理；
- 混合配置中先读取现代字段，再以明确存在的旧字段为准；
- 升级前永久保留 `config.json.legacy`；
- 主配置损坏但 `.bak` 有效时，可从旧格式备份继承；
- 原版 v2.8.4 配置位于当前数据目录时直接继承，不依赖产品名称或目录改名路径；
- 新增 `INSTALL_CONFIG_FILES_SHA256.txt` 固定清单。

### 自动验证矩阵

- 纯净新装；
- 首次保存与完整回读；
- 视频、图片、队列、界面、组件、历史、通知和播放器参数继承；
- 旧配置中的 `false` 与 `0`；
- 损坏主配置从旧格式 `.bak` 继承；
- 现代配置字节级不变；
- 原版 v2.8.4 配置直接映射。

## 第二阶段第一轮｜主配置最近有效副本与恢复状态 UI

### 已发现边界

原子保存的 `.bak` 主要保护当前一次写入，成功保存后会被删除。若主配置随后因异常写入、磁盘或安全软件影响而损坏，可能没有长期有效副本。同时，配置恢复和继承曾主要在后台发生，用户难以确认本次启动是否使用恢复路径。

### 已实施

- 启动正式加载前验证 `config.json`；
- 有效主配置刷新独立 `config.json.lastgood`；
- 主配置缺失或损坏时依次尝试 `.bak` 与 `.lastgood`；
- 损坏主文件隔离为 `.corrupt`、`.corrupt.1` 等，不覆盖原证据；
- 三份均无效时明确报告，不把损坏文件伪装成默认配置；
- 全新安装无配置时不创建主配置、备份或迁移标记；
- 配置恢复、继承或目录错误进入统一启动状态；
- 状态文字合并空白并限制为 220 个字符；
- 新增 `CONFIG_RESILIENCE_FILES_SHA256.txt` 固定清单。

### 自动验证矩阵

- 新装环境无副作用；
- 有效主配置刷新最近有效副本；
- `.bak` 恢复与损坏文件隔离；
- `.lastgood` 回退；
- 有效主配置永不被旧副本覆盖；
- 无可恢复副本时保留原文件并报告；
- 启动状态空值、换行、中文和长度边界。

## 第二阶段第二轮｜FFmpeg 与播放器路径继承

### 设计原则

用户明确保存的外部组件路径属于用户配置，不应因为 Runtime 或自动检测存在而被静默覆盖。路径继承需要区分明确有效、可无歧义规范化和当前不可用三类状态。

### 已实施

- 有效 FFmpeg 或播放器文件路径原样保持权威；
- FFmpeg 目录仅在目录本身或 `bin` 子目录存在完整 FFmpeg/FFprobe 对时规范为可执行文件；
- 配置误指向同目录 `ffprobe` 时，仅在完整组件对存在时规范为 `ffmpeg`；
- PotPlayer 目录仅在实际存在播放器可执行文件时规范化；
- 无效外部路径不清空、不替换，继续保留供用户修复；
- 当前不可用时说明将尝试 Runtime、自动查找或系统默认播放器；
- 只有无歧义变化才保存配置并刷新最近有效副本；
- 新增 `COMPONENT_INHERITANCE_FILES_SHA256.txt` 固定清单。

### 自动验证矩阵

- FFmpeg 直接目录与 `bin` 子目录；
- 误存为 `ffprobe`；
- 无效 FFmpeg 路径保持原值；
- PotPlayer 目录规范化；
- FFmpeg 与播放器混合继承；
- 空路径无副作用。

## 第二阶段第三轮｜启动状态 UI 优先级

### 已发现边界

配置提示具有诊断价值，但不能覆盖转换进度、队列变化、任务失败、搁置编辑或参数应用等更高优先级实时状态。

### 已实施

- 提示分为 `配置状态` 与 `配置提醒`；
- 含未完成、不可用、异常、损坏、失败、错误或只读时作为提醒；
- 提示始终保存在运行时诊断字段中；
- 仅在状态栏为空、就绪或等待添加任务时显示；
- 转换、队列、失败、搁置和参数更新消息绝不被覆盖；
- 活动状态持续存在时主动放弃抢占；
- 保持 220 字符边界。

### 自动验证矩阵

- 信息与警告分类；
- 空值、长文本和中文截断；
- 被动状态允许展示；
- 主动状态禁止抢占；
- Windows GUI 交叉构建。

## 第二阶段第四轮｜启动提示 UI 线程并发收口

### 复核发现

第三轮的 Windows 专用展示器使用后台 goroutine 轮询全局 `app`。Linux 全量 `-race` 无法编译和执行 Windows 文件，因此“交叉构建通过”并不能证明这段全局读取具备完整并发语义。

### 已实施

- 删除后台 goroutine、全局 `app` 轮询、超时 channel 和重复延时；
- 仅在确有启动提示时，于主 goroutine初始化阶段提前锁定 OS 线程；
- 使用当前线程的 Win32 `WH_GETMESSAGE` 钩子；
- 正式消息循环第一次取消息时，在同一 UI 线程完成提示读取、诊断合并和状态栏更新；
- 完成后立即卸载钩子，不持续驻留；
- self-test 和 UI 截图模式不显示配置提示；
- 完整的“就绪。检测到……”状态被识别为被动状态；
- 已有 Runtime 提示与配置提示合并保存，不互相覆盖；
- 按 Win32 ABI 使用 `int32(code)` 判断钩子代码。

### 自动验证矩阵

- 完整就绪状态识别；
- Runtime 与配置诊断合并及去重；
- 信息、警告和长度边界继续通过；
- 固定清单同步；
- Windows 测试程序和 GUI 双交叉构建。

## 当前结论

四轮工作均已进入 `p101-exp`：

- 原配置内容中的非默认值、`false` 和 `0` 能够继承；
- 主配置具备独立最近有效副本和损坏隔离；
- 用户选择的 FFmpeg 与播放器路径保持权威；
- 可无歧义的目录型路径会规范化；
- 当前不可用的外部路径不会被擅自清空；
- 配置恢复与继承结果具备 UI 可见性；
- 启动提示不会覆盖实时任务状态；
- Windows 启动提示不再依赖后台轮询全局应用对象。

每轮均通过 P101 范围门禁、固定源码清单、Go 全测、全量竞态、`go vet`、Windows 测试程序和 GUI 双交叉构建。Windows 原生 `-race`、完整 Runtime、真实只读目录、安全软件占用和用户桌面视觉结果，仍需在提升到 `p101-stable` 前执行。

## 后续重点

后续安装和 UI 边界只继续检查：

- FFmpeg/FFprobe 缺失、不可执行或 Runtime 无写入权限时的明确降级；
- 配置目录只读、磁盘满、文件被安全软件占用或首次保存失败时，是否保护原文件并给出稳定诊断；
- 配置、会话和历史文件同时存在时的读取顺序、故障隔离和互不覆盖；
- 便携模式与普通模式切换时，用户数据位置和组件路径是否保持可解释；
- 状态栏提示、底部按钮和窄窗口之间的空间预算与视觉层级；
- 不再扩展产品改名或目录改名兼容。

当前不生成正式 EXE，不启动 v4.5.1，也不改变 v4.5.0 正式基线。
