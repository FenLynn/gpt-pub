# Mediova 软件开发总结

## 产品起点与目标

Mediova 最初围绕一个非常直接的实际需求展开：把手机、相机和其他来源的视频自动转正，并在一次处理中完成分辨率调整、编码和压缩。随着真实使用中不断出现批量文件、不同方向信息、4K MOV、复杂音视频轨道、字幕、可变帧率、大量图片、GPU 差异和 Windows 界面适配问题，软件逐步从单一“视频转正器”发展为本地媒体批处理与创作工作站。

产品始终坚持本地处理，不上传用户媒体，不修改或删除源文件。软件的核心价值不是简单包装 FFmpeg，而是把探测、任务组织、兼容判断、输出占用、失败恢复、真实结果校验和 Windows 桌面交互组成一个可靠闭环，让用户可以把一批媒体交给软件处理，而不必逐个检查命令行参数和异常结果。

## 功能能力的形成

早期版本建立了视频文件和文件夹导入、递归扫描、方向识别、90°/270°转正、分辨率调整和 H.265 输出。随后加入图片处理、JPG/PNG 支持、最大边长、质量档位、目标码率和目标体积，并形成“统一设置加单任务覆盖”的参数模型。任务可以批量跟随全局设置，也可以对单个或多选项目进行覆盖，避免为了少数特殊文件拆分整个批次。

视频处理链逐渐扩展到多音轨、文本字幕、位图字幕、VFR 和手机 MOV 等复杂输入。对无法安全直接复制的流不采用盲目封装，而是先判断兼容性，再选择保留、转换、忽略或明确失败。软件还建立了源文件、输出文件和 PotPlayer 对比入口，方便在压缩后快速检查画质和媒体完整性。

裁剪能力已经建立基础入口，包括时长裁剪和画面区域裁剪。当前链路可以参与正式转换，但时间轴定位、预览反馈和批量裁剪交互仍属于后续重点优化方向。视频分段、无损拼接、合并、轨道选择和字幕编辑尚未完成，已经作为后续媒体工作流扩展计划保留。

## 性能与任务系统演进

软件早期暴露过拖入文件闪退、解码器检测停滞、4K 预览卡顿、大量图片扫描阻塞、并发任务互相影响以及失败任务状态不闭合等问题。后续没有通过删减功能或降低并发简单规避，而是逐步建立独立的媒体探测、缩略图、扫描和转换工作池，使用动态逻辑处理器并发，限制容易造成资源争抢的后台任务数量，并对界面刷新和进度更新进行节流。

输出管理增加了同名文件原子占用，避免并发任务同时写入相同目标。任务只有在输出真实存在并通过最低完整性检查后才能记为成功；启动失败、进程失败、输出缺失、输出过小、恢复失败等情况必须形成明确失败结果。每个输入都要进入准备、队列、转换、暂停、完成或失败等可识别状态，不能静默消失，也不能因为批处理结束就默认全部成功。

硬件编码方面，软件可以检测 NVIDIA NVENC、Intel QSV 和 AMD AMF，并允许硬件优先。硬件编码不可用或实际执行失败时，任务会自动回退到 CPU，而不是让整个批次中断。并行任务数可以配置，默认以多核桌面环境为主要使用场景，同时保留大批量任务保护，避免探测、缩略图和编码同时无上限扩张。

## 界面发展

界面经历了多轮重构。顶部操作逐步收拢为严格单行工具栏，搜索和状态筛选不能因窗口宽度变化掉到下一行。底部区域把总进度、任务数量、百分比、耗时、预计剩余时间、暂停状态和失败数量整合到完整进度条及其相邻操作区，避免文字、按钮和进度条互相覆盖。

任务列表中的结果表达也被重新设计。行内进度使用完整条形区域并在内部显示文字；体积变化不是简单显示一个百分比，而是按原始体积和输出体积的比例表达，压缩变小时使用正向提示，体积变大时使用警示提示，小幅变化保持中性。标题、列边界、按钮尺寸、悬浮说明和多选操作经过多轮统一。

窗口适配覆盖了 100%–175% DPI、不同宽度和高度、最大化与还原、多行状态区及较小屏幕。开发中曾多次出现缩放后文字重叠、按钮越界、搜索区换行、转换按钮与进度条冲突等问题，因此后续界面修改不能只在单一截图尺寸下通过，必须验证多种窗口尺寸和 DPI。

## 稳定性与验证体系

为了减少依赖用户反复人工验证，项目逐步建立了自动测试、故障注入和 Windows 原生自检。测试覆盖配置并发、历史追加、批量扫描、FFmpeg 探测超时、媒体流兼容、输出完整性、任务包、导入导出、同名任务、硬件检测和恢复链路。构建时使用独立临时数据目录，避免上一轮测试历史污染下一轮结果。

长期 CI 会校验源码逐文件 SHA-256，执行 Go 全量测试、关键包竞态检测和 `go vet`，在 Linux 上交叉构建 Windows 测试程序和 GUI，并在 Windows Runner 上生成正式资源版 EXE。Windows 验证使用真实 FFmpeg 与 FFprobe，启动正式 EXE 运行原生自检。Mediova v4.0.0 的正式发布自检为 57/57，通过后才建立标签和 Release。

这些自动化并不意味着完全取消真实 Windows 冒烟测试。拖放、托盘、多显示器、显卡驱动、播放器路径、窗口焦点、文件时间和特殊媒体样本仍然具有环境依赖，但用户不应再承担主要回归测试。开发者必须先生成测试媒体、运行自动化和自检，再把少量无法自动覆盖的交互交给真实环境确认。

## 从旧产品到 Mediova v4.0.0

v2.x 阶段主要完成批量处理、参数设置、GPU、目标体积和界面结构；v3.x 阶段重点补强复杂媒体、任务闭环、大批量性能、DPI、恢复和自动验证。v3.9.4 成为品牌迁移前的稳定能力基线。v4.0.0 没有重写成熟内部格式，而是完成对外产品名称、窗口、托盘、关于、诊断、Windows 资源、构建产物和数据目录的统一。

新数据目录使用 `%APPDATA%\Mediova`、`%LOCALAPPDATA%\Mediova` 和便携目录 `MediovaData`。首次运行时，仅当新位置缺少对应数据时，才从旧 VideoUpright 目录复制；旧目录不会删除，已经存在的新文件不会覆盖。配置结构、任务包和内部 Go module 保持兼容，从而避免仅为改名制造无价值的数据破坏。

Mediova v4.0.0 已迁入 GPT-Pub 的 `projects/1-桌面软件/101-Mediova/`，通过公开边界检查、源码哈希、Go 测试、竞态检测、`go vet`、Windows 构建、真实 FFmpeg 和原生自检。正式 EXE 为 `Mediova_v4.0.0.exe`，大小 3,737,088 字节，SHA-256 为 `8598af6b5e999ba29f5a6f02df16f4ebb2a3801b240c3d627429709ae7828423`。标签与 Release 为 `p101-v4.0.0`。

私有旧仓库已经停止 Mediova 的 CI、开发和发布，仅保留源码和 Git 历史作为只读档案。此后所有 Mediova 需求、代码、测试、PR、标签和 Release 都只在 GPT-Pub P101 中维护。

## 当前阶段与后续方向

当前基线已经具备可持续迭代条件。近期首先应根据真实 Windows 使用结果处理 v4.0.x 稳定性问题，然后继续完善右键菜单、裁剪时间轴、文件级暂停恢复、HEIC/HEIF、手机 MOV、HDR、轨道选择和字幕封装。更后的完整工作流包括视频分段、无损拼接和合并。

后续每轮开发都应先更新 `工作记录.md`，按 `p101-exp → p101-stable → main` 推进，经过相应测试后再建立正式标签与 Release。重大架构、兼容策略、默认行为或验证门槛发生变化时，应同步更新本总结和 `开发约束.md`，保证新对话不需要依赖旧聊天记录才能继续工作。
