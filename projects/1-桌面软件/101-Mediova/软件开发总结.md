# Mediova 软件开发总结

## 产品起点与长期目标

Mediova 起源于一个直接的工程需求：自动识别手机、相机和其他来源视频的方向，在一次处理中完成转正、分辨率调整、编码和压缩。随着真实使用中持续出现批量文件、4K MOV、复杂音视频轨道、字幕、VFR、大量图片、GPU 差异、文件时间保留和 Windows 界面适配问题，软件逐步从单一“视频转正器”演进为本地媒体批处理与创作工作站。

产品始终坚持本地处理，不上传用户媒体，不修改或删除源文件。Mediova 的核心价值不是简单包装 FFmpeg，而是把媒体探测、任务组织、参数管理、兼容判断、输出占用、失败恢复、真实结果校验和 Windows 桌面交互组成可靠闭环，使整批媒体可以被安全交给软件处理。

## 功能能力的形成

早期版本建立了文件与文件夹导入、递归扫描、方向识别、90°/270°转正、分辨率调整和 H.265 输出。随后加入图片处理、JPG/PNG、最大边长、质量档位、目标码率和目标体积，并形成“全局默认加单任务覆盖”的参数模型。

视频处理链逐渐扩展到多音轨、文本字幕、位图字幕、VFR 和手机 MOV。软件不盲目复制全部媒体流，而是先判断目标封装与编码兼容性，再选择保留、转换、忽略或明确失败。源文件、输出文件和 PotPlayer 对比入口用于压缩后快速检查画质与媒体完整性。

裁剪已建立时长裁剪和画面区域裁剪的基础入口。时间轴定位、预览反馈、批量裁剪、视频分段、无损拼接、合并、轨道选择和字幕编辑仍属于后续方向，不通过删除计划制造“全部完成”。

## 性能、并发与结果闭环

软件早期曾出现拖入文件闪退、解码器检测停滞、4K 预览卡顿、大量图片扫描阻塞、并发任务互相影响和失败状态不闭合等问题。后续没有通过删减功能或机械降低并发规避，而是建立相互独立且有上限的扫描、媒体探测、缩略图和转换工作池，并对界面刷新和进度更新节流。

输出管理加入同名文件原子占用，防止并发任务写入同一目标。任务只有在输出真实存在并通过最低完整性检查后才能记为成功；启动失败、进程失败、输出缺失、输出异常过小、恢复失败和验证失败必须形成明确结果。临时文件与正式输出必须可区分、可清理。

硬件编码支持 NVIDIA NVENC、Intel QSV 和 AMD AMF 检测。硬件编码不可用或执行失败时安全回退 CPU，而不是使整个批次失效。任何并发扩展仍须服从内存、磁盘、探测和界面响应边界。

## 界面演进与视觉验证

界面经历了多轮重构。顶部操作逐步收拢为严格单行工具栏，搜索、状态筛选和状态灯不能因窗口宽度变化掉到下一行。底部区域把输出母目录、批量参数、总进度、任务数量、耗时、预计剩余和开始、暂停、停止操作组织成稳定横向结构，避免文字、按钮和进度条互相覆盖。

v4.1.0 完成统一背景、自绘按钮状态、输出母目录、真实体积比例和压缩颜色逻辑，但正式 EXE 与截图复核证明，代码和几何测试通过不等于视觉已经兑现。v4.1.1 因此重构默认表面规则：普通工具栏和次要按钮默认不再使用浅色卡片底，悬停、按下、当前模式和禁用状态分层；图标、间距、状态灯、折叠按钮和下拉框边线同步统一。

进度和压缩体积条采用单层绘制。体积条按输入体积与输出体积之和显示真实左右比例；变化在 ±10% 内或输出变大但最终小于 15 MB 时黄色优先，明显压缩为分级绿色，明显增长为分级红色。该业务含义通过独立逻辑和测试固定，界面重构不得随意改变。

v4.1.1 将“存在截图”升级为“真实窗口尺寸正确并经过人工复核”。首轮自动截图曾出现画布尺寸正确但实际窗口被系统夹窄、右侧和下方形成黑区的问题，人工复核阻止了误合并。随后 CI 使用 `GetWindowRect` 建立实际尺寸门禁，并生成真正不同的宽屏与紧凑布局截图。

v4.2.0 在此基础上把截图矩阵扩展为视频宽屏、视频紧凑、图片模式和搁置模式四种真实窗口场景。长期 UI 准入由规则测试、几何测试、真实 EXE 截图和人工复核共同组成，任何一层都不能替代其他层。

## 从单 EXE 到轻量透明 Runtime

v4.0.0 的主程序是单 EXE，但 FFmpeg/FFprobe 和相关 DLL 会进入 AppData，使可公开、可替换的运行组件与私人配置、历史、缓存和本机状态混在一起。随着组件增加，这种结构会使更新、故障诊断和公开发布边界越来越不清晰。

v4.1.0 因此采用“轻量透明 Runtime + 独立 Data”，同时保留一个直接启动的主程序：

```text
Mediova/
├── Mediova.exe
├── Components/
│   └── FFmpeg/
│       └── bin/
├── runtime-manifest.json
├── THIRD_PARTY_NOTICES.md
└── README.txt
```

Runtime 保存可公开、可替换、可校验、可删除后重建的程序和组件；`%APPDATA%\Mediova` 保存配置、历史、会话和备份；`%LOCALAPPDATA%\Mediova` 保存缓存、临时文件、缩略图、本机状态和崩溃信息。Mediova 不增加自释放启动器、后台服务、安装数据库或无必要宿主层。

旧组件迁移坚持“只复制缺失文件、不覆盖新 Runtime、不删除旧目录”。只有 Runtime 缺少有效组件时才从旧 AppData 保守复制，并在复制后验证 `ffmpeg.exe`、`ffprobe.exe` 和必要依赖。用户明确选择的系统路径、外部目录或自定义组件路径保持权威。

## v4.2.0：从批次表单到可编辑队列

v4.2.0 的核心不是增加一种媒体格式，而是重构任务状态机。此前“全局设置、个体设置、等待队列和正在转换”之间边界不够清楚，长时间批处理中继续导入、修改和追加任务容易互相影响。新模型明确区分准备中、队列中、转换中、暂停、搁置待修改、完成和失败。

视频与图片分别保存输出母目录、最近目录和默认参数。文件夹导入按照导入根目录计算相对路径，并在输出母目录下复刻原目录树。切换媒体模式时，输出目录、底部参数、右侧参数和默认值同步切换。

底部参数是当前模式的全局默认控制器和新任务模板，字段变化只立即影响同模式准备中任务。右侧个体编辑使用草稿与显式应用，多选时只提交用户实际修改的字段。任务进入队列的瞬间冻结转换参数、输出目录、完整输出路径、冲突策略和必要运行快照，后续默认变化不得改写已入队任务。

活动队列运行期间可以继续导入、编辑并动态追加同类型任务，新任务独立执行输出冲突和磁盘空间预检，不中断正在转换的任务。同一活动队列只运行一种媒体，另一模式仍可继续准备。

队列中、转换中和暂停任务默认锁定。单个锁定任务可以进入独立搁置会话修改参数，多选锁定任务只允许安全移除。转换任务搁置时安全终止 FFmpeg、等待退出、清理本次临时输出并保留并发名额；应用新参数或取消修改后均从 0% 重启，不伪装断点续转。“从任务列表移除”不删除源文件，也不误删已经完成的正式输出。

动态追加后，总任务数、完成数和百分比按真实分母重新计算。百分比允许下降，但必须同时显示“已完成 x/y”，不能维持虚假的旧进度。

## 验证体系升级

项目持续减少对用户人工回归的依赖。长期 CI 校验源码逐文件 SHA-256，执行 Go 全量测试、全量竞态和 `go vet`，并完成 Windows 测试程序与 GUI 交叉构建。

Windows 验证使用独立的 `APPDATA`、`LOCALAPPDATA`、`XDG_CONFIG_HOME` 和 Runtime 根目录，从固定公开通道获取真实 FFmpeg/FFprobe，构建完整 Runtime ZIP，逐文件验证 manifest，并扫描私人 Data 泄漏。随后启动正式 `Mediova.exe` 执行原生自检。

v4.2.0 正式 CI `30740707877` 通过 Linux 与 Windows 原生全测、全量竞态、`go vet`、真实 FFmpeg Runtime、四套 UI 截图和 61/61 原生自检。测试覆盖输出相对目录树、动态追加队列、同名并发、复杂轨道、VFR 和完整性故障注入。正式标签为 `p101-v4.2.0`，Release 运行编号为 `30740967788`。

自动化并不等于完全取消真实 Windows 观察。拖放、托盘、多显示器、显卡驱动、PotPlayer、窗口焦点、特殊媒体、文件时间和 125%～175% DPI 仍有环境依赖，但用户不应承担基础功能测试；开发者必须先完成自动测试、正式构建、自检和截图复核。

## 版本脉络

- v2.x：形成批量处理、基本参数、GPU、目标体积和界面结构；
- v3.x：扩展复杂媒体、任务闭环、大批量性能、DPI、恢复和自动验证；
- v3.9.4：品牌迁移前的稳定能力基线；
- v4.0.0：统一 Mediova 品牌、数据目录和公开开发主线；
- v4.1.0：完成轻量透明 Runtime/Data 分离、输出母目录、真实压缩比例和 UI 自绘逻辑基础；
- v4.1.1：纠正未完成的视觉兑现，建立真实窗口尺寸门禁和人工视觉复核；
- v4.2.0：完成视频与图片双参数体系、输出相对目录树、入队冻结、动态追加队列、搁置修改和安全移除。

## 当前阶段与后续方向

当前正式版本为 v4.2.0。发布后的重点是收集真实桌面反馈，确认高 DPI、多显示器、显卡驱动、拖放、托盘、PotPlayer 和特殊媒体边界。下一版本不得只因版本号递增而启动，必须先形成可复现问题、明确目标和完成标准。

后续功能仍以真实需求为准，包括裁剪时间轴、文件级暂停恢复、HEIC/HEIF、HDR、轨道选择、字幕封装、视频分段以及无损拼接与合并。任何新组件必须服从 Runtime/Data 边界；任何任务模型修改不得破坏 v4.2.0 已固化的准备中编辑、入队冻结、动态追加和安全搁置语义。

每轮开发必须先更新 `工作记录.md`，按 `p101-exp → p101-stable → main` 推进。重大架构、兼容策略、默认行为、第三方组件或验证门槛发生变化时，应同步更新本总结与 `开发约束.md`，保证新对话不依赖旧聊天记录也能继续工作。
