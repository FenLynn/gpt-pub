# Mediova 软件开发总结

## 产品起点与长期目标

Mediova 最初来自一个直接的工程需求：让手机、相机和其他来源的视频能够自动识别方向并转正，同时在一次处理中完成分辨率调整、编码和压缩。随着真实使用中不断出现批量文件、4K MOV、复杂音视频轨道、字幕、可变帧率、大量图片、GPU 差异、文件时间保留和 Windows 界面适配问题，软件逐步从单一“视频转正器”发展为本地媒体批处理与创作工作站。

产品始终坚持本地处理，不上传用户媒体，不修改或删除源文件。Mediova 的核心价值不是简单包装 FFmpeg，而是把媒体探测、任务组织、兼容判断、输出占用、失败恢复、真实结果校验和 Windows 桌面交互组成可靠闭环，使用户能够把整批媒体交给软件处理，而不必逐个编写命令或人工确认每一个异常状态。

## 功能能力的形成

早期版本建立了视频文件和文件夹导入、递归扫描、方向识别、90°/270°转正、分辨率调整和 H.265 输出。随后加入图片处理、JPG/PNG、最大边长、质量档位、目标码率和目标体积，并形成“统一设置加单任务覆盖”的参数模型。批次可以跟随全局设置，单个或多选任务也可以独立覆盖，避免为了少数特殊文件拆分整个任务队列。

视频处理链逐渐扩展到多音轨、文本字幕、位图字幕、VFR 和手机 MOV。软件不盲目复制所有媒体流，而是先判断目标封装和编码兼容性，再选择保留、转换、忽略或明确失败。源文件、输出文件和 PotPlayer 对比入口也逐步建立，用于压缩后快速检查画质与媒体完整性。

裁剪能力已经建立基础入口，包括时长裁剪和画面区域裁剪。当前链路可以参与正式转换，但时间轴定位、预览反馈和批量裁剪仍属于后续优化方向。视频分段、无损拼接、合并、轨道选择和字幕编辑尚未完成，继续保留在工作记录中，不通过删除计划制造“全部完成”。

## 性能、任务与结果闭环

软件早期曾出现拖入文件闪退、解码器检测停滞、4K 预览卡顿、大量图片扫描阻塞、并发任务互相影响以及失败状态不闭合等问题。后续没有通过删减功能或机械降低并发规避，而是建立独立的扫描、媒体探测、缩略图和转换工作池，根据逻辑处理器数量调度，同时限制高开销后台任务数量，并对界面刷新和进度更新进行节流。

输出管理加入同名文件原子占用，防止并发任务写入同一目标。任务只有在输出真实存在并通过最低完整性检查后才能记为成功；启动失败、进程失败、输出缺失、输出异常过小、恢复失败和验证失败必须形成明确结果。每个输入都必须进入准备、队列、转换、暂停、完成或失败等可识别状态，不能静默消失，也不能在批处理结束时被默认判定为成功。

硬件编码支持 NVIDIA NVENC、Intel QSV 和 AMD AMF 检测。硬件编码不可用或执行失败时，任务可以安全回退 CPU，而不是使整个批次失效。并行数量可以配置，但任何并发扩展都必须继续服从内存、磁盘、探测和界面响应边界。

## 界面演进与 v4.1.0 统一

界面经历了多轮重构。顶部操作逐步收拢为严格单行工具栏，搜索、状态筛选和状态灯不能因窗口宽度变化掉到下一行。底部区域把输出母目录、批量参数、总进度、任务数量、耗时、预计剩余和开始/暂停/停止操作组织成稳定的横向结构，避免文字、按钮和进度条互相覆盖。

v4.1.0 对界面视觉进行了集中统一，而不是继续逐个控件打补丁。主界面采用统一底色，普通区域依靠间距和极淡分隔线组织，不再层层套卡片、白块和厚重边框。顶部图标缩小，按钮默认透明并保留淡边线，悬停、按下、选中和禁用状态使用统一规则。状态灯放大到接近文字高度，折叠按钮缩小，右侧参数区和底部参数栏采用同一套控件语言。

输出目录区域升级为“输出母目录”，支持可编辑地址、最近使用目录、浏览选择和直接打开当前目录。最近目录会去重并限制数量，避免配置无限增长。底部下拉框不再机械等宽，而是根据常用内容和可用空间分别确定宽度。

任务进度和压缩体积条改为单层绘制。未完成区域只保留极淡背景，文字在完整条形区域内水平、垂直居中，不再套入额外小框。体积条按照输入体积与输出体积之和计算左右真实比例，例如输出为输入的 103.7% 时，两侧应接近 49.1:50.9，而不是把 103.7% 当作进度宽度。

压缩颜色规则固定为黄色优先：变化在 ±10% 内显示黄色；输出虽然变大但最终仍小于 15 MB，也显示黄色。明显压缩使用绿色，压缩越多颜色越深；明显增长使用红色，增长越多颜色越深。该规则已经从视觉口头要求固化为独立逻辑和自动测试，避免后续界面重构再次偏离。

## 从单 EXE 到轻量透明 Runtime

v4.0.0 的主程序是单 EXE，但完整运行环境并不是真正只有一个文件。用户导入 FFmpeg ZIP 后，`ffmpeg.exe`、`ffprobe.exe` 和相关 DLL 会进入 `%LOCALAPPDATA%\Mediova`。这使“可公开、可替换、可重新下载的运行组件”与“私人配置、历史、缓存和本机状态”混在同一个 Data 根目录中。

这种混合在早期功能较少时可以接受，但随着未来可能增加 HEIC/HEIF、HDR、字幕、媒体分析和辅助进程，继续把运行组件放入 AppData 会带来三个问题：用户难以判断哪些文件可以删除或覆盖；更新包和故障诊断无法清晰区分程序损坏与 Data 损坏；公开发布边界容易与私人数据边界混淆。

因此 v4.1.0 采用“轻量透明 Runtime + 独立 Data”架构，同时保留单一主 EXE，不照搬多组件工作台的全部复杂度：

```text
Mediova/
├── Mediova.exe
├── Components/
│   └── FFmpeg/
│       └── bin/
├── runtime-manifest.json
├── THIRD_PARTY_NOTICES.md
└── README.txt
```

Runtime 是公开、可替换、可校验、可删除后重建的程序文件集合。Data 仍分为：

```text
%APPDATA%\Mediova       # 配置、历史、会话、备份
%LOCALAPPDATA%\Mediova  # 缓存、临时文件、缩略图、本机状态和崩溃信息
```

Mediova 没有增加启动器、后台服务、安装数据库或无必要的 DLL 拆分。图标、界面和稳定的 Go 逻辑仍嵌入 `Mediova.exe`；只有真实外部运行依赖进入 `Components`。这使架构足以支持未来扩展，又不会为了形式统一而把轻量工具改造成复杂平台。

## Runtime 架构标准与必要性

Mediova 的 Runtime/Data 分离遵循以下标准：

1. **按可替换性分类，而不是按文件类型分类。** 可从发布包恢复的程序、组件和公开资源进入 Runtime；用户产生或机器产生的私人状态进入 Data。
2. **Runtime 可整体公开和覆盖。** Runtime 包不能包含配置、历史、日志、缓存、私人路径、真实媒体或凭据。
3. **Data 不承载正式运行组件。** `ffmpeg.exe`、`ffprobe.exe` 和 DLL 不再作为 Data 安装到 AppData。
4. **一个真实主程序。** `Mediova.exe` 直接启动，不增加自释放启动器，也不在启动时把 Runtime 重新复制到 Data。
5. **逐文件可验证。** `runtime-manifest.json` 记录产品、版本、平台、部署形态、文件大小和 SHA-256；正式 CI 逐文件复核。
6. **第三方边界透明。** Runtime 包含 `THIRD_PARTY_NOTICES.md`，说明 FFmpeg 来源、许可证和运行时分发边界。
7. **迁移只复制。** Runtime 缺少有效组件时才从旧 AppData 复制；不删除旧目录，不覆盖已存在的新组件。
8. **用户选择优先。** 只有旧 AppData 组件路径会在 Runtime 有效时归一化；用户明确指定的外部 FFmpeg 路径继续保持权威。
9. **完整包优先。** 架构变化版本交付完整 Runtime ZIP；后续只有单个公开运行文件变化时才允许按原相对路径提供增量更新。

这次分离的必要性不是追求“文件夹版比单 EXE 高级”，而是建立长期可维护的运行边界。只有边界明确，后续组件扩展、增量更新、完整性检查、故障恢复和公开发布才不会继续依赖隐式 AppData 状态。

## 兼容迁移

v4.0.0 已把旧 VideoUpright 数据保守复制到 Mediova 数据目录。v4.1.0 进一步处理旧 FFmpeg 组件：如果新 Runtime 已有有效 `ffmpeg.exe` 与 `ffprobe.exe`，不执行迁移；如果 Runtime 缺失而旧 AppData 组件完整，则只复制缺失文件；复制后验证组件对是否存在。旧组件不会删除，新 Runtime 文件不会覆盖。

配置中若仍指向旧 AppData 组件，在 Runtime 有效时会自动转为 Runtime 路径。用户明确选择的系统 FFmpeg、其他文件夹或自定义构建不会被强制改写。这样既能完成官方架构迁移，也不破坏高级用户已有部署。

## 验证体系升级

项目持续减少对用户人工回归的依赖。长期 CI 校验源码逐文件 SHA-256，执行 Go 全量测试、关键包竞态检测和 `go vet`，并在 Linux 上交叉构建 Windows 测试程序与 GUI。

v4.1.0 的 Windows 验证增加了四项硬门槛：每次普通测试和竞态测试分别使用独立的 `APPDATA`、`LOCALAPPDATA`、`XDG_CONFIG_HOME` 和 Runtime 根目录；从公开 GitHub Release 获取真实 FFmpeg/FFprobe；构建完整 Runtime ZIP；逐文件验证 Runtime 清单并扫描私人 Data 泄漏。随后启动正式 `Mediova.exe` 执行原生自检，自检项不得少于现有 57 项基线。

实现阶段可观察 Windows 运行已经通过 Go 全测、竞态、`go vet`、真实 FFmpeg、完整 Runtime 构建、清单校验和原生自检。实现阶段主 EXE SHA-256 为 `9d6cc313182e7804d4117677a3bae033b84ab163690b80acf50302884178bb8b`，Runtime ZIP SHA-256 为 `26ee217c1eeabd66ba0adf4078459ebb73b3093101d696b95eeceac36ae4c74f`。正式 Release 会从最终 `main` 准入产物重新固定运行编号和最终哈希。

自动化并不等于完全取消真实 Windows 冒烟测试。拖放、托盘、多显示器、显卡驱动、PotPlayer、窗口焦点、特殊媒体和文件时间仍有环境依赖，但用户不应承担主要测试。开发者必须先完成自动测试、正式构建和自检，再把少量环境相关交互交给真实使用观察。

## 版本脉络

- v2.x：批量处理、基本参数、GPU、目标体积和界面结构；
- v3.x：复杂媒体、任务闭环、大批量性能、DPI、恢复和自动验证；
- v3.9.4：品牌迁移前的稳定能力基线；
- v4.0.0：统一 Mediova 品牌、数据目录和公开开发主线；
- v4.1.0：完成界面视觉统一、真实压缩条规则、输出母目录交互，以及轻量透明 Runtime/Data 分离。

## 当前阶段与后续方向

v4.1.0 产品实现和首轮 Windows 原生验证已经完成，当前进入稳定候选晋级、最终主线准入和正式 Release。正式发布后，近期重点是观察不同 Windows 10/11、DPI、多显示器、显卡驱动、播放器和真实媒体样本，必要时发布 v4.1.x 补丁。

后续功能仍按工作记录推进：右键菜单、裁剪时间轴、文件级暂停恢复、HEIC/HEIF、手机 MOV、HDR、轨道选择、字幕封装、视频分段以及无损拼接与合并。任何新组件必须服从 Runtime/Data 边界，不得重新把可公开运行文件写回 AppData。

后续每轮开发必须先更新 `工作记录.md`，按 `p101-exp → p101-stable → main` 推进。重大架构、兼容策略、默认行为、第三方组件或验证门槛发生变化时，应同步更新本总结与 `开发约束.md`，保证新对话不依赖旧聊天记录也能继续工作。
