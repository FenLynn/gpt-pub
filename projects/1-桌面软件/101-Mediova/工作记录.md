竖屏显示器不列为当前像素级正式验收场景。当前自适应优先级为常见横屏窗口、最大化与还原、100%–175% DPI、多显示器切换和窄窗口降级；竖屏只要求程序不崩溃、不出现阻断操作的严重遮挡。

## 第二阶段恢复协议审查

### 已发现问题

v4.5.0 的恢复协议要求完成、跳过和失败结果保持原状态，但原实现先检查源文件是否存在，再判断任务是否已经处于终态。因此，用户在处理完成后移动或删除源文件时，历史上的完成、跳过或失败记录会被错误改写为“源文件缺失失败”，同时丢失原输出路径、失败原因或校验信息。

### 修复原则

- `转换完成`、`已跳过` 和 `失败`属于历史结果，恢复时优先计数并原样保留；
- 不因为源文件后来移动或删除而改写终态结果；
- `准备中`、`队列中`、`转换中`、`已暂停`、`搁置` 和 `已停止`仍需要重新执行，因此继续检查源文件是否存在；
- 非终态任务源文件缺失时，仍明确标记为“源文件缺失”，并清除临时输出、进度、引擎和运行时间；
- 不放宽文件级从 0% 重新处理、源文件保护或结果完整性规则。

### 回归覆盖与证据

- 修复 PR：`#289`；

- 新增三类终态源文件均已移动时的完整保留测试；
- 新增非终态源文件缺失仍明确失败的反向测试；
- 一次性验证运行：`30784887518`；

## 第三阶段会话与进程韧性审查

### 已发现问题

- 会话原子保存先把现有 `session.json` 移至 `.bak`，再把完整 `.tmp` 移为新的主快照。若程序或系统恰好在两次改名之间中断，主快照会短暂缺失；原加载逻辑看到主文件不存在后直接返回，无法利用已经写完的 `.tmp` 或有效 `.bak`；
- `ProcessController.Pause()` 与 `Resume()` 原先只在锁内更新逻辑状态，实际挂起或恢复 FFmpeg 的系统调用在锁外执行。并发暂停、恢复或“暂停状态下新进程登记”可能发生操作穿越，导致界面显示已恢复而实际子进程仍被挂起。

### 修复原则

- Windows 启动、正式加载会话之前先检查主快照；主文件存在时绝不覆盖；
- 主文件缺失时，优先验证并恢复已完整写入的 `.tmp`；`.tmp` 无效或不存在时再恢复有效 `.bak`；
- 恢复主快照仍采用写入、同步和改名链，不直接覆盖半成品；
- 暂停状态、进程登记和实际 suspend/resume 系统信号统一串行化，保证最后完成的控制操作与真实 FFmpeg 进程状态一致；
- 不改变会话 schema、任务参数、正式版本号或媒体处理结果。

### 回归覆盖与证据

- 修复 PR：`#291`；
- 修复分支：`p101-preflight-resilience`；
- 新增 5 项主快照自愈矩阵：完整 `.tmp` 优先、仅 `.bak` 恢复、无效 `.tmp` 回退 `.bak`、已有主文件不覆盖、三者均不存在时不制造文件；
- 新增 2 项确定性进程竞态测试：恢复不得穿越尚未完成的暂停；恢复不得穿越暂停状态下的新进程登记；
- 新增 1200 项队列交叉压力测试，覆盖冻结、排队、转换、暂停、搁置、参数应用、取消修改和停止返回准备状态，并核对冻结序号与参数不漂移；
- 固定源码 SHA-256、Go 全测、全量竞态、`go vet`、Windows 测试程序交叉构建和 Windows GUI 交叉构建均通过；

## 后续更新计划

### 当前预备工作的下一阶段

在不启动正式版本的前提下，继续扩充可自动闭环的稳定性证据：

- 建立受控测试媒体样本，覆盖方向元数据、横竖画面、VFR、多音轨、字幕、特殊文件名、损坏文件和现代图片输入；
- 检查 FFmpeg/FFprobe 超时取消后的子进程、句柄、管道和临时文件清理，避免只验证函数返回而遗漏资源残留；
- 扩大动态追加、删除、重试、输出路径冲突和恢复交叉发生的长队列测试；
- 在具备 Windows 原生运行条件时补做启动前会话自愈、暂停/恢复和多 DPI 的真实进程与桌面验证；
- 只登记能够由自动证据证明的问题，不把尚未实机确认的视觉猜测直接写成修复。

### v4.5.1｜仅限稳定性热修

只有出现明确、可复现且不适合等待大版本的问题时才启动，例如：

- 特定 DPI、主题或窗口尺寸下仍出现控件错位；
- 会话快照在真实异常退出场景中出现恢复遗漏；
- 某类 HEIC/HEIF/AVIF 或复杂媒体产生错误分类或静默失败；
- 托盘、拖放、显卡驱动或外部播放器集成出现阻断性问题。

不得把功能扩张混入 v4.5.1。当前实验自适应增强、恢复协议修复和会话/进程韧性增强不自动等同于启动 v4.5.1；只有形成明确问题集合、版本范围和正式验收标准后再决定版本归属。

### v4.6.0｜队列可观测性与重试闭环

建议作为下一主版本候选，先做设计和样本验证，再决定是否实施：

- 失败任务按原因筛选、批量重新预检和安全重试；
- 任务历史与当前队列更清楚地区分；
- 可导出精简处理报告，记录输入、输出、参数、引擎、耗时、校验和失败原因；
- 恢复摘要、动态追加、剩余任务和队列健康状态更易理解；
- 不增加复杂账户、数据库或云同步系统。

### v4.7.0｜预览效率与批量编辑

在 v4.6.0 稳定后再评估：

- 更低成本的时间轴缩略图或关键帧导航；
- 裁剪预设管理和更清晰的批量差异提示；
- 大图片与 4K 视频预览的缓存预算、取消和回收策略；
- 保持单一预览系统，不引入第二套渲染架构。

### v5.0.0｜只在真正架构变化时启动

只有现有任务、配置或 Runtime 模型无法承载明确需求时才考虑，例如跨机器可迁移任务包、插件边界或全新的处理图模型。不得仅为“升大版本”重写稳定的 Win32、队列或 FFmpeg 管线。

## 启动下一版本的前置条件

新版本开始前必须写清：

1. 可复现问题或明确用户价值；
2. 不做会造成什么实际损失；
3. 最小实现范围和不做范围；
4. 配置、会话、任务和 Runtime 的兼容边界；
5. 自动测试、真实 Windows 截图、原生自检和用户实机验证标准。

若没有满足这些条件的事项，v4.5.0 保持为当前正式稳定基线。
