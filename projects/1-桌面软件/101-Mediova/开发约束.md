# Mediova 开发约束

本文件是 Mediova 后续开发、修复、测试、发布和新对话接续的强制约束。任何自动化代理或新建对话在修改代码前，应先阅读本文件，再阅读 `软件开发总结.md` 和 `工作记录.md`。

## 1. 项目身份与责任边界

- 产品名称：**Mediova**。
- 项目编号：P101。
- 正式路径：`projects/1-桌面软件/101-Mediova/`。
- 技术栈：Go、原生 Win32、FFmpeg/FFprobe、Windows x64。
- 当前正式版本：v4.0.0。
- 当前唯一开发仓库：`FenLynn/gpt-pub`。
- 私有旧仓库只保留只读源码与 Git 历史，不得恢复第二条 Mediova 开发主线。
- P101 开发只能修改 P101 目录、P101 长期 CI，以及共享目录中与 P101 状态直接相关的最小内容。
- **不得修改 AtlasDesk 的产品目录、源码、CI、分支、版本记录、发布记录或计划。**
- 不得把 P101 与其他项目的长期分支互相合并；跨项目已经稳定的仓库变化只能通过 `main` 接收。

## 2. 分支与发布流程

长期分支固定为：

```text
p101-exp → p101-stable → main → 标签与 Release → 回流 p101-stable / p101-exp
```

具体规则：

1. 日常需求、修复和实验从最新 `main` 回流后的 `p101-exp` 开始。
2. `p101-exp` 达到候选标准后，通过 PR 晋级 `p101-stable`。
3. `p101-stable` 必须通过完整 Windows 原生验证后，才可通过 PR 合入 `main`。
4. 正式标签和 Release 只能从 `main` 建立。
5. 发布完成后，最新 `main` 必须回流到 `p101-stable` 和 `p101-exp`。
6. 临时迁移、修复、发布和触发分支在任务结束后必须删除，不得长期堆积。
7. 不得直接在 `main` 上进行日常功能开发。
8. 不得为了减少冲突，把其他项目分支直接合入 P101 长期分支。

## 3. 产品安全底线

- 软件不得修改或删除源视频、源图片和源目录结构。
- 覆盖已有输出必须由明确规则或用户操作决定，不能静默覆盖。
- 同名输出必须使用原子占用或等效机制，防止并发任务写入同一目标。
- 每个输入必须形成明确结果，不能静默丢失、永久停留在中间状态或被批次结束默认判定为成功。
- 只有输出文件真实存在，并通过最低完整性检查后，任务才能记为成功。
- 启动失败、编码器失败、FFmpeg 失败、输出缺失、输出异常过小、取消、恢复失败和验证失败必须形成明确状态和可追溯原因。
- 不得通过删除功能、隐藏错误、降低检查门槛或把失败记为成功来制造“稳定版”。
- 处理过程中产生的临时文件必须可识别、可清理，不能与正式输出混淆。

## 4. 默认行为与兼容原则

现有默认行为未经明确产品决策不得随意改变：

- 自动读取媒体方向信息并转正。
- 视频输出默认采用 MP4。
- 视频编码以 H.265/HEVC 和高质量为主要默认路线。
- 默认输出分辨率为 1080P，并根据横屏、竖屏保持正确方向和比例。
- 文件夹导入默认包含子文件夹。
- 图片主要输出为 JPG；现阶段正式支持 JPG/PNG 输入。
- 清除 GPS、设备信息等隐私元数据默认关闭，不能未经用户选择主动删除。
- 图片应尽可能保留 EXIF 原始拍摄时间；视频应尽可能保留 QuickTime/MP4 创建时间及 Windows 创建、修改时间。
- 批量统一设置与单任务覆盖同时存在，单任务设置优先于统一设置。
- 多选任务应允许批量修改参数。
- 硬件编码可优先使用，但不可用或执行失败时必须安全回退 CPU。
- 并行任务数可配置，默认面向多核桌面环境，同时必须限制探测、缩略图和扫描工作池。

任何默认值变化都必须说明：变化原因、影响范围、旧配置兼容方式、自动测试和用户迁移结果。

## 5. 数据目录与旧版本兼容

Mediova v4.0.0 使用：

```text
%APPDATA%\Mediova
%LOCALAPPDATA%\Mediova
MediovaData
```

兼容规则：

- 首次运行仅在新位置缺少相应数据时，从旧 VideoUpright 目录复制。
- 不删除旧目录。
- 不覆盖已经存在的新文件。
- 复制失败必须返回明确错误，不得静默假定迁移成功。
- 配置 JSON、任务包、历史、会话和内部模块格式应保持兼容，除非有充分必要性和明确迁移器。
- 构建和测试必须使用独立临时数据目录，禁止读取开发机或上一次测试留下的真实历史。
- AppData 中不得混入发布 EXE 或其他本应属于程序目录的运行时文件，除非未来经过明确架构决策。

## 6. 媒体处理约束

- 旋转、缩放、裁剪和编码应尽可能在同一次 FFmpeg 处理中完成，避免无意义的多次重编码。
- 对多音轨、字幕、附件、位图字幕和 VFR 必须先判断安全处理方式，不能盲目复制全部流。
- 无法安全保留的轨道应明确告知，不得静默丢弃关键内容。
- 目标体积模式必须根据时长和音频占用合理计算视频码率，并处理不可能目标。
- 无损拼接只能用于参数兼容的媒体流；不兼容时必须明确失败原因或切换到用户认可的转码方案。
- 裁剪、分段和合并结果同样受输出完整性和任务闭环规则约束。
- FFmpeg/FFprobe 探测必须有超时和故障处理，不能让界面永久卡在“检测中”。
- 不能依赖开发者电脑中偶然存在的 FFmpeg 路径；正式验证必须使用明确提供的真实 FFmpeg/FFprobe。

## 7. 界面与交互约束

- 顶部主要工具栏保持单行；搜索、状态筛选和状态灯不得因窗口缩放自动掉到下一行。
- 不同窗口大小必须重新布局，禁止文字重叠、控件覆盖、按钮越界和不可访问区域。
- 底部操作按钮、总进度条和状态文字不得互相冲突。
- 总进度条应使用完整条形区域，核心进度文字位于条内或与条形成统一信息结构。
- 行内任务进度应保持完整、可读，并能显示当前状态和剩余信息。
- 体积结果条应按原体积与输出体积的实际比例表达；明显变小使用正向提示，明显变大使用警示提示，小幅变化保持中性。
- 列标题、边框、字体、字号、按钮尺寸和间距必须统一。
- 次要说明优先使用悬浮提示，避免长期占用布局空间。
- 标题和路径应在可用空间内清晰横向组织，不能无控制地挤成两层混乱文字。
- 文本区域需要根据内容和窗口宽度支持合理换行。
- DPI、最大化、还原、多显示器和不同缩放比例属于每轮界面修改的回归范围。
- 关闭窗口时的托盘行为、任务运行确认和播放器调用必须保持一致，不得因界面重构失效。

## 8. 性能与并发约束

- 不得在 UI 线程执行长时间媒体探测、目录扫描、缩略图生成或编码等待。
- 扫描、探测、缩略图和转换使用相互独立且有上限的工作池。
- 大批量导入必须进行节流和批量刷新，不能为每个文件触发高频完整界面重绘。
- 并发配置、历史写入和任务状态修改必须具备竞态保护。
- 任务取消和暂停必须明确作用边界，不能留下无法识别的残缺输出。
- 大批量测试至少应覆盖数千文件扫描；重要性能修改应给出前后数据或稳定性证据。
- 4K 视频预览和缩略图不能阻塞主要操作；必要时使用低成本代理数据而不是解码完整媒体。

## 9. 测试与验证门槛

用户不承担主要回归测试。提交前应尽可能自行生成测试视频、图片和异常样本，并完成以下验证：

### 基础门槛

- `SOURCE_FILES_SHA256.txt` 与受管源码逐文件一致。
- `go test -count=1 ./...` 通过。
- `go test -race -count=1 ./internal/config ./internal/media` 通过。
- `go vet -unsafeptr=false ./...` 通过。
- Windows amd64 测试程序交叉构建通过。
- Windows GUI 交叉构建通过。

### 稳定候选与正式主线门槛

- Windows Runner 上执行全量 Go 测试和 `go vet`。
- 正式资源版 EXE 构建成功。
- ProductName、FileVersion 和 ProductVersion 与目标版本一致。
- 使用真实 FFmpeg 与 FFprobe。
- 启动正式 EXE 执行原生自检。
- 原生自检不得少于当前基线 57 项，除非有明确、合理且经过审查的测试结构调整。
- 自检 JSON 中所有检查均通过。
- 构建产物、`SHA256.txt` 和实际文件哈希一致。

### 真实环境补充验证

以下内容自动化后仍需少量 Windows 冒烟确认：拖放、托盘、多显示器、不同 DPI、显卡驱动、PotPlayer 路径、窗口焦点、文件时间及特殊真实媒体。进行人工验证前，自动测试和自检必须先通过。

## 10. 构建、版本与发布约束

- 正式构建脚本位于 `代码/build_v4.0.0.ps1`；后续版本升级应建立对应版本入口或安全更新现有脚本。
- 正式 EXE 命名遵循 `Mediova_v<版本>.exe`。
- Windows 资源中的产品名、文件版本、产品版本和界面版本必须一致。
- Release 只提供经过固定验证的正式产物，不上传调试文件、真实用户数据、缓存、日志、私有附件或重复无价值文件。
- 正式发布必须记录 EXE 大小、SHA-256、自检数量、CI 运行和标签。
- 项目未附带 LICENSE，保留全部权利；不得擅自添加开源许可证或改变版权边界。
- 版本号必须对应实际变化，不得为了推进对话机械增加补丁号。

## 11. 文档与工作记录约束

- 新需求被确认进入计划后，先更新 `工作记录.md`。
- 开始实施后将状态改为“进行中”，并写明尚缺的验证条件。
- 完成后勾选 `[x]`，状态改为“完成”，同步更新版本说明和必要测试。
- 重大架构、数据兼容、默认行为、测试门槛和发布流程变化必须更新本文件。
- 阶段性重要结果应写入 `软件开发总结.md`，避免新对话依赖旧聊天记录。
- 不得删除未完成项目来伪造完成度；取消或延期项目改为“暂缓”并说明原因。
- README 应保持新对话阅读入口清晰。

## 12. 开发方式与决策原则

- 优先解决根因，不接受对同一界面或稳定性问题反复打表面补丁。
- 不过度设计。能用简单、可验证、可维护的本地方案解决时，不引入不必要的服务、数据库或复杂框架。
- 不为技术炫耀重写已经稳定的模块。
- 不因迁移、改名或整理目录破坏用户数据和既有格式。
- 不把尚未验证的推测写成已经完成的功能。
- 对无法自动验证的内容必须明确说明剩余风险。
- 修改应保持范围可审查；P101 PR 不得夹带其他项目变化。
- 交付前检查工作区、PR 差异、分支目标、CI 和正式产物，不能只根据代码看起来正确就宣布完成。

## 13. 后续功能优先级

在没有新的明确用户指令时，默认顺序为：

1. v4.0.x 真实环境回归与稳定性修复。
2. 右键菜单、裁剪时间轴、预览和文件级暂停恢复。
3. HEIC/HEIF、手机 MOV、HDR 和元数据兼容。
4. 音视频轨道选择、字幕编辑和批量封装。
5. 视频分段、无损拼接与合并。
6. 持续的大批量、长时间运行、多显示器和 DPI 回归。

优先级可以根据用户明确需求调整，但不得跳过相应安全、兼容和验证门槛。
