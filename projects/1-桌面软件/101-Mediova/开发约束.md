# Mediova 开发约束

> 约束层级：C｜项目级  
> 适用范围：P101 Mediova  
> 上位规则：A｜`/GPT_RULES.md`；B｜`../开发约束.md`

本文件只保存 Mediova 当前仍生效、且不能仅由 A/B 级规则表达的项目长期约束。分支、PR、CI、发布、Runtime/Data 和真实环境验证首先服从 A/B；本文件只能细化或收紧，不得放宽上位规则。

## C-01｜项目身份与修改边界

- 产品名称：Mediova；项目编号：P101。
- 正式路径：`projects/1-桌面软件/101-Mediova/`。
- 技术栈：Go、原生 Win32、FFmpeg/FFprobe、Windows x64。
- 唯一活动维护仓库为 `FenLynn/gpt-pub`；私有旧仓库只保留只读历史，不得恢复第二条开发主线。
- 长期分支为 `p101-exp`、`p101-stable` 和 `main`，提升、回流与清理服从 B 级规则。
- P101 的有效产品差异只能位于 P101 项目目录、P101 活动 CI，以及确有必要的 P101 共享状态行。
- 不得修改 AtlasDesk 的产品目录、源码、CI、分支、版本、发布记录、计划或 Runtime/Data 文件。

## C-02｜源文件与结果闭环

- 软件不得修改或删除源视频、源图片和源目录结构。
- 覆盖已有输出必须由明确规则或用户操作决定，不能静默覆盖。
- 同名输出必须使用原子占用或等效机制，防止并发任务写入同一目标。
- 每个输入必须形成明确结果，不能静默丢失、永久停留在中间状态或被批次结束默认判定为成功。
- 只有输出文件真实存在并通过最低完整性检查后，任务才能记为成功。
- 启动失败、编码器失败、FFmpeg 失败、输出缺失、输出异常过小、取消、恢复失败和验证失败必须形成可追溯状态与原因。
- 临时文件必须可识别、可清理，不能与正式输出混淆。
- 不得通过删除功能、隐藏错误、降低检查门槛或把失败记为成功制造“稳定版”。

## C-03｜默认行为与兼容

未经明确产品决策，不得随意改变以下默认行为：

- 自动读取媒体方向信息并转正；
- 视频输出默认 MP4，主要编码路线为 H.265/HEVC 与高质量；
- 默认输出 1080P，并根据横竖屏保持正确方向与比例；
- 文件夹导入默认包含子文件夹；
- 图片主要输出 JPG；JPG/PNG 为稳定输入，HEIC/HEIF/AVIF 只有在当前 FFmpeg 实际解码预检通过时才视为可处理；
- 清除 GPS、设备信息等隐私元数据默认关闭；
- 尽可能保留图片 EXIF 拍摄时间、视频容器创建时间和 Windows 创建/修改时间；
- 批量统一设置与单任务覆盖并存，单任务设置优先；
- 多选任务允许批量修改；
- 硬件编码不可用或执行失败时安全回退 CPU。

默认值或格式变化必须说明原因、影响范围、旧配置兼容方式、迁移结果和回归证据。配置、任务包、历史和会话格式应保持兼容；确需破坏性升级时必须提供明确迁移器和回滚边界。

## C-04｜Runtime、Data 与组件迁移

Mediova 使用“轻量透明 Runtime + 独立 Data”。

```text
Mediova/
├── Mediova.exe
├── Components/FFmpeg/bin/
├── runtime-manifest.json
├── THIRD_PARTY_NOTICES.md
└── README.txt
```

Runtime 规则：

- `Mediova.exe` 是唯一直接主程序，不增加自释放启动器、后台服务或无必要宿主层。
- 已稳定嵌入 EXE 的图标、界面和普通资源不得仅为“文件夹化”而拆出。
- 外部运行依赖统一位于 `Components/<组件>/`，不得作为 Data 写入 AppData。
- 程序不得启动时把 Runtime 复制或释放到 Data。
- Runtime 必须可以整体公开、复制、覆盖、校验和删除后重建，不能依赖上次运行留下的隐藏组件。
- `runtime-manifest.json` 必须记录产品、版本、平台、部署形态，以及逐文件相对路径、大小和 SHA-256。
- Runtime 必须包含准确的第三方来源和许可说明。

Data 规则：

```text
%APPDATA%\Mediova       # 配置、历史、会话、备份
%LOCALAPPDATA%\Mediova  # 缓存、临时文件、缩略图、本机状态、日志、崩溃信息
MediovaData              # 便携模式 Data
```

- Roaming Data 保存轻量、重要、私人且值得备份的内容；Local Data 保存机器相关或可再生内容。
- Runtime、源码、CI、Artifact、Release 和更新包不得包含配置、历史、会话、日志、缓存、私人路径、真实媒体、Token 或凭据。
- 便携模式仍须保持 Runtime 与 Data 的逻辑边界，不得把正式组件安装到便携 Data。
- 只有 Runtime 缺少有效组件时，才允许从旧 AppData 复制；只复制缺失文件，不覆盖 Runtime 已有文件，不删除旧目录。
- 复制后必须验证 `ffmpeg.exe`、`ffprobe.exe` 和必要依赖；用户明确选择的系统路径或外部路径保持权威。

## C-05｜媒体处理与第三方组件

- 旋转、缩放、裁剪和编码应尽可能在一次 FFmpeg 处理中完成，避免无意义的多次重编码。
- 多音轨、字幕、附件、位图字幕和 VFR 必须先判断安全处理方式，不能盲目复制全部流。
- 无法安全保留的关键轨道必须明确告知，不得静默丢弃。
- 目标体积模式必须根据时长和音频占用计算视频码率，并识别不可能目标。
- 无损拼接只适用于参数兼容的媒体流；不兼容时明确失败原因或使用用户认可的转码方案。
- 裁剪、分段、拼接和合并同样服从 C-02 的结果闭环。
- FFmpeg/FFprobe 探测必须有超时与故障处理，不能让界面永久停在“检测中”。
- HEIC、HEIF、AVIF 等现代图片必须通过当前 FFmpeg 的有界真实解码预检，不能仅凭扩展名宣称支持。
- 正式验证必须使用明确获取的真实 FFmpeg/FFprobe，不能依赖开发机偶然存在的路径。
- 第三方二进制进入 Runtime 前必须记录来源、版本或获取通道、许可证和完整性信息。
- 使用浮动下载通道构建候选时，正式 Release 必须以标签提交生成的实际 Artifact、清单和 SHA-256 固定结果。

## C-06｜界面与交互

- 主界面使用统一底色，分区优先依靠留白、对齐和极淡分隔线，不得层层套卡片、白块和重复粗边框。
- 同类控件使用统一字体、字号、边线、内边距和状态反馈。
- 顶部主要工具栏保持单行；搜索、筛选和状态灯不得因窗口缩放掉到下一行。
- 所有可点击按钮必须具备默认、悬停、按下、选中、禁用五态；禁用状态仍须可辨认，且不得残留旧边框或改变外框尺寸。
- 开始、暂停、停止三个主要按钮必须由同一 footer 几何模型布局，保持同高、同基线、固定间距和整体右对齐；不得分别从窗口底部反推坐标。
- 进度条、状态文字与按钮组必须共享 footer 边界，不能互相覆盖，也不能通过负偏移维持偶然布局。
- “输出母目录”支持编辑、最近目录去重、浏览和打开当前目录；无效目录必须明确提示。
- 进度条和体积条采用单层绘制，文字在完整条形区域内居中，不在条内嵌套小框。
- 体积条按输入体积与输出体积总和计算真实比例；±10% 变化为黄色；输出变大但最终小于 15 MB 时黄色优先；明显压缩为分级绿色；明显增长为分级红色。
- 行内条形以上下 5 px 为几何基准并随 DPI 合理缩放。
- 底部参数控件按真实内容和可用空间确定宽度，不机械等宽，也不为极端文本无限扩张。
- 每次界面变化必须覆盖多窗口尺寸、最大化/还原、100%–175% DPI 和多显示器风险；自动化无法证明的视觉结果标记为“待验证”。

## C-07｜性能、并发与恢复

- UI 线程不得执行长时间媒体探测、目录扫描、缩略图生成、解码预检或编码等待。
- 扫描、探测、缩略图和转换使用相互独立且有上限的工作池。
- 大批量导入必须节流并批量刷新，不能为每个文件触发高频完整重绘。
- 配置、历史、任务状态和会话快照写入必须具备竞态保护。
- 会话快照必须通过同目录临时文件、同步落盘和原子替换保存，并保留可验证的 `.bak` 回退；不得直接截断唯一主文件后写入。
- 取消和暂停必须明确作用边界，不能留下无法识别的残缺输出。
- 大批量回归至少覆盖数千文件扫描；会话恢复压力测试不得低于 2500 项当前基线，除非测试结构变化经过明确审查。
- 4K 预览和缩略图不得阻塞主要操作，必要时使用低成本代理数据。

## C-08｜项目验证门槛

在 A-08 和 B-05 基础上，P101 至少执行：

```text
sha256sum -c SOURCE_FILES_SHA256.txt
go test -count=1 ./...
go test -race -count=1 ./...
go vet -unsafeptr=false ./...
```

并完成 Windows amd64 测试程序与 GUI 交叉构建。

每个普通测试、竞态测试、构建测试和原生自检必须使用独立临时环境，至少隔离：

```text
APPDATA
LOCALAPPDATA
XDG_CONFIG_HOME
MEDIOVA_RUNTIME_DIR
```

稳定候选与正式主线还必须：

- 在当前 PR 准确 head SHA 上执行 Windows 原生全测、全量竞态和 `go vet`；
- 使用真实 FFmpeg/FFprobe 构建完整 Runtime；
- 核对 ProductName、FileVersion、ProductVersion、界面版本和文件名；
- 逐文件复核 Runtime 清单路径、大小和 SHA-256；
- 扫描私人 Data 泄漏，包括 `session.json` 与 `session.json.bak`；
- 启动正式 `Mediova.exe` 执行原生自检；
- 原生自检不得少于当前 62 项基线，除非测试结构变化已经明确审查；
- 上传完整 Runtime 候选 Artifact、`SHA256.txt`、自检报告、四套真实 UI 截图和清单。

拖放、托盘、多显示器、显卡驱动、PotPlayer、窗口焦点、文件时间和特殊媒体仍需真实 Windows 观察；尚未实机确认时必须写为“待验证”，不能用构建成功替代。

## C-09｜构建、发布与记录

- 版本号必须有单一事实源，代码、资源、界面、构建脚本、文件名、阶段记录和 Release 不得矛盾。
- 正式主程序在 Runtime 中命名为 `Mediova.exe`。
- 面向用户的默认交付包命名为 `Mediova-v<版本>-Light.zip`，必须排除 `ffmpeg.exe`、`ffprobe.exe` 及 `Components/FFmpeg/`；除非用户明确要求，不得推荐携带 FFmpeg 的大体积包。
- 轻量包至少包含 `Mediova.exe`、轻量安装说明、与包内容一致的 `runtime-manifest.json` 和第三方说明，并单独提供包与主 EXE 的 SHA-256。
- 覆盖已有安装时不得删除用户现有 `Components/FFmpeg/`；首次部署由用户选择已有 FFmpeg/FFprobe 路径，或自行放入 `Components/FFmpeg/bin/`。
- 完整 FFmpeg Runtime 只作为内部验证 Artifact，不作为日常用户下载。
- Release 只提供标签提交生成并通过正式准入的用户产物，不上传调试文件或私人 Data。
- 正式发布必须记录标签、源提交、CI、原生自检、实机状态、轻量 ZIP 与主 EXE 大小和 SHA-256、清单结论及签名状态。
- 项目源码未附带开源 LICENSE，保留全部权利；第三方 Runtime 组件按自身许可证单独披露。

记录职责固定为：

- `README.md`：入口、当前基线链接、工程入口和分支入口；
- `工作记录.md`：活跃事项、完成标准、证据和尚缺内容；
- `阶段记录.md`：当前正式基线、验证、产物和已知限制；
- `开发约束.md`：当前长期规则，不记录一次性 CI 进度；
- `软件开发总结.md`：长期设计路线、取舍和技术债；
- 版本说明、PR、Release、Git 和 Artifact：保存版本变化与完整证据。

正式发布时必须更新阶段记录、清理工作记录中的已完成事项；候选版本不得提前写成正式发布，最终运行编号和哈希只能在对应 Release 完成后登记。

## C-10｜任务状态、参数冻结与队列操作

- 视频与图片分别保存输出母目录、最近目录、全局默认参数和右侧个体参数；切换媒体模式时不得残留另一模式的目录、文本或选项。
- 底部参数是当前模式的全局默认控制器和新任务模板。单字段变化只立即作用于同模式准备中任务；已入队、转换中、暂停和搁置任务不受影响。
- 右侧个体参数使用草稿与显式提交。多选出现混合值时，只能提交用户实际修改的字段。
- 任务从准备中进入队列中时，必须冻结转换参数、输出母目录、完整输出路径、冲突策略和必要运行快照；后续全局默认变化不得修改该快照。
- 活动队列运行期间允许继续导入、编辑并动态追加同类型任务；新增任务须独立执行冲突与空间预检。
- 同一活动队列只运行一种媒体；另一媒体类型可以继续准备，但不得混入当前队列。
- 队列中、转换中和暂停任务默认锁定；普通底部参数和普通右侧操作不得直接改写锁定任务。
- 单个锁定任务可以进入独立搁置会话；同一时间只允许一个参数修改会话。多选锁定任务只允许安全移除。
- 队列任务搁置后从等待调度中取出；应用后优先恢复原位置，原位置已经过去时进入当前等待队列前端。
- 转换任务搁置时必须安全终止 FFmpeg、等待进程退出、清理本次临时输出并保留一个并发名额；应用或取消后均从 0% 重新转换。
- 队列整体暂停时可以编辑搁置任务，但应用后等待恢复；整体停止时未提交草稿丢弃，搁置任务退回准备中且释放名额。
- 从任务列表移除不得删除源文件，也不得误删已经完成的正式输出。
- 动态追加后，总任务数、完成数和百分比必须按真实分母更新；百分比允许下降，但必须显示“已完成 x/y”。

## C-11｜双工作区底部状态与列表可读性

- 视频与图片可以共用底部控件实例，但进度统计、按钮文案、启用状态和命令作用域必须以当前工作区为准；另一个媒体队列运行时，当前页不得显示或控制对方队列。
- 视频任务列表必须提供独立时长列；图片行显示 `—`。新增列时必须迁移旧列宽。
- 进度文字整体居中后，按每个字符中心所在背景选择颜色：蓝色填充区使用白字，浅色轨道区使用深色字；不得恢复在 ListView/`PrintWindow` 中不稳定的裁剪重绘方案。
- 压缩后条形的原始体积侧必须有稳定可辨识的浅灰底，结果侧按压缩效果着色。
- 状态灯和小图标必须使用 DPI 感知矢量/字体绘制或等效高分辨率资源，禁止直接拉伸低分辨率位图。

## C-12｜会话快照与异常恢复

- 会话文件必须带 schema 版本、软件版本、保存时间、保存原因和正常退出标记；不得恢复为无版本语义的裸任务数组写入格式。
- 加载必须兼容已公开的旧任务数组格式；未来 schema 升级必须明确迁移或拒绝策略。
- 保存必须采用同目录临时文件、文件同步、主文件与 `.bak` 轮换和原子替换；主快照损坏时允许读取通过校验的备份。
- 恢复时只保留可持久化事实：冻结参数、输出母目录、冲突策略、输入信息和已完成结果。
- 进度、引擎、临时输出路径、输出大小、运行错误、开始/结束时间和搁置运行态属于瞬时信息，异常恢复时必须清除。
- 运行中、队列中、暂停、搁置和停止任务恢复为准备中，并从文件开头 0% 重新处理；不得伪装帧级或编码器内部断点续转。
- 完成、跳过和既有失败结果保持原状态，除非用户明确重新执行。
- 源文件缺失必须标记为明确失败，不能删除任务、修改源路径或默认为完成。
- 启动恢复摘要必须说明恢复来源、总数、重新处理数、缺失数和保留的终态结果。
