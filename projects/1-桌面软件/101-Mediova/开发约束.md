# Mediova 开发约束

本文件是 Mediova 后续开发、修复、测试、发布和新对话接续的强制约束。任何自动化代理或新建对话在修改代码前，应依次阅读本文件、`软件开发总结.md` 和 `工作记录.md`。

## 1. 项目身份与责任边界

- 产品名称：**Mediova**。
- 项目编号：P101。
- 正式路径：`projects/1-桌面软件/101-Mediova/`。
- 技术栈：Go、原生 Win32、FFmpeg/FFprobe、Windows x64。
- 当前正式版本：v4.0.0；当前候选版本：v4.1.0。
- 当前唯一开发仓库：`FenLynn/gpt-pub`。
- 私有旧仓库只保留只读源码与 Git 历史，不得恢复第二条 Mediova 开发主线。
- P101 开发只能修改 P101 目录、P101 长期 CI，以及共享目录中与 P101 状态直接相关的最小内容。
- **不得修改 AtlasDesk 的产品目录、源码、CI、分支、版本记录、发布记录、计划或 Runtime/Data 文件。**
- 不得把 P101 与其他项目的长期分支互相合并；跨项目已经稳定的仓库变化只能通过 `main` 接收。

## 2. 分支与发布流程

长期分支固定为：

```text
p101-exp → p101-stable → main → 标签与 Release → 回流 p101-stable / p101-exp
```

具体规则：

1. 日常需求、修复和实验从已接收最新 `main` 的 `p101-exp` 开始。
2. `p101-exp` 达到候选标准后，通过 PR 晋级 `p101-stable`。
3. `p101-stable` 必须通过完整 Linux 与 Windows 原生准入后，才可通过 PR 合入 `main`。
4. 正式标签和 Release 只能从 `main` 建立。
5. 发布完成后，最新 `main` 必须回流到 `p101-stable` 和 `p101-exp`。
6. 临时迁移、诊断、修复、发布和触发分支在任务结束后必须删除。
7. 不得直接在 `main` 上进行日常功能开发。
8. 不得为了减少冲突，把其他项目分支直接合入 P101 长期分支。
9. 一次性工作流只能用于明确的迁移、实施或发布任务，成功后必须自删除或通过清理 PR 删除。

## 3. 产品安全底线

- 软件不得修改或删除源视频、源图片和源目录结构。
- 覆盖已有输出必须由明确规则或用户操作决定，不能静默覆盖。
- 同名输出必须使用原子占用或等效机制，防止并发任务写入同一目标。
- 每个输入必须形成明确结果，不能静默丢失、永久停留在中间状态或被批次结束默认判定为成功。
- 只有输出文件真实存在，并通过最低完整性检查后，任务才能记为成功。
- 启动失败、编码器失败、FFmpeg 失败、输出缺失、输出异常过小、取消、恢复失败和验证失败必须形成明确状态和可追溯原因。
- 不得通过删除功能、隐藏错误、降低检查门槛或把失败记为成功来制造“稳定版”。
- 处理过程中产生的临时文件必须可识别、可清理，不能与正式输出混淆。

## 4. 默认行为与兼容原则

现有默认行为未经明确产品决策不得随意改变：

- 自动读取媒体方向信息并转正。
- 视频输出默认采用 MP4。
- 视频编码以 H.265/HEVC 和高质量为主要默认路线。
- 默认输出分辨率为 1080P，并根据横屏、竖屏保持正确方向和比例。
- 文件夹导入默认包含子文件夹。
- 图片主要输出为 JPG；当前正式支持 JPG/PNG 输入。
- 清除 GPS、设备信息等隐私元数据默认关闭，不能未经用户选择主动删除。
- 图片应尽可能保留 EXIF 原始拍摄时间；视频应尽可能保留 QuickTime/MP4 创建时间及 Windows 创建、修改时间。
- 批量统一设置与单任务覆盖同时存在，单任务设置优先于统一设置。
- 多选任务应允许批量修改参数。
- 硬件编码可优先使用，但不可用或执行失败时必须安全回退 CPU。
- 并行任务数可配置，但探测、缩略图、扫描和转换工作池必须分别限流。

任何默认值变化都必须说明变化原因、影响范围、旧配置兼容方式、自动测试和用户迁移结果。

## 5. Runtime/Data 架构硬约束

Mediova 从 v4.1.0 起采用“轻量透明 Runtime + 独立 Data”架构。

### 5.1 Runtime

默认 Runtime 根目录是 `Mediova.exe` 所在文件夹：

```text
Mediova/
├── Mediova.exe
├── Components/
│   └── FFmpeg/
│       └── bin/
├── runtime-manifest.json
├── THIRD_PARTY_NOTICES.md
└── README.txt
```

Runtime 规则：

- Runtime 只包含可公开、可替换、可校验、可重新下载的程序和运行依赖。
- 主程序保持单一直接 EXE，不增加自释放启动器、后台服务或无必要的宿主层。
- 已经稳定嵌入 EXE 的图标、界面和普通资源不得仅为“文件夹化”而拆出。
- 真实外部依赖统一位于 `Components/<组件>/`，保持清晰相对路径。
- 正式运行组件、EXE 和 DLL 不得重新写入 AppData。
- 程序不得在启动时把 Runtime 复制或释放到 Data。
- Runtime 可以整体覆盖、删除后重建；不得依赖上一次运行留下的隐式文件才能启动。
- `runtime-manifest.json` 必须记录产品、版本、平台、部署形态、逐文件路径、大小和 SHA-256。
- Runtime 包必须包含第三方组件来源和许可说明。
- 任何新增外部工具、插件、编解码器、辅助进程或模型文件，必须先明确它属于 Runtime 还是 Data，不得随意放置。

### 5.2 Data

```text
%APPDATA%\Mediova
```

用于轻量、重要、私人、值得备份的内容，例如配置、历史、会话和备份。

```text
%LOCALAPPDATA%\Mediova
```

用于本机私人状态和可再生内容，例如缓存、临时文件、缩略图、日志、状态和崩溃信息。

Data 规则：

- Data 不得包含正式发布 EXE、FFmpeg/FFprobe、DLL 或其他可公开运行组件。
- Runtime、公开仓库、Release 和增量更新包不得包含用户配置、历史、日志、缓存、私人路径、真实媒体、Token 或凭据。
- Roaming 与 Local Data 的职责不得随意混合；重要可备份内容优先 Roaming，可再生或机器相关内容优先 Local。
- 便携模式使用 `MediovaData`，但仍应保持 Runtime 与 Data 的逻辑边界，不把组件安装到便携 Data。

### 5.3 组件迁移

- 只有 Runtime 缺少有效组件时，才允许从旧 AppData 复制。
- 迁移只复制缺失文件，不覆盖 Runtime 已存在文件，不删除旧目录。
- 复制完成后必须验证成对组件和必要 DLL 是否存在。
- 迁移失败必须明确返回错误，不能静默假定成功。
- 旧 AppData 组件路径可以在 Runtime 有效时归一化为 Runtime 路径。
- 用户明确选择的系统路径、外部目录或自定义组件路径保持权威，不得强制重写。
- 未来重大迁移若无法安全放在产品代码中，应使用一次性外部迁移器，但必须先备份并可回滚。

## 6. 媒体处理与第三方组件约束

- 旋转、缩放、裁剪和编码应尽可能在同一次 FFmpeg 处理中完成，避免无意义的多次重编码。
- 对多音轨、字幕、附件、位图字幕和 VFR 必须先判断安全处理方式，不能盲目复制全部流。
- 无法安全保留的轨道应明确告知，不得静默丢弃关键内容。
- 目标体积模式必须根据时长和音频占用合理计算视频码率，并处理不可能目标。
- 无损拼接只能用于参数兼容的媒体流；不兼容时必须明确失败原因或切换到用户认可的转码方案。
- 裁剪、分段和合并结果同样受输出完整性和任务闭环约束。
- FFmpeg/FFprobe 探测必须有超时和故障处理，不能让界面永久卡在“检测中”。
- 不能依赖开发者电脑中偶然存在的 FFmpeg 路径；正式验证必须使用明确获取的真实组件。
- 第三方二进制进入 Runtime 前必须记录来源、版本或获取通道、许可证和完整性信息。
- 使用浮动 `latest` 通道构建候选时，正式 Release 必须以最终 Artifact 与 SHA-256 固定实际结果。
- 后续若更换 FFmpeg 构建来源、许可配置或编码器集合，必须更新 `THIRD_PARTY_NOTICES.md` 和版本说明。

## 7. 界面视觉与交互约束

### 7.1 全局视觉

- 主界面采用统一底色，不得层层叠加卡片、白块、厚重底纹和重复边框。
- 分区优先依靠留白、对齐和极淡分隔线，不通过每一区都套框实现。
- 同类控件必须使用统一字体、字号、边线、圆角、内边距和状态反馈。
- 顶部主要工具栏保持单行；搜索、状态筛选和状态灯不得因窗口缩放掉到下一行。
- 不同窗口大小必须重新布局，禁止文字重叠、控件覆盖、按钮越界和不可访问区域。

### 7.2 按钮和状态

所有可点击按钮必须具有五态：

```text
默认 → 悬停 → 按下 → 选中 → 禁用
```

- 默认状态使用透明或统一底色与淡边线。
- 悬停必须明显但克制，让用户知道即将点击哪个控件。
- 按下状态应提供明确反馈，不得与悬停完全相同。
- 选中状态持续表达当前模式，但不能使用厚重高饱和框。
- 禁用状态降低对比度，但文字和功能身份仍可辨认。
- 顶部主图标不得贴近或超出按钮客户区；图标与文字保持自然距离。
- 状态灯直径应接近文字字面高度，不能退化为难以辨认的小点。
- 折叠按钮保持紧凑，不能抢占状态区视觉注意力。
- 开始、暂停、停止等主要操作使用一致的实心按钮体系，不能与普通输入框混淆。

### 7.3 输出母目录

- 统一文案为“输出母目录”。
- 地址控件支持编辑、最近目录下拉和浏览选择。
- 最近目录必须去重并限制合理数量。
- 点击“输出母目录”标签或按钮应打开当前目录。
- 无效目录必须有明确提示，不能导致崩溃。
- 地址栏和参数栏不得出现父子边框叠加造成的黑线。

### 7.4 进度与体积条

- 进度条和体积条使用单层绘制，不得在条内再套一个小框。
- 未完成区域使用极淡背景，不形成强烈槽体。
- 文字必须在完整条形区域内水平、垂直居中。
- 行内条形保持现有完整行高几何基线，上下留白采用 5 px 设计基准，并随 DPI 合理缩放。
- 体积条左右宽度按输入体积与输出体积的实际总和计算，不把输出百分比直接当作进度宽度。
- 变化在 ±10% 内显示黄色。
- 输出变大但最终小于 15 MB 时，黄色优先级最高。
- 明显压缩显示绿色，压缩越多颜色越深。
- 明显增长显示红色，增长越多颜色越深。
- 颜色判定和比例计算必须保留独立自动测试，不能只靠截图确认。

### 7.5 布局回归

- 底部下拉框根据常用内容分别确定宽度，不机械等宽，也不为极端最长文本无限扩张。
- 右侧参数区与底部参数栏使用同一视觉语言。
- DPI、最大化、还原、多显示器和不同缩放比例属于每轮界面修改的回归范围。
- 关闭窗口的托盘行为、任务运行确认和播放器调用不得因界面重构失效。

## 8. 性能与并发约束

- 不得在 UI 线程执行长时间媒体探测、目录扫描、缩略图生成或编码等待。
- 扫描、探测、缩略图和转换使用相互独立且有上限的工作池。
- 大批量导入必须节流和批量刷新，不能为每个文件触发高频完整界面重绘。
- 并发配置、历史写入和任务状态修改必须具备竞态保护。
- 任务取消和暂停必须明确作用边界，不能留下无法识别的残缺输出。
- 大批量测试至少覆盖数千文件扫描；重要性能修改应给出前后数据或稳定性证据。
- 4K 预览和缩略图不能阻塞主要操作；必要时使用低成本代理数据。

## 9. 测试与验证门槛

用户不承担主要回归测试。提交前应尽可能自行生成测试视频、图片和异常样本。

### 9.1 基础门槛

- `SOURCE_FILES_SHA256.txt` 与受管源码逐文件一致。
- `go test -count=1 ./...` 通过。
- `go test -race -count=1 ./internal/config ./internal/media` 通过。
- `go vet -unsafeptr=false ./...` 通过。
- Windows amd64 测试程序交叉构建通过。
- Windows GUI 交叉构建通过。
- 界面比例、颜色、目录历史和 Runtime 路径规则的独立测试通过。

### 9.2 测试环境隔离

每一次普通测试、竞态测试、构建测试和原生自检必须使用独立临时环境，至少隔离：

```text
APPDATA
LOCALAPPDATA
XDG_CONFIG_HOME
MEDIOVA_RUNTIME_DIR
```

- 不同测试命令不得复用同一个 Data 根目录。
- 测试不得读取开发机或上一次运行留下的真实配置、历史、组件和缓存。
- 测试结束后应清理临时目录。
- 若测试依赖 Runtime 组件，必须使用独立临时 Runtime 或明确的 CI Runtime。

### 9.3 稳定候选与正式主线门槛

- Windows Runner 上执行全量 Go 测试、竞态检查和 `go vet`。
- 使用真实 FFmpeg 与 FFprobe。
- `build_v4.1.0.ps1` 或目标版本脚本成功生成完整 Runtime。
- ProductName、FileVersion、ProductVersion 和界面版本一致。
- `runtime-manifest.json` 的逐文件路径、大小和 SHA-256 全部复核。
- Runtime 包含要求的主程序、组件、README 和第三方说明。
- Runtime ZIP 不包含配置、历史、日志、缓存、凭据或其他私人 Data。
- 启动正式 `Mediova.exe` 执行原生自检。
- 原生自检不得少于当前 57 项基线，除非有明确、合理且经过审查的测试结构调整。
- 自检 JSON 中所有检查均通过。
- `SHA256.txt`、Runtime ZIP 和实际文件哈希一致。

### 9.4 真实环境补充验证

自动化后仍需少量真实 Windows 观察：拖放、托盘、多显示器、不同 DPI、显卡驱动、PotPlayer、窗口焦点、文件时间和特殊媒体。进行人工验证前，自动测试和原生自检必须先通过。

## 10. 构建、版本与发布约束

- v4.1.0 正式构建脚本为 `代码/build_v4.1.0.ps1`；后续版本必须建立对应安全入口。
- 正式主程序在 Runtime 中命名为 `Mediova.exe`。
- 完整发布包命名遵循 `Mediova-v<版本>-Runtime.zip`。
- 架构变化版本必须交付完整 Runtime ZIP，不能只提供主 EXE。
- 后续只修改单个公开运行文件时，可以提供按 Runtime 原相对路径组织的增量更新，但不得省略完整性信息。
- Windows 资源中的产品名、文件版本、产品版本和界面版本必须一致。
- Release 只提供经过固定验证的正式产物，不上传调试文件、真实用户数据、缓存、日志、私有附件或无价值重复文件。
- 正式发布必须记录标签、源提交、准入运行、Release 运行、Runtime ZIP 大小与 SHA-256、主 EXE 大小与 SHA-256、自检数量和清单结果。
- 项目源码未附带开源 LICENSE，保留全部权利；第三方 Runtime 组件的许可证必须单独、准确披露。
- 版本号必须对应实际变化，不得为了推进对话机械增加补丁号。

## 11. 文档与工作记录约束

- 新需求确认进入计划后，先更新 `工作记录.md`。
- 开始实施后将状态改为“进行中”，并写明尚缺的验证条件。
- 完成后勾选 `[x]`，状态改为“完成”，同步更新版本说明和必要测试。
- 重大架构、数据兼容、默认行为、第三方组件、测试门槛和发布流程变化必须更新本文件。
- 阶段性重要结果应写入 `软件开发总结.md`，避免新对话依赖旧聊天记录。
- 不得删除未完成项目来伪造完成度；取消或延期项目改为“暂缓”并说明原因。
- README 应保持新对话阅读入口、构建方式、Runtime 结构和 Data 边界清晰。
- 候选版本不得提前写成正式发布；最终运行编号和哈希只能在 Release 完成后登记。

## 12. 开发方式与决策原则

- 优先解决根因，不接受对同一界面或稳定性问题反复打表面补丁。
- 不过度设计。能用简单、可验证、可维护的本地方案解决时，不引入不必要的服务、数据库、启动器或复杂框架。
- 不为技术炫耀重写已经稳定的模块。
- Runtime 分离是为了明确运行边界，不是为了制造更多文件。
- 不因迁移、改名或整理目录破坏用户数据和既有格式。
- 不把尚未验证的推测写成已经完成的功能。
- 对无法自动验证的内容必须明确说明剩余风险。
- 修改应保持范围可审查；P101 PR 不得夹带其他项目变化。
- 交付前检查差异、分支目标、CI、Runtime 清单和正式产物，不能只根据代码看起来正确就宣布完成。

## 13. 后续功能优先级

在没有新的明确用户指令时，默认顺序为：

1. v4.1.x 真实环境回归与稳定性修复。
2. 右键菜单、裁剪时间轴、预览和文件级暂停恢复。
3. HEIC/HEIF、手机 MOV、HDR 和元数据兼容。
4. 音视频轨道选择、字幕编辑和批量封装。
5. 视频分段、无损拼接与合并。
6. 持续的大批量、长时间运行、多显示器和 DPI 回归。

优先级可以根据用户明确需求调整，但不得跳过相应安全、Runtime/Data、兼容和验证门槛。
