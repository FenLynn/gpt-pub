# 软件设计记录建议书

本文件用于指导 GPT-Pub 桌面软件的长期记录方式。

目标只有一个：**让新对话能够快速接续，同时不让文档维护反过来拖慢开发。**

本文件是分类级参考，不直接覆盖仓库规则。项目只有在自己的约束文件中明确采纳本建议中的某条做法后，才把它视为项目强制要求。

---

## 1. 最终结论

软件项目初始只建立三个文件：

```text
README.md
工作记录.md
阶段记录.md
```

确有长期规则时，再增加：

```text
开发约束.md
```

发生重大架构取舍、历史路线替代或长期技术债时，再增加：

```text
设计与演进.md
```

因此推荐模型不是“所有项目默认五文件”，而是：

```text
三文件起步
→ 有需要才升级四文件
→ 再有需要才升级五文件
```

不为形式创建空白文件，也不为统一外观重写稳定历史。

## 2. A、B、C 约束层级

### 2.1 层级定义

```text
A｜仓库级规则
↓
B｜分类级规则
↓
C｜项目级规则
```

| 层级 | 典型文件 | 适用范围 |
|---|---|---|
| A | `/GPT_RULES.md` | 整个 GPT-Pub |
| B | `/projects/1-桌面软件/开发约束.md` | 所有桌面软件；仅在确有共享硬规则时创建 |
| C | `项目目录/开发约束.md` | 单个项目；仅在项目需要长期约束时创建 |

当前这份《软件设计记录建议书》仍是参考文件，不自动等同于 B 级强制约束。

B 级约束原则上应至少服务两个项目。只适用于一个项目的规则应留在 C 级，不为了层级完整强行创建分类约束。

### 2.2 不建议把 A、B、C 强行写入文件名

不建议把文件改成：

```text
A-GPT_RULES.md
B-桌面软件约束.md
C-项目约束.md
```

原因是：

- `GPT_RULES.md` 是稳定入口，改名会破坏既有链接和工具习惯；
- 文件所在路径已经表达作用域；
- 同名 `开发约束.md` 更方便新对话按固定名称查找；
- 以后增加其他分类时，不需要继续制造特殊文件名。

更推荐在文档开头标明层级：

```markdown
> 约束层级：C｜项目级
> 上位规则：A｜/GPT_RULES.md；B｜../开发约束.md
> 适用范围：P101 Mediova
```

这样既保留 A＞B＞C 的直观关系，又不污染文件名。

### 2.3 规则编号

真正需要长期引用的规则可以编号：

```text
A-01  仓库级规则
B-03  桌面软件分类规则
C-07  某项目专属规则
```

编号只用于稳定、长期、可能被其他文档引用的规则。

普通说明、示例、临时要求和一次性修复不编号。

### 2.4 约束关系

默认原则：

```text
A > B > C
```

下位规则可以：

- 细化上位规则；
- 在本范围内增加更严格的要求；
- 补充上位规则未规定的项目细节。

下位规则不得：

- 放宽上位规则；
- 与上位规则冲突；
- 通过写一句“本项目特殊”自行覆盖上位规则。

### 2.5 特殊情况

确需突破 A 级规则时，不能只在 B 或 C 中说明理由后自行生效。

正确方式是：

1. 修改 A 级规则，明确允许该类例外；或
2. 在 A 级规则中登记限定范围的例外。

例外至少应写明：

```text
对应上位规则
适用项目或范围
特殊原因
主要风险
重新评估条件或失效条件
```

B 级规则同理。C 级如需突破 B，必须先在 B 中明确授权或登记例外。

## 3. 三文件起步

### 3.1 README.md

只负责入口和导航：

- 软件是什么；
- 当前正式基线在哪里；
- 当前工作在哪里；
- 代码、构建和 CI 从哪里进入；
- 应按什么顺序阅读。

README 不应长期复制完整架构、全部计划、历代版本和发布哈希。

### 3.2 工作记录.md

只负责当前开发窗口：

```text
现在做什么
方案是否确定
还缺什么
如何才算完成
证据在哪里
```

它是滚动看板，不是完整功能清单，也不是永久历史库。

### 3.3 阶段记录.md

只负责当前正式基线：

- 当前版本或当前未发布基线；
- 正式提交、标签和 Release；
- 重要架构结论；
- CI、测试和自检结果；
- Artifact、EXE、ZIP 大小和 SHA-256；
- 已知限制和剩余风险。

新版本发布后，阶段记录整体更新到新基线。旧版本由 Git 标签、Release 和历史提交保存。

## 4. 何时升级到四文件

项目出现以下任一情况时，增加 `开发约束.md`：

- 涉及用户数据、隐私、备份或不可逆操作；
- 存在固定分支、CI、发布或交付规则；
- 存在必须长期保持的兼容行为；
- 多轮开发已经发生“修复新问题又破坏旧决定”；
- 多个对话或代理需要持续接续；
- 某些默认行为一旦改变会产生明显风险。

`开发约束.md` 只保存**当前仍生效**的规则。

适合写：

```text
必须
不得
仅允许
默认
除非经过明确决策
```

不适合写：

```text
当前正在修复
本轮已经完成
下一步准备
某次 CI 已通过
```

---

## 5. 何时升级到五文件

项目出现以下任一情况时，增加 `设计与演进.md`：

- 发生重大架构选择；
- 部署形态、数据位置或格式发生变化；
- 模块职责或运行时边界发生变化；
- 存在多个可行路线并已明确取舍；
- 保留了长期兼容层或明显技术债；
- 已投入明显成本的路线被放弃；
- 新开发者只看当前代码无法理解设计原因；
- 同一错误路线很可能被后续对话反复提出。

普通按钮、颜色、间距、圆角和一次性 UI 修复不进入设计与演进。

重大决策可以在同一文件内使用简化编号：

```markdown
### AD-D-004｜Dashboard 采用混合浏览模式

- 状态：生效
- 问题：……
- 决策：……
- 原因：……
- 影响：……
- 替代：无
```

状态只需：

```text
生效
已替代
未采用
试验
```

不为每个决定单独创建 ADR 文件。

## 6. 单一事实源

| 信息 | 主文件或主证据 |
|---|---|
| 仓库硬规则 | `GPT_RULES.md` |
| 分类共享硬规则 | 分类 `开发约束.md`，如存在 |
| 项目长期规则 | 项目 `开发约束.md`，如存在 |
| 项目入口 | `README.md` |
| 当前工作 | `工作记录.md` |
| 当前正式基线 | `阶段记录.md` |
| 重大设计原因 | `设计与演进.md`，如存在 |
| 实现事实 | 源码 |
| 验证事实 | 测试和 CI |
| 历史事实 | Git、PR、标签和 Release |
| 截图、视频、完整日志 | PR、Issue 或 Artifact |

同一完整事实只写在一个主文件中。其他文件只写一句摘要和链接。

文档不能用“写了已完成”替代真实代码和验证证据。

## 7. 新对话读取顺序

约束必须先按层级读取：

```text
A｜/GPT_RULES.md
→ B｜分类开发约束.md（如存在）
→ C｜项目开发约束.md（如存在）
```

随后读取项目状态：

```text
README.md
→ 阶段记录.md
→ 工作记录.md
→ 设计与演进.md（按当前模块选择性阅读）
```

完整推荐顺序为：

```text
GPT_RULES.md
→ 分类开发约束.md（如存在）
→ 项目开发约束.md（如存在）
→ README.md
→ 阶段记录.md
→ 工作记录.md
→ 设计与演进.md（按需）
```

`设计与演进.md` 可能逐渐变长，不要求每个新对话无差别全文读取。只读取与当前任务相关的主题即可。

## 8. 工作记录保持轻量

### 8.1 推荐状态

只保留：

| 状态 | 含义 |
|---|---|
| 待决策 | 问题确认，但路线尚未确定 |
| 计划 | 路线已确定，尚未开始 |
| 进行中 | 已开始实施，尚未完成 |
| 待验证 | 自动验证完成，仍缺实机或用户确认 |
| 暂缓 | 当前不推进，并说明重新评估条件 |
| 取消 | 明确不再实施，并保留原因 |

“完成”不作为长期活跃状态，只进入“最近完成”。

不要同时使用复选框和状态字段，避免出现 `[x] + 进行中` 之类冲突。

### 8.2 最小字段

推荐只保留：

```text
工作项
状态
完成标准
当前证据或尚缺内容
```

### 8.3 稳定编号按需使用

只有以下情况才建议使用 `AD-UI-001`、`MV-MEDIA-001` 之类编号：

- 多个事项并行；
- 一个事项跨多个 PR；
- 需要在反馈、截图、测试和提交之间反复引用；
- 活跃事项较多，仅靠名称容易混淆。

普通小修复直接使用任务名称、PR 号或版本号即可。

### 8.4 不要求所有小修改先建项

以下事项实施前应进入工作记录：

- 用户确认的独立需求；
- 影响架构、数据、隐私或兼容性的修改；
- 跨多个提交或需要实机验收的工作；
- 计划进入正式版本的功能和缺陷。

拼写修正、明显路径错误、同一任务内的小型回归和纯文档纠错，可以在 PR 或完成时补充，不要求修改前单独建项。

### 8.5 容量是提示，不是硬门槛

工作记录应只保留活跃事项、近期候选和少量最近完成项。

“活跃事项约 20 项”“最近完成约 5–10 项”只是整理提示，不是机械限制。超过后应判断是否失焦，而不是为了数字删除仍有价值的信息。

## 9. 信息流转

```text
需求确认
→ 工作记录
→ 实施与验证
→ PR、CI、Artifact
→ 如形成长期规则，进入开发约束
→ 如形成重大设计结论，进入设计与演进
→ 正式发布后，更新阶段记录和 Release
→ 工作记录移出活跃区，只保留近期摘要
```

不要求每次改动同时更新所有文档。

| 事件 | 通常更新 |
|---|---|
| 新需求确认 | 工作记录 |
| 普通缺陷修复 | 工作记录或仅 PR |
| 新增长期规则 | 开发约束 + 工作记录 |
| 重大架构选择 | 设计与演进；必要时开发约束 |
| 自动测试完成但待实机 | 工作记录改为待验证 |
| 正式发布 | 阶段记录 + Release；清理工作记录 |
| 纯文档纠错 | 只改对应文件 |

## 10. 最小模板

### 10.1 README.md

```markdown
# 产品名

一句话定位。

## 当前入口

- 当前正式基线：[阶段记录](阶段记录.md)
- 当前工作：[工作记录](工作记录.md)
- 长期规则：[开发约束](开发约束.md)（如存在）
- 设计原因：[设计与演进](设计与演进.md)（如存在）

## 工程入口

代码路径、构建命令、活动 CI。

## 分支

项目 exp → 项目 stable → main → 标签与 Release。
```

### 10.2 工作记录.md

```markdown
# 产品名工作记录

## 当前基线

版本、分支、当前目标。

## 活跃事项

| 工作项 | 状态 | 完成标准 | 证据/尚缺 |
|---|---|---|---|

## 暂缓或取消

| 工作项 | 状态 | 原因 | 重新评估条件 |
|---|---|---|---|

## 最近完成

只保留近期摘要和证据链接。
```

### 10.3 阶段记录.md

```markdown
# 产品名阶段记录

## 当前正式基线

- 版本：
- 标签：
- 正式提交：
- CI：
- Artifact：
- 交付物与 SHA-256：
- 已知限制：
```

## 11. 常见反模式

避免：

- 项目刚建立就生成五个空文档；
- README 同时承担百科、计划、历史和发布记录；
- 工作记录长期堆积全部已完成功能；
- 阶段记录不断追加所有旧版本；
- 每个按钮调整都建立规则编号或设计决策；
- 同一内容在多个文件完整复制；
- 为满足行数、条目数或编号形式机械整理；
- 下位规则自行声明可以覆盖上位规则；
- 没有证据就把事项写成完成；
- 每次修改都同时更新三到五份文档。

## 12. 对现有项目的处理

### Mediova

已经具有较完整的五文件记录，不需要推翻重写。

后续从下一轮开发开始逐步收敛：

- 工作记录从完整功能总表转为当前看板；
- `软件开发总结.md` 可继续保留，职责逐步收缩为设计与演进；
- 不为历史功能补编号；
- 不为形式立即改名。

### AtlasDesk

可先保持现状。

下一次进入持续开发时：

1. 先补齐轻量 `工作记录.md`；
2. 将现有长期架构和数据边界整理为项目 `开发约束.md`；
3. 只有需要解释重大取舍时，再建立 `设计与演进.md`。

不要为了与 Mediova 目录完全一致而一次性创建所有文件。

## 13. 最终原则

```text
能用三个文件解决，就不要用五个。
能用链接解决，就不要复制内容。
能由 Git 和 CI 保存，就不要再造一份历史。
能写成一条清晰规则，就不要设计一套流程。
```

文档体系的价值是减少下一次理解成本，而不是增加每一次开发成本。
