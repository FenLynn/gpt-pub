# 软件设计记录建议书

本文件用于指导 GPT-Pub 桌面软件的长期记录方式。

目标只有一个：**让新对话能够快速接续，同时不让文档维护反过来拖慢开发。**

本文件是参考建议，不自动等同于分类级强制约束。真正的强制规则只来自仓库、分类或项目自己的约束文件。

---

## 1. 最终模型

软件项目初始只建立三个文件：

```text
README.md
工作记录.md
阶段记录.md
```

出现长期不可破坏的规则时，再增加：

```text
开发约束.md
```

出现重大架构取舍、历史路线替代或长期技术债时，再增加：

```text
设计与演进.md
```

因此默认路线是：

```text
三文件起步
→ 确有需要才升级四文件
→ 再有需要才升级五文件
```

文档数量由真实复杂度决定，不由项目身份决定。不要为形式创建空白文件，也不要为了目录统一重写稳定历史。

## 2. A、B、C 约束层级

```text
A｜仓库级规则
↓
B｜分类级规则
↓
C｜项目级规则
```

| 层级 | 典型文件 | 适用范围 |
|---|---|---|
| A | `/GPT_RULES.md` | 整个 GPT-Pub |
| B | `/projects/1-桌面软件/开发约束.md` | 所有桌面软件；仅在确有共享硬规则时创建 |
| C | `项目目录/开发约束.md` | 单个项目；仅在项目需要长期约束时创建 |

### 2.1 文件名保持稳定

不建议改成 `A-GPT_RULES.md`、`B-桌面软件约束.md`、`C-项目约束.md`。

原因是：

- `GPT_RULES.md` 是稳定入口；
- 文件所在路径已经表达作用域；
- 固定名称 `开发约束.md` 更方便新对话和工具查找；
- A、B、C 是逻辑层级，不需要污染文件名。

更推荐在约束文件开头标明：

```markdown
> 约束层级：C｜项目级
> 适用范围：P101 Mediova
> 上位规则：A｜/GPT_RULES.md；B｜../开发约束.md（不存在时写“无”）
```

### 2.2 下位规则的边界

默认关系为：

```text
A > B > C
```

下位规则可以：

- 细化上位规则；
- 增加更严格的要求；
- 补充上位规则未规定的本地细节。

下位规则不得：

- 放宽上位规则；
- 与上位规则冲突；
- 写一句“本项目特殊”就自行覆盖上位规则。

### 2.3 分类约束的创建门槛

B 级规则原则上至少应服务两个项目。只适用于一个项目的规则应留在 C 级。

适合进入 B 级的内容，例如：

- 正式开发统一走 `项目 exp → 项目 stable → main`；
- 一个项目不得修改另一个项目的源码、CI 和发布记录；
- Runtime、Release 和 Artifact 不得包含用户私人数据；
- 数据迁移不得静默删除旧数据或覆盖已存在的新数据；
- 正式发布必须记录提交、CI、交付物和 SHA-256；
- 桌面界面变更必须考虑窗口尺寸、DPI、最大化和多显示器。

只属于 AtlasDesk 或 Mediova 的规则不得为了“看起来通用”上升到 B 级。

### 2.4 规则编号按需使用

真正需要长期引用的规则可以编号：

```text
A-01
B-03
C-07
```

编号只用于稳定、长期、可能被其他文档引用的规则。普通说明、示例、临时要求和一次性修复不编号。

### 2.5 例外写在上位规则中

确需突破上位规则时，不另建“例外文件”，也不能只在下位文件中声明。

例外应登记在被突破的上位约束中：

```markdown
### EX-01｜限定例外名称

- 对应规则：A-04
- 适用范围：P102 v0.8.0 首次迁移
- 原因：……
- 主要风险：……
- 失效条件：……
```

C 如需突破 B，先在 B 中授权；B 如需突破 A，先在 A 中授权。

## 3. 文件职责

| 文件 | 唯一职责 |
|---|---|
| `README.md` | 从哪里开始 |
| `工作记录.md` | 当前正在做什么 |
| `阶段记录.md` | 当前正式基线得到了什么 |
| `开发约束.md` | 现在不能违反什么 |
| `设计与演进.md` | 为什么形成当前设计 |

### 3.1 README.md

只保留：

- 软件的一句话定位；
- 当前正式基线、当前工作和可选约束文档的链接；
- 代码、构建和活动 CI 入口；
- 分支与发布入口。

README 不复制完整架构、全部计划、历代版本和发布哈希。

### 3.2 工作记录.md

只回答：

```text
现在做什么
方案是否确定
还缺什么
如何才算完成
证据在哪里
```

它是滚动看板，不是完整功能清单，也不是永久历史库。

### 3.3 阶段记录.md

只保存当前正式基线或当前未发布基线：

- 版本、分支、正式提交、标签和 Release；
- 当前仍成立的重要架构结论；
- CI、测试和自检结果；
- Artifact、EXE、ZIP 大小和 SHA-256；
- 正式交付内容；
- 已知限制和剩余风险。

新版本发布后，阶段记录整体更新到新基线。旧版本由 Git 标签、Release 和历史提交保存。

### 3.4 开发约束.md

只保存当前仍生效的长期规则。

适合写：

```text
必须
不得
仅允许
默认
除非经过明确决策
```

不适合写：

```text
当前正在修复
本轮已经完成
下一步准备
某次 CI 已通过
```

### 3.5 设计与演进.md

只记录真正昂贵、长期有影响的决定，例如：

- 部署形态、Runtime 或 Data 架构变化；
- 数据位置或格式变化；
- 模块职责和边界变化；
- 已投入明显成本的路线被放弃；
- 长期兼容层或技术债；
- 后续很可能被再次提出的错误路线。

按钮位置、颜色、间距、圆角和普通缺陷修复不进入设计与演进。

重大决策可在同一文件内使用简化编号，不为每项决定单独建立 ADR 文件。

## 4. 何时升级到四、五文件

### 4.1 增加开发约束.md

满足以下任意一项：

- 同一个长期决定已经被破坏过一次；
- 涉及用户数据、隐私、备份、迁移或不可逆操作；
- 存在固定分支、CI、发布、交付或兼容规则；
- 某项规则预计会影响多个后续版本；
- 多个对话或代理容易对此作出不同理解；
- 某些默认行为一旦改变会产生明显风险。

### 4.2 增加设计与演进.md

满足以下任意一项：

- 一个决策影响两个以上模块；
- 改变 Runtime、Data、部署或更新架构；
- 存在多个可行路线并已明确取舍；
- 放弃过一条已经投入明显开发成本的路线；
- 仅看当前代码无法理解为什么这样设计；
- 同一错误路线很可能被后续对话反复提出。

反过来说，普通 UI 调整、一次性版本计划和小型缺陷修复不足以触发新增文件。

## 5. 单一事实源与允许重复

| 信息 | 主文件或主证据 |
|---|---|
| 仓库硬规则 | `GPT_RULES.md` |
| 分类共享硬规则 | 分类 `开发约束.md`，如存在 |
| 项目长期规则 | 项目 `开发约束.md`，如存在 |
| 项目入口 | `README.md` |
| 当前工作 | `工作记录.md` |
| 当前正式基线 | `阶段记录.md` |
| 重大设计原因 | `设计与演进.md`，如存在 |
| 实现事实 | 源码 |
| 验证事实 | 测试和 CI |
| 历史事实 | Git、PR、标签和 Release |
| 截图、视频、完整日志 | PR、Issue 或 Artifact |

同一完整事实只写在一个主文件中，其他位置只写一句摘要和链接。

允许简短重复的内容仅限：

```text
产品名称
项目编号
正式路径
长期分支
当前正式版本
文档链接
```

不应重复完整架构、完整任务清单、完整 CI 结果、完整兼容策略和完整历史演进。

文档不能用“写了已完成”替代真实实现和验证证据。

## 6. 新对话读取顺序

先读取约束：

```text
A｜/GPT_RULES.md
→ B｜分类开发约束.md（如存在）
→ C｜项目开发约束.md（如存在）
```

再读取项目状态：

```text
README.md
→ 阶段记录.md
→ 工作记录.md
→ 设计与演进.md（按当前任务选择性阅读）
```

`设计与演进.md` 可能逐渐变长，不要求每个新对话无差别全文读取。

## 7. 工作记录保持轻量

推荐状态只保留：

| 状态 | 含义 |
|---|---|
| 待决策 | 问题已确认，路线尚未确定 |
| 计划 | 路线已确定，尚未开始 |
| 进行中 | 已开始实施，尚未完成 |
| 待验证 | 自动验证完成，仍缺实机或用户确认 |
| 暂缓 | 当前不推进，并说明重新评估条件 |
| 取消 | 明确不再实施，并保留原因 |

不要同时使用复选框和状态字段。

最小字段只需：

```text
工作项
状态
完成标准
证据或尚缺内容
```

### 7.1 完成判定

一个事项只有同时满足以下条件，才能移入“最近完成”：

```text
实现已经存在
+
完成标准已经满足
+
至少有一种可追溯证据
```

证据可以是 PR、提交、CI、Artifact、截图或用户实机确认。

自动 CI 无法证明视觉或真实设备问题时，应标记为“待验证”，不能提前写成完成。

### 7.2 稳定编号按需使用

只有以下情况才建议使用 `AD-UI-001`、`MV-MEDIA-001` 等编号：

- 多个事项并行；
- 一个事项跨多个 PR；
- 需要在反馈、截图、测试和提交之间反复引用；
- 仅靠任务名称已经容易混淆。

普通小修复直接使用任务名称、PR 号或版本号即可。

### 7.3 不要求所有小修改先建项

以下事项实施前应进入工作记录：

- 用户确认的独立需求；
- 影响架构、数据、隐私或兼容性的修改；
- 跨多个提交或需要实机验收的工作；
- 计划进入正式版本的功能和缺陷。

拼写修正、明显路径错误、同一任务内的小型回归和纯文档纠错，可以在 PR 或完成时补充。

工作记录只保留活跃事项、近期候选和少量最近完成。数量只是整理提示，不是机械门槛。

---

## 8. 更新规则

不要求每次修改同时更新所有文档。

| 事件 | 通常更新 |
|---|---|
| 新需求确认 | 工作记录 |
| 普通缺陷修复 | 工作记录或仅 PR |
| 新增长期规则 | 开发约束；必要时工作记录 |
| 重大架构选择 | 设计与演进；必要时开发约束 |
| 自动测试完成但待实机 | 工作记录改为待验证 |
| 正式发布 | 阶段记录 + Release；清理工作记录 |
| 纯文档纠错 | 只改对应文件 |

每次正式发布只检查四项：

1. `阶段记录.md` 更新为新的正式基线；
2. `工作记录.md` 移出完成项，只留近期摘要；
3. `开发约束.md` 仅在长期规则变化时更新；
4. `设计与演进.md` 仅在重大设计变化时更新。

README 只有入口、路径、构建方式或阅读顺序变化时才更新。

截图、视频、逐像素比较和完整测试日志留在 PR、Issue 或 Artifact；项目文档只保留结论和证据链接。

## 9. 项目迁出、停止或冻结

项目迁出或停止维护时：

- README 改为只读历史说明和新维护位置；
- 工作记录停止增加活动事项；
- 阶段记录冻结最后正式状态和迁移结果；
- 开发约束与设计演进保留历史，不继续扩展；
- 活动 CI、发布和开发停止；
- 源码、提交、标签和历史证据保留，不重写、不删除。

已迁出项目不得在原仓库恢复第二条活动主线，除非先明确重新调整唯一事实源。

## 10. 最小模板

### README.md

```markdown
# 产品名

一句话定位。

## 当前入口

- 正式基线：[阶段记录](阶段记录.md)
- 当前工作：[工作记录](工作记录.md)
- 长期规则：[开发约束](开发约束.md)（如存在）
- 设计原因：[设计与演进](设计与演进.md)（如存在）

## 工程入口

代码路径、构建命令、活动 CI。

## 分支

项目 exp → 项目 stable → main → 标签与 Release。
```

### 工作记录.md

```markdown
# 产品名工作记录

## 当前目标

本轮要解决的问题。

## 活跃事项

| 工作项 | 状态 | 完成标准 | 证据/尚缺 |
|---|---|---|---|

## 暂缓或取消

| 工作项 | 状态 | 原因 | 重新评估条件 |
|---|---|---|---|

## 最近完成

只保留近期摘要和证据链接。
```

### 阶段记录.md

```markdown
# 产品名阶段记录

## 当前基线

- 版本或状态：
- 分支：
- 正式提交：
- 标签与 Release：
- CI：
- Artifact：
- 交付物与 SHA-256：
- 已知限制：
```

## 11. 对现有项目的处理

Mediova 已具有较完整记录，后续渐进收敛：工作记录转为当前看板，`软件开发总结.md` 逐步承担设计与演进职责，不为历史功能补编号，不为形式立即改名。

AtlasDesk 保持现状。下一次进入持续开发时，先补轻量工作记录；确有长期规则时再整理项目开发约束；确有重大设计取舍时再增加设计与演进。

两个项目都不需要为了与本建议书完全一致而立即重写稳定文档。

---

## 12. 最终原则

```text
能用三个文件解决，就不要用五个。
能用链接解决，就不要复制内容。
能由 Git 和 CI 保存，就不要再造一份历史。
能写成一条清晰规则，就不要设计一套流程。
```

文档体系的价值是减少下一次理解成本，而不是增加每一次开发成本。
