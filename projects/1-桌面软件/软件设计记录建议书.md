# 软件设计记录建议书

本建议书用于 GPT-Pub `projects/1-桌面软件/` 下长期维护的软件项目，目标是在不制造文档负担的前提下，让新对话、自动化代理和后续开发者能够快速理解项目边界、设计原因、当前工作和正式版本结果。

本建议书是分类级参考标准。项目可根据规模采用完整或轻量方案，但项目自己的 `开发约束.md` 一旦引用或采纳其中规则，即应按项目约束执行。

## 1. 核心目标

软件记录体系应同时解决五个问题：

1. **入口**：项目是什么，应从哪里开始阅读；
2. **边界**：哪些规则长期有效，什么不能被破坏；
3. **原因**：当前设计为何形成，哪些方案已经尝试或放弃；
4. **进度**：现在正在做什么，怎样才算完成；
5. **证据**：当前正式版本经过了什么验证，交付物是什么。

任何文件都不应同时承担上述全部职责。

## 2. 四条总原则

### 2.1 一类信息只有一个主文件

同一完整事实只允许有一个权威归属。其他文件只能给出简短指针，不复制整段内容。

例如：

```text
Runtime 不得包含用户数据
→ 完整规则写入《开发约束》

README
→ 只写“Runtime/Data 详细边界见《开发约束》”

阶段记录
→ 只写“本次发布已通过 Runtime/Data 边界扫描”及验证证据
```

允许在多个文件中重复的内容仅限必要身份信息：产品名、项目编号、正式路径和文档链接。即使重复，也应保持简短。

### 2.2 文档记录结论，不替代代码和证据

- 源码是实现事实源；
- 自动测试和 CI 是验证事实源；
- Git 提交、PR、标签和 Release 是历史事实源；
- 文档负责解释边界、原因、当前状态和正式结论。

不得用“文档写了已完成”替代实际实现和验证。

### 2.3 工作记录是当前看板，不是永久历史库

工作记录只保留活跃事项、待验证事项、近期候选和少量最近完成项。完整历史由 Git、PR、Release 和阶段记录保存。

不得把软件历代全部功能长期堆入工作记录。

### 2.4 规范应随项目规模伸缩

长期迭代的桌面应用推荐采用完整五文件结构；一次性工具或小型辅助程序可以采用轻量结构，不应为了形式创建长期空白文档。

## 3. 推荐文档结构

### 3.1 完整方案

适用于 AtlasDesk、Mediova 等长期迭代、具有数据兼容和发布流程的软件：

```text
项目目录/
├── README.md
├── 开发约束.md
├── 设计与演进.md
├── 工作记录.md
├── 阶段记录.md
└── 代码/
```

### 3.2 轻量方案

适用于功能单一、生命周期短、没有复杂架构的软件：

```text
项目目录/
├── README.md
├── 工作记录.md
└── 阶段记录.md
```

当项目出现以下任一情况时，再新增 `开发约束.md`：

- 存在用户数据、不可逆操作或隐私边界；
- 存在固定分支、CI、发布或兼容规则；
- 多轮开发中已经发生过“修复一个问题又破坏旧决定”；
- 项目需要多个对话或代理长期接续。

当项目出现以下任一情况时，再新增 `设计与演进.md`：

- 发生重大架构选择；
- 存在多个可行路线且已经明确取舍；
- 有历史兼容层或技术债需要解释；
- 新开发者只看当前源码无法理解设计原因。

## 4. 单一事实源分工

| 信息类型 | 权威文件 | 说明 |
|---|---|---|
| 产品定位、项目入口、阅读顺序 | `README.md` | 简短导航，不展开百科式说明 |
| 当前有效的必须、不得和默认规则 | `开发约束.md` | 只保留当前生效规则 |
| 重大设计原因、历史取舍、被替代方案 | `设计与演进.md` | 允许保留已废弃决策及替代关系 |
| 当前进行中、已决策、待验证、暂缓事项 | `工作记录.md` | 滚动维护，不承担永久历史 |
| 当前正式版本、提交、CI、哈希、交付和限制 | `阶段记录.md` | 只保存当前正式基线 |
| 历代版本说明 | GitHub Release | 不在阶段记录中无限追加 |
| 具体代码变化 | Git 提交和 PR | 文档只引用，不复制完整 diff |

### 4.1 当前规则与历史决策的区别

这是最容易混淆的边界：

- `开发约束.md` 只写**现在仍然生效**的规则；
- `设计与演进.md` 可以记录**过去为什么这样做、后来为何被替代**。

例如：

```text
当前规则：Dashboard 跨域外链交给系统默认浏览器
→ 开发约束.md

历史原因：早期所有弹窗均内嵌 WebView2，复杂站点导致 RenderProcessUnresponsive，因此改为混合模式
→ 设计与演进.md
```

## 5. README 标准

### 5.1 唯一职责

README 只负责让第一次进入项目的人在一分钟内知道：

- 软件是什么；
- 当前正式基线在哪里查看；
- 当前开发进度在哪里查看；
- 应按什么顺序阅读；
- 如何进入代码、构建和分支流程。

### 5.2 推荐结构

```markdown
# 产品名

一句话定位。

## 当前入口

- 正式基线：见 [阶段记录](阶段记录.md)
- 当前工作：见 [工作记录](工作记录.md)
- 长期规则：见 [开发约束](开发约束.md)
- 设计原因：见 [设计与演进](设计与演进.md)

## 新对话阅读顺序

1. 开发约束.md
2. 设计与演进.md
3. 工作记录.md
4. 阶段记录.md

## 工程入口

代码路径、构建入口、活动 CI。

## 分支

项目 exp → 项目 stable → main → 标签与 Release。
```

### 5.3 容量建议

- 推荐不超过约 100–150 行；
- 不复制完整架构、任务列表、发布哈希和历史演进；
- 入口、路径或阅读顺序变化时才更新。

## 6. 开发约束标准

### 6.1 唯一职责

保存未来一段时间仍必须遵守的当前规则。

适合使用的表达：

```text
必须
不得
仅允许
默认
除非经过明确决策
```

不适合的表达：

```text
当前正在修复
本轮已经修改
下一步准备
CI 某次运行已经通过
```

### 6.2 推荐主题

1. 项目身份与允许修改范围；
2. 分支、PR、CI、发布和交付；
3. 用户数据、隐私、备份和迁移；
4. Runtime、依赖和本地 Data 边界；
5. 默认行为与兼容原则；
6. UI、DPI、最大化、多显示器和可访问性；
7. 性能、并发、资源释放和长期运行；
8. 测试、故障注入、真实环境验证；
9. 文档更新职责；
10. 不过度设计和根因优先原则。

### 6.3 更新触发

仅在以下情况更新：

- 新增长期规则；
- 原规则失效或被替代；
- 数据或兼容边界变化；
- 测试、发布或交付门槛变化；
- 用户明确作出长期产品决策。

普通按钮、颜色或一次性修复不进入开发约束。

## 7. 设计与演进标准

### 7.1 唯一职责

解释当前设计为何形成，而不是罗列历代所有功能。

推荐按主题组织：

```text
产品定位的形成
Runtime 与 Data 的关系
关键模块边界
重要技术路线选择
历史兼容层与技术债
已放弃方向
```

### 7.2 使用简化决策记录

不为每个决定创建单独 ADR 文件，以免目录膨胀。重大决策在同一文件中使用稳定编号：

```markdown
### AD-D-004｜Dashboard 采用混合浏览模式

- 状态：生效
- 问题：所有新窗口都进入内嵌 WebView2，复杂外站可能拖死渲染进程。
- 决策：同域页面和必要登录留在内部，跨域外链交给默认浏览器。
- 原因：保留 Dashboard 工作台体验，同时避免把 AtlasDesk 做成通用浏览器。
- 影响：外部网站使用系统浏览器和浏览器扩展；AtlasDesk 只维护自身页面。
- 替代：无。
```

决策状态建议固定为：

- `生效`：当前仍采用；
- `已替代`：由新决策取代，并注明新编号；
- `未采用`：经过评估但没有执行；
- `试验`：尚未成为正式路线。

编号一经分配不得重用或重新编号。

### 7.3 更新触发

只有以下变化进入设计与演进：

- 重大架构调整；
- 模块职责变化；
- 数据格式或部署方式变化；
- 重要技术路线被采用或放弃；
- 发现会长期影响后续开发的根因；
- 历史兼容层需要保留、合并或清除。

## 8. 工作记录标准

### 8.1 唯一职责

回答以下问题：

```text
现在做什么？
方案是否已经确定？
还缺什么？
如何验收？
证据在哪里？
```

### 8.2 不使用“复选框 + 状态”双重表达

以下形式容易失配：

```text
[x] + 进行中
[ ] + 完成
```

因此只保留一个受控状态字段，不再同时使用复选框。

推荐状态：

| 状态 | 含义 |
|---|---|
| `待决策` | 问题已确认，但路线尚未确定 |
| `已决策` | 方案已确定，尚未开始或尚未完成实现 |
| `进行中` | 已开始实施，尚未达到完成标准 |
| `待验证` | 实现和自动验证已完成，仍需真实环境确认 |
| `计划` | 已认可，但不进入当前实施窗口 |
| `暂缓` | 当前不推进，并注明原因 |
| `取消` | 明确不再实施，并保留原因 |

完成项不继续占据活跃状态区，只进入“最近完成”。

### 8.3 工作项稳定编号

推荐格式：

```text
<项目缩写>-<领域>-<三位序号>
```

AtlasDesk 示例：

```text
AD-UI-001
AD-WIN-001
AD-DEV-001
AD-WEB-001
```

Mediova 示例：

```text
MV-UI-001
MV-MEDIA-001
MV-TASK-001
```

编号用于在工作记录、PR、提交、测试和用户反馈之间建立引用，不因排序变化而重编号。

### 8.4 推荐结构

```markdown
# 产品名工作记录

## 当前基线

正式基线、开发分支、当前目标版本。

## 进行中

| 编号 | 状态 | 工作项 | 完成标准 | 证据/尚缺 |

## 已决策，待实施

| 编号 | 状态 | 工作项 | 完成标准 | 决策依据 |

## 等待实机确认

| 编号 | 自动验证 | 实机确认项 | 当前风险 |

## 下一步候选

| 编号 | 状态 | 工作项 | 进入条件 |

## 暂缓或取消

| 编号 | 状态 | 原因 | 重新评估条件 |

## 最近完成

最多保留最近 10 项，每项只留一句结果和证据链接。
```

### 8.5 容量建议

- 活跃事项推荐不超过 20 项；
- “最近完成”最多保留 10 项；
- 超过限制时应重新排序、拆分版本范围或把远期内容移入“计划/暂缓”；
- 不建立无限增长的“全部完成历史”章节；
- 删除旧完成项不等于删除历史，Git、PR、Release 和阶段记录仍保留证据。

### 8.6 完成判定

一个工作项只有同时满足以下条件才能进入“最近完成”：

1. 代码或文档已经实现；
2. 预先写明的完成标准全部满足；
3. 相应自动测试、构建或检查通过；
4. 无法自动覆盖的内容已明确标为“待验证”，不能提前写成完成；
5. 证据列包含 PR、提交、CI、Artifact、截图或用户实机确认之一。

不得只因“已经写了代码”就记为完成。

## 9. 阶段记录标准

### 9.1 唯一职责

阶段记录只保存**当前正式版本的冻结快照**：

- 正式版本与标签；
- 源提交；
- 重要架构结论；
- 数据兼容结论；
- CI、测试和自检结果；
- Artifact、EXE、ZIP 的大小和 SHA-256；
- 正式交付内容；
- 已知限制和剩余风险。

### 9.2 不无限追加历代版本

发布新版本时，整体更新 `阶段记录.md` 为新的正式基线。旧版本由以下位置保存：

```text
Git 标签
GitHub Release
Git 历史
旧提交中的阶段记录
```

阶段记录不是完整版本年表。

### 9.3 正式证据要求

不能只写“测试通过”，应尽可能记录：

```text
CI 运行编号
测试数量或自检数量
Artifact 编号
正式提交
文件大小
SHA-256
剩余人工验证项目
```

## 10. 信息生命周期

推荐流转如下：

```text
用户确认需求
→ 工作记录：待决策 / 已决策
→ 开始实施
→ 工作记录：进行中
→ 自动验证完成
→ 工作记录：待验证或最近完成
→ 形成长期规则
→ 开发约束
→ 形成重大设计结论
→ 设计与演进
→ 正式发布
→ 阶段记录 + GitHub Release
→ 工作记录移出活跃区，仅保留近期摘要
```

一项内容不应在五个文件中同时完整复制。

不要求每次修改同时更新所有文档。

## 12. AtlasDesk 示例

以下示例只说明记录格式，不作为 AtlasDesk 实时状态的权威来源；实际状态仍以 P102 项目文件为准。

### 12.1 README 示例

```markdown
# P102｜AtlasDesk

AtlasDesk 是面向个人科研与软件开发的 Windows 桌面工作台。

## 项目入口

- 当前正式基线：见《阶段记录》
- 当前开发：见《工作记录》
- 长期规则：见《开发约束》
- 设计原因：见《设计与演进》
```

### 12.2 开发约束示例

```markdown
## Dashboard 浏览边界

- Dashboard 自身域名、内部路由和必要身份验证允许在 AtlasDesk WebView2 内打开。
- 其他域名的外链默认交给 Windows 系统默认浏览器。
- AtlasDesk 不发展为通用浏览器，不为外部复杂网站维护完整标签页、下载、权限和扩展体系。
- WebView2 渲染进程失去响应时，必须隔离故障并允许恢复 Dashboard，不能让整个应用永久进入错误页。
```

### 12.3 设计与演进示例

```markdown
### AD-D-004｜Dashboard 采用混合浏览模式

- 状态：生效
- 问题：早期所有新窗口都进入共享 WebView2，复杂外站可能导致 RenderProcessUnresponsive。
- 决策：同域页面和登录留在内部，跨域外链交给默认浏览器。
- 原因：保留工作台体验，并避免把 AtlasDesk 做成半个浏览器。
- 影响：外站可使用完整浏览器能力和 Bitwarden 扩展。
```

### 12.4 工作记录示例

| 编号 | 状态 | 工作项 | 完成标准 | 证据/尚缺 |
|---|---|---|---|---|
| `AD-UI-001` | 已决策 | 主界面改为连续式左右布局 | 去掉左右大卡片、阴影和中间空槽，仅保留一根分割线 | 用户已确认方案 |
| `AD-WIN-001` | 进行中 | 修复最大化工作区 | 顶部、底部不裁切，任务栏正常保留，多 DPI 可用 | 尚缺 Windows 实机回归 |
| `AD-DEV-001` | 进行中 | 恢复开发环境页 | 项目与环境均可见，终端不再隐藏环境控件 | 尚缺实现与 CI |
| `AD-WEB-001` | 已决策 | Dashboard 混合外链 | 跨域外链进入默认浏览器 | 用户已确认方案 |
| `AD-WEB-002` | 计划 | WebView2 故障恢复 | RenderProcessUnresponsive 后可重建或恢复主 Dashboard | 尚未实施 |

### 12.5 阶段记录示例

```markdown
## 当前正式版本

- 版本：v0.8.0
- 标签：p102-v0.8.0
- 正式提交：<commit>
- Windows CI：<run>
- Runtime ZIP：<size>，SHA-256 `<hash>`
- 已知限制：Dashboard 外部复杂站点仍需在后续版本切换为混合模式
```

## 13. Mediova 后续调整建议

Mediova 已经建立了较完整的 `README.md`、`开发约束.md`、`软件开发总结.md`、`工作记录.md` 和 `阶段记录.md`，无需推翻重写。后续可渐进调整：

1. 保留 `开发约束.md`，删除其中已经失效的版本性描述，只保留当前生效规则；
2. 将 `软件开发总结.md` 的职责收缩为设计原因和演进经验；文件名可在文档整理版本中改为 `设计与演进.md`，也可暂时保留旧名以避免无价值的链接变动；
3. 将 `工作记录.md` 从“完整功能总表”改为活跃看板，移除长期完成清单，只保留最近 10 项完成摘要；
4. `阶段记录.md` 只保存当前正式版本的冻结证据，不继续累积历代版本；
5. `README.md` 缩短为入口和导航，详细内容改为链接；
6. 新工作项逐步采用 `MV-领域-序号` 编号，不要求一次性为所有历史功能补编号。

迁移原则是**从下一轮开发开始逐步收敛**，不为文档形式重写稳定历史，也不制造没有实际收益的大规模改名。

## 14. 常见反模式

以下做法应避免：

- README 同时复制架构、历史、工作清单和全部发布哈希；
- 开发约束中混入“当前正在修复”的流水账；
- 设计与演进按每个补丁版本机械追加功能列表；
- 工作记录长期保留几百条已完成能力；
- 阶段记录不断追加所有旧版本，变成第二份 Release 页面；
- 同一工作项既写复选框又写状态，二者可能互相矛盾；
- 没有完成标准和证据就标记完成；
- 为每个小决定创建单独 ADR 文件，导致目录碎片化；
- 每改一个按钮就同时修改五个文档；
- 删除暂未完成事项以制造“全部完成”的假象。

## 15. 文档质量检查

每次正式发布或重大文档整理时，检查：

- [ ] README 是否仍然只是入口；
- [ ] 每条长期规则是否只在开发约束中完整出现；
- [ ] 重大设计结论是否说明了问题、决策、原因和影响；
- [ ] 工作记录是否只保留活跃窗口和最近 10 项完成；
- [ ] 工作项状态是否使用受控词汇，没有复选框冲突；
- [ ] “完成”是否有明确证据；
- [ ] 阶段记录是否只对应当前正式版本；
- [ ] 旧版本是否已经由标签和 Release 保存；
- [ ] 文档之间是否使用链接而不是复制整段内容；
- [ ] 是否存在已经失效但仍被写成当前规则的内容。

## 16. 最终推荐

长期桌面软件默认采用：

```text
README.md
开发约束.md
设计与演进.md
工作记录.md
阶段记录.md
```

其职责可以概括为：

```text
README       → 从哪里开始
开发约束     → 现在不能违反什么
设计与演进   → 为什么形成当前设计
工作记录     → 当前正在做什么
阶段记录     → 当前正式版本最终得到了什么
```

通过单一事实源、稳定编号、受控状态、证据闭环、滚动清理和按规模裁剪，可以同时获得良好的新对话接续能力与较低的长期维护成本。
